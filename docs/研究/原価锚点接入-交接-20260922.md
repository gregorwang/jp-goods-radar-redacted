# 原価（定価）锚点接入：可行性实测与接入方案 — 交接文档

**日期**：2026-09-22
**时区**：所有时间以 UTC 记录（数据库、`next_run_at`、日志都是 UTC）。用户所在时区 **UTC+8**。
**本次会话**：只做了调研与实测，**没有改动任何代码**。
**相关文档**：判据总纲见 `AGENTS.md §4`；外部仓库见 `gregorwang/jp-market-databricks`。
**对侧交接**：`jp-market-databricks` 仓库的改动提示词已单独交付用户，本文只写 jpgr 这一侧。

起因：用户提出"能不能批量调用 `jp-market-databricks` 里那个查原価的 API，去算每天关键词抓到的商品"。
结论是能接、几乎零成本，**但可用率远低于直觉，必须按它真实的样子设计，否则会造出新的误报源**。

---

## 1. 这个东西是什么

`jp-market-databricks/apps/teika-lookup-worker` 是一个查**厂商定価 / 官方参考原価**的服务。
输入一个日文商品名，返回**带类型的答案**，不是"价格或空"：

| `match_type` | 含义 | 能不能用 |
|---|---|---|
| `exact` | 归一化标题精确命中一件商品 | ✅ 直接用 |
| `variant` | 同作品同形态、含全部判别词的候选 | ⚠️ **是列表不是单值** |
| `approximate` | 召回最相关的发售母体或同系列周边供参考 | ❌ 不是这件商品的原価 |
| `category_stat` | 认得出作品和品类，但库里没这件商品 | ❌ 只能当区间 |
| `ip_not_covered` | 认得出作品，但没采 | ❌ 不等于"市面上没有" |
| `unparsed` | 没解析出来 | ❌ |

它自己的 API 文档第一页就在警告：**不要取 `candidates[0]`，不要对 `variant` 求平均**。
这套纪律和 `AGENTS.md §4` 的「判定档位 vs 送达门槛」是同一个东西，接入时必须原样继承。

---

## 2. 架构事实（决定了怎么接）

- `price_reference` 与 `jpgr` 是**同一台 VPS（203.0.113.10）同一个 PostgreSQL 17 集群下的两个独立数据库**。
- 查询本体 `lookup_teika(q)` 就是 `price_reference` 里的一个 **PostgreSQL 函数**
  （`pg/price_reference/lookup.sql`），Databricks 只是兜底。
- 对侧 Worker 已有 Hyperdrive 绑定 `PRICE_DB`，配置 id `your-hyperdrive-id`，
  只读角色 `teika_reader`。**jpgr 的 collector 复用同一个配置即可，不需要新基础设施。**
- 实测单次查询 **32 毫秒**（100 条 3.246 秒）。每天 182 件新商品 ≈ 6 秒数据库时间。

**结论：不要走 HTTP 网关。** 走 HTTP 等于 Cloudflare 绕一圈回到同一台机器，而且会压
`teika-lookup-worker/README.md` 里已经记录的那个连接数问题（40 并发时约 1/4 被
Hyperdrive 报 `CONNECTION_CLOSED`，README 自己怀疑是 jpgr 占用了 `max_connections`）。

跨库不能直接 join，所以是两次查询，不是一条 SQL。

## 3. 实测数据（全部跑在生产数据上，不要重新推导）

### 3.1 清洗不是瓶颈 —— 600 条真实商品名

网关入口的 `clean()`（`src/index.js`）**已经**剔除 `未開封 / 新品 / 中古 / 美品 /
送料無料 / 即購入OK / 匿名配送` 等品相与物流词。用户担心的"煤炉脏标题没清洗"这件事，
它在做。

| 方案 | `exact` | 商品级（exact+variant） | `unparsed` |
|---|---|---|---|
| A 原始标题直查（**绕过网关清洗，是错误测法**） | 4 | 51（8.5%） | 222（37.0%） |
| B 网关 `clean()` 等价实现 = **线上真实行为** | 1 | 58（9.7%） | 189（31.5%） |
| C1 只 NFKC+停用词，不删括号 | 2 | 59（9.8%） | 198（33.0%） |
| C2 B + 新增噪音规则（促销词 / `◆☆★` / `検:` 尾巴 / レンタル落ち / ポイント最大N倍） | 1 | 62（10.3%） | 190（31.7%） |

**加了一整套噪音规则只多救回 4 条（+0.7%）。清洗这条路已经走到头了，不要再投入。**

按来源（A 原样 → B 网关清洗后的商品级命中）：

| 来源 | A | B |
|---|---|---|
| mercari_jp | 12.4% | 12.4% |
| yahoo_fleamarket_jp | 9.5% | 9.5% |
| surugaya | 6.0% | **10.8%**（`【中古】` 被剔除） |
| rakuten_ichiba | 2.8% | 3.8% |
| yahoo_auctions_jp | 0% | 3.3% |

反直觉但重要：**个人二手平台命中率最高**（卖家照抄官方商品名），**乐天最差**
（标题塞满促销词，解析失败率 58.5%）。

### 3.2 真正卡住的地方是判别词，不是噪音

限定在**收录作品范围内**的 491 条：

| 结果 | 占比 |
|---|---|
| `approximate`（认出作品和品类，认不出是哪一件） | **66.4%** |
| `unparsed` | 16.5% |
| `variant` | 12.4% |
| `category_stat` | 4.5% |
| `exact` | 0.2% |

而这些失败里品类**大多解析出来了**（FIGURE 126 条、DISPLAY 39、ACRYLIC 26；
只有 99 条连品类都没解析出）。卡住的是**角色 / 版本 / 系列对不上具体哪一件** ——
和 jpgr 自己 2026-09-05、09-06 两次事故完全同一个难题。

### 3.3 机制：查询越长，命中越少

`variant` 的判据是「候选必须包含查询里的**全部**判别词」。所以：

| 方案（800 条样本） | 商品级命中 |
|---|---|
| 原始标题（已清洗） | 51（6.4%） |
| **AI 抽取字段重拼成短查询** | **90（11.3%）** |
| 日文原标题**追加** AI 角色+版本（即加长） | 31（**3.9%**） |

**加长直接腰斩。** 噪音词删不删是次要的，查询长度才是主要矛盾。

### 3.4 有效做法：用已有的 AI 抽取字段重拼短查询

`radar_analytics.ai_enrichments` 里已存 **19,142 条** `listing_semantics`，
字段含 `workTitle` / `characters` / `productType` / `editionOrModel` / `series`。
**这笔 Gemini 费用已经付过了。**

重拼规则（实测用的）：`workTitle + characters + productType + editionOrModel`

| 输入（800 条） | 商品级 | `category_stat` | 能给出任何价格参考 |
|---|---|---|---|
| 原始标题（已清洗） | 6.4% | 3.1% | 9.5% |
| **AI 重拼** | **11.3%** | **16.1%** | **27.4%** |

最能说明问题的一条 —— **原标题里根本没有作品名**：

```
原始: BANDAI SPIRITS ESPRESTO Excite Motions エミリア
      → unparsed
重拼: Re:从零开始的异世界生活 エミリア 手办 ESPRESTO Excite Motions
      → variant，唯一命中
```

AI 把标题里缺失的作品名补上了。这是纯文本清洗永远做不到的。

> **未验证的增量空间**：重拼时 `workTitle` 有时输出中文（`Re:从零开始的异世界生活`），
> 而对侧 API 的已知缺口是「中文字形不通日文汉字」。那些命中实际是靠角色名
> `エミリア` 撞上的。若改用保留日文的作品名，命中率应当还能再涨——**这一条没测，
> 是明确的待验证项。**

### 3.5 决定性约束：候选定価发散

对 11.3% 的命中逐条检查候选定価的收敛性（800 条样本）：

| 口径 | 条数 | 占 800 条 |
|---|---|---|
| 重拼后拿到含定価的候选 | 76 | 9.5% |
| └ 候选只有 1 个（**可直接用**） | 7 | **0.9%** |
| └ 多候选但定価收敛（hi ≤ lo×1.2，**可直接用**） | 5 | **0.6%** |
| └ **定価发散（>1.2 倍，不可当单值）** | 64 | **8.0%** |

多候选的 hi/lo 倍率：**p25 = 1.50，p50 = 3.33，p90 = 13.67**。

实例：

```
リゼロ エミリア フィギュア 箱無し     → 7 个候选，定価 4,180 ~ 27,258（6.5 倍）
エミリア アクリルキーホルダー         → 20 个候选，定価   660 ~  2,200（3.3 倍）
リゼロ クリアファイル 13点まとめ売り  → 命中单件クリアファイル（打包货配单件定価，口径错误）
```

**能给出一个可信定価数字的只有 1.5%，折合每天约 2.7 件。**

### 3.6 那 1.5% 的价值（为什么仍然值得做）

variant 命中里能算溢价率的 45 条：倍率 **p25 = 0.57 / p50 = 1.07 / p75 = 2.52**，
其中 **19 条低于定価**。溢价最高的一条是：

```
冴えない彼女の育てかた Fes. Fine A3プリモアート
定価 22,000 円  →  挂牌 39,000 円  =  1.77 倍
```

**这正是 2026-09-05 事故里那件商品**（见 `AGENTS.md §4`）。当时系统在版本上判错、
戴着"确认同款"的帽子发了邮件。定価锚点不修匹配器，但它会在同一封邮件里写出
"这条在要 1.77 倍原价"——**一条独立于匹配逻辑的刹车**。

### 3.7 三个档案永远查不到

对侧 `items_classified` 共 **77,814** 件：

| jpgr 档案涉及的作品 | 库里件数 |
|---|---|
| 初音ミク / 雪ミク | 8,232 |
| Re:ゼロ | 7,362 |
| 冴えカノ | 4,297 |
| メダリスト | 1,187 |
| **WHITE ALBUM2** | **0** |
| **氷菓 / 千反田** | **0** |
| **高木さん** | **0** |

不是没匹配上，是真的一件都没有。`keyword` 档案「冰菓·千反田爱瑠全品类」、
`exact_product` 档案「高木さん からかいパーカー」「WHITE ALBUM2 ぬいぐるみ」
接入后必须**显式标注"该作品不在原価库覆盖范围"**，绝不能表述成"查不到这件商品"
——后者会让用户以为是非官方周边。这是对侧文档明确的红线。

参考量级：jpgr 近 30 天新增 5,471 件商品，其中 **3,609 件（66%）**标题里含收录作品别名。
作品认得出，但只有 10% 能落到商品级——差距全在判别词。

## 4. 接入方案：两档，不是一个数字

**不要做"给每条商品标定価"。数据不支持——每天只有约 2.7 件能标。**

正确的产品形态是**两档标注 + 每档案可配的送达门槛**，与 `AGENTS.md §4` 同构：

### 档位 A：确定定価（`converged`，约 1.5%）

候选唯一，或多候选定価收敛（hi ≤ lo×1.2）。
邮件里可以写完整句子：**「定価 22,000 円，这条 39,000 円（1.77 倍）」**。

### 档位 B：离谱价格警报（`diverged` 但挂牌价超出区间上限，约 8%）

候选定価发散时**不说"定価是多少"**，只用**区间上限作反证**：

> 钥匙扣候选定価 660 ~ 2,200 円，整个系列最贵的一款也才 2,200 —— 煤炉要 8,000，
> 不管它具体是哪一款，8,000 都离谱。

这条推理在候选发散时**依然成立**，因为它用的是区间上限而不是某一个候选。
这正是 `AGENTS.md §4`「拒绝要有反证」：**候选里最贵的一款都低于挂牌价，这是反证，
可以定案；候选发散本身只是证据不足，只能降档，不能拿来报价。**

### 永不进邮件

`approximate`（44.4%）、`category_stat`（16.1%）、`ip_not_covered`、`unparsed`。
这两类加起来占 47%，是**最容易被误用的**——它们回答的是"这一类通常多少钱"，
而用户问的是"这件多少钱"。问题被换掉了，必须说明，不能静默降级。

## 5. jpgr 侧待办

对侧（`jp-market-databricks`）要先落地三件事，**其中第 2 件是本侧的硬依赖**：
把 `clean()` 下沉成 PG 函数共用一份、`lookup_teika()` 返回 `price_band`
（`n / lo / hi / ratio / converged`）、修 `exact` 被清洗破坏的 bug。
提示词已单独交付用户。

本侧待办：

1. **Hyperdrive 绑定**。`apps/collector` 增加一个指向 `price_reference` 的绑定，
   复用配置 id `your-hyperdrive-id`，只读。
   注意 `PRIMARY_DB` / `ANALYTICS_DB` 已经是同一个 Hyperdrive 的两个绑定，
   这是第三个，指向**不同的数据库**，不要混用。

2. **重拼查询**。从 `radar_analytics.ai_enrichments`（`purpose='listing_semantics'`）
   取 `workTitle + characters + productType + editionOrModel` 拼成短查询。
   **不要**把原始标题也拼进去（实测掉到 3.9%）。
   待验证：优先使用保留日文的作品名（见 §3.4）。

3. **落库**。存**整个带类型的答案**（`match_type` + `price_band` + 候选摘要），
   **不是一个价格字段**。只存一个数字，就是在重犯 `AGENTS.md §4` 骂的那个
   "输出二值化"的错误。建议挂在 `watch_run_listing_observations` 上，
   与 `ai_relevance` / `ai_confidence` 并列——那两列的先例
   （`postgres/migrations/20260906190000_suspect_notice_policy.sql`）
   说明了为什么"AI 说了但没落成列"等于没说。

4. **送达门槛**。档位 B（离谱警报）的触发倍率必须是**每个档案一个设置**，
   不能有全局开关，默认取严。理由同 `suspect_notice_policy`：
   同一个 2 倍溢价，对求了三年的绝版是可以接受，对随手加的便宜货是骚扰。

5. **`verify:sql`**。本次改动涉及新 SQL，推送前 `.githooks/pre-push` 会跑。
   注意新增的是**跨库查询**，`scripts/verify-operational-sql.mjs` 当前只对 `jpgr` 库
   做 PREPARE——针对 `price_reference` 的语句能不能被它覆盖，**需要先确认**，
   不要默认它会自动生效。

## 6. 不要做的事

- **不要加噪音词规则。** 已实测收益 0.7%（§3.1）。
- **不要取 `candidates[0]`、不要求平均、不要 `coalesce` 出一个数**。对侧文档与
  `AGENTS.md §4` 双重禁止。
- **不要为了提升命中率放宽判别词判据。** 候选发散已经是主要问题（p90 差 13.67 倍），
  放宽只会让区间更没用。
- **不要把 `approximate` / `category_stat` 的数字写进邮件的价格行。**
- **不要训机器学习模型预测定価。** 覆盖内的商品是确定性查表，不需要模型；
  覆盖外的商品**没有办法验证预测对不对**（不在库里就是不在库里），
  一个无法验证的数字进了邮件就是新的误报源头。
  真正值得用模型的是"合理二级市场价"，但训练数据（787 条严格成交证据）目前太少，
  **这是攒数据的问题，不是训模型的问题**。

**不是生产对象，可以随时清掉**：

`clean_v1` 对对侧第 1 件事（把 `clean()` 下沉到 PG）有参考价值，其余可直接删。

```sql
DROP TABLE IF EXISTS cmp, r2, s2, t_sample, pair, pair2, pr, pr2, conv;

```

## 9. 一个顺带的发现（独立课题，不要和本次混做）

对侧还有 `apps/image-search-modal`：WD Tagger 粗搜 + DINOv2 重排，**3.3 万张官图**，
Modal T4 GPU，闲置 120 秒缩到 0。它同时回答两个问题：**这是哪件官方商品 + 它的定価**。

这正是 jpgr 最缺的那只眼睛——实测 jpgr 五大来源的 **JAN 覆盖率全是 0%**
（mercari_jp / yahoo_auctions_jp / rakuten_ichiba / yahoo_fleamarket_jp / surugaya），
而 `AGENTS.md §4` 把"硬标识符冲突"列为可以定案的反证，**这条路径在生产里从未触发过**。
同款判定 100% 压在文字上，这就是两次事故的共同土壤。而**图片覆盖率是 100%**。

约束：GPU 冷启动 20~45 秒，且对侧把图片接口限制在每天 20:00–23:00（Asia/Shanghai）开放。
每天 182 张图在一个窗口里跑得完，且与日报的夜间节奏天然契合。

**这一条本次没有实测，是独立的下一个课题。**
