# 煤炉卖家换货：商品档案误报调查（2026-10-14）

> 结论：**不是我们串了数据，是卖家把同一个链接改卖别的东西了**；系统只认商品 ID，没发现，按新东西的价格发了 4 封"降价"邮件。
> 频率极低（约三个月一次），**决定不修**，只把出事的档案暂停。以后真要做，方案见第 4 节——只用代码、不接 AI。

## 1. 现象

商品库里一件 ADAM ET ROPE 风衣（煤炉 `m65628273587`），点「管理关注档案」跳到的档案叫
「リゼロトレーディングビッグホロ缶バッジ エミリアの誕生日生活ver.コンプリート」，看起来像"商品和档案串了"，
而且这个档案用户不记得建过。

## 2. 经过（日本时间）

| 时间 | 发生了什么 |
|---|---|
| 10-12 17:12 | 「爱蜜莉雅」关键词档案搜到 `m65628273587`，当时标题是缶バッジ那串，8666 円 |
| 10-12 17:20 | 这件和另外 8 件一起推送到手机 App |
| 10-12 17:21 | 在 App 推送详情页点了「等降价」→ 建出这个商品档案，名字取自当时的标题（`apps/web/src/lib/listing-watch.ts`，经 `/api/device/watches`） |
| 10-12 白天 | 卖家把链接改成风衣：标题、成色（新品未使用 → 目立った傷や汚れなし）、价格都变了 |
| 10-13 05:02 / 17:37 / 23:58、10-14 08:05 | 系统把风衣的价格当缶バッジ在降，发了 4 封降价邮件（8666→7800→7200→6980→6500） |
| 10-14 | 档案 `b3738505-baa6-4b43-acdb-0123671a8d57` 手工暂停（和主站「暂停」按钮同一组语句） |

坐实的证据：17:20 那条推送（`events.id = 6bb65d6f-d400-4a5e-ac20-48121dac1505`）的 payload 里存着当时的原标题和价格。
旁证：风衣标题里没有「エミリア」，它不可能是靠这个标题被关键词搜到的。

同一晚 22:44 建的另一个缶バッジ档案（`m39869982997`）是正常的。7 个商品档案逐个比过档案名和现标题，**只有这一个中招**
（冴えカノ那个只是标题加了「a様専用」，还是同一件）。

## 3. 标题多常变、怎么变

观察表里 580 件商品在观察期内改过标题。按首末两次标题的字符相似度（两两字符组合的重合比例）分：

| 相似度 | 件数 | 典型 |
|---|---|---|
| 0.5 以上 | 548 | 加「最終価格」「値下げ」、乐天每周换优惠券前缀、全角半角、「18体→20体」 |
| 0.5 以下 | 32 | 见下 |

0.4 以下的 15 件里三种情况混在一起：

- **真换货**：本案风衣；「AMP+ 喜多川海夢フィギュア」→「フィギュア 8体セット」；「特典アクリルチャーム」→「缶バッジセット」
- **同一件**：「ねんどろいど レーシングミク」整个标题被替换成「バニラアイス様専用」——是给买家留货，反而说明快卖掉了
- **说不准**：「UNION ARENA エミリア SR」→「ユニオンアリーナ エミリア パラレル 星2」

所以**"标题哈希一变就判换货"太严**，会把那 548 件小改全误判；哈希只适合当"没变就放行"的第一道门。

注意这个数**偏低**：东西一换成风衣，关键词就搜不到它了，观察表看不到后续。真正相关的是商品档案这个小圈子——
盯的都是挂很久没卖掉、在等降价的货，正是卖家最可能放弃后改卖别的那批（7 个档案里出了 1 个，样本太小，不能当概率）。

## 4. 为什么不修，以及真要修怎么修

**不修的理由**（用户 10-14 拍板）：约三个月一次、损失是几封不该发的邮件、出事能挽回；
而改动至少 2 个文件（判降价的代码 `packages/core/src/events.ts` 拿不到旧标题，旧标题复查时就被覆盖了），完整版 4～5 个文件。
收益配不上工程复杂度。

**AI 判同款那层不要**：调 AI → 等回复 → 写库，这条链路的等待时长和数据库超时配错过（见行情邮件排查手册），
为极低频事件背这个风险不值。

**真要做时的方案**（只用代码）：

1. 建档时把标题存成"身份证"；每次复查先去噪（优惠券括号、値下げ / 最終価格 / ○○様専用、全半角）再比，一样就放行。
2. 对不上时算相似度：大部分相同 → 小改，照常跟踪，并把新标题记成新身份证。
3. 几乎完全不同（様専用除外）→ 这一轮不发降价，档案暂停，页面写明原标题和现标题，只通知一次。误判的代价只是一个暂停的档案，点"恢复"就回来。

## 5. 复现用的 SQL

```sql
-- 商品档案名 vs 现标题，找换货
select p.name, l.title, l.source_item_id, p.enabled
from radar_core.watch_profiles p
join radar_core.watch_bindings b on b.watch_profile_id=p.id
join radar_core.listings l on l.source_id=b.source_id and l.source_item_id=b.source_item_id
where p.dossier_kind='item' order by p.created_at;

-- 各来源有多少商品改过标题
with t as (
  select source_id, source_item_id, count(distinct title) n
  from radar_core.watch_run_listing_observations where title is not null group by 1,2)
select source_id, count(*) items, count(*) filter (where n>1) title_changed
from t group by 1 order by items desc;

-- 某条推送里当时的原标题（换成要查的 event id 和商品 ID）
select substring(payload_json from '.{0,50}m65628273587.{0,200}')
from radar_core.events where id='6bb65d6f-d400-4a5e-ac20-48121dac1505';
```

相似度分布那段用的是两两字符组合的 Jaccard（库里没装 pg_trgm，用 `generate_series` + `substr` 手算），
原始 SQL 较长，需要时按"首次标题 vs 最后标题，取 2 字切片求交并比"重写即可。
