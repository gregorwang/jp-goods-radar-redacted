# 数据库写入放大：每入库一轮就改写这个词的全部历史 · 实测（2026-10-14）

起因是"精确同款雷达每轮抓到的商品几乎一样，能不能不重复判定"。查下来 AI 早就按件缓存了
（WHITE ALBUM2 档案煤炉 7 天 56 轮、每轮同样 27 件，真正调模型 0 次），
但顺着"重复写入"查到了一个大得多的问题。

## 结论

- `radar_analytics.ingest_search_run` 每入库一轮，都会把这个关键词**有史以来所有**观测行的
  `is_new_for_query` 重算并写回，值没变也写（PostgreSQL 的 UPDATE 不管值变没变都写新行版本）。
- 实测：`listing_observations` 16.7 万行，累计 UPDATE **4847 万次**（平均每行被改写约 290 遍）。
  按 10-13 的轮数算每天约 **916 万次**行改写，真正需要变的是 **0 行**。
- 后果：表 855 MB，实际数据只有约 260 MB（`pg_dump` 压缩后 38 MB）；每轮入库越来越慢
  （历史最长的词每轮改写 41,468 行、2.75 秒），而且随历史只增不减。10-11 起改每小时抓，放大了 3 倍。
- 修法：UPDATE 加一个条件——值没变的行不写。结果逐行相同。
  迁移 `postgres/migrations/20261014120000_ingest_skip_unchanged_new_flag.sql`，10-14 11:52（日本时间）上线。
  同一个词新旧对比：41,468 行 / 2.75 秒 → 0 行 / 0.08 秒。
- 同日 `VACUUM (FULL, ANALYZE)` 收回空洞：855 MB → 315 MB，锁表 8.6 秒；磁盘剩余 7.7 → 8.4 GB。
  动手前把整表 `pg_dump` 到笔记本 `jpgr-backups/listing_observations-20261014.dump`（38 MB）。

## 同日第二轮：省地方（用户要求"现在就做"）

| 做了什么 | 效果 |
|---|---|
| 商品内容按指纹只存一份：新表 `radar_analytics.listing_payloads`，观测行只记 `payload_hash`；两个价格视图和 `packages/analytics` 的商品变体查询改读 `COALESCE(指纹表, 旧列)` | 16.8 万行里不重复的内容只有 6.3 万份；改造前后、清旧列后 `strategy_price_facts_v1` 17 万行逐行哈希一致 |
| 迁移 `20261014130000`（建表回填改入库改视图）→ `20261014131000`（补回视图的 `security_invoker`，被 CREATE OR REPLACE VIEW 冲掉了）→ `20261014140000`（网站代码上线后清旧列，再 VACUUM FULL） | |
| Databricks 同步：`--keep-local 0`，上传成功后删本机导出 | 每天省 2.9 GB 常驻（导出比整个库还大）；磁盘 75% → 67% |
| 同步脚本：`source_run_artifacts` 加进 `jpgr_history`，归档成功后本机只留 30 天（`LOCAL_TRIM_AFTER_ARCHIVE`） | 这张表仓库里没有读取方，约 7.5 MB/天、原来从不删 |

**结果（10-14 12:40 日本时间全部做完）**：`listing_observations` 早上 855 MB → 修空改写并压缩后 315 MB →
内容挪走、清旧列、VACUUM FULL 后 **42 MB**，另 `listing_payloads` 98 MB，合计 140 MB。
改造后第一轮真实入库（雅虎拍卖 80 件）：80 行全部只记指纹、指纹全能取到内容，其中只有 7 份是新内容。
清旧列后再算 `strategy_price_facts_v1`（改造前的 170,519 行），哈希与改造前一致。磁盘 33G 用 22G（66%），剩 12G。

试过但没用的：只调低压缩门槛（`toast_tuple_target` + lz4）只省 8%——重复是跨行的，单行压缩压不动。

**故意没动的**：`radar_core.watch_run_listing_observations` 的保留期（90 天，随 `watch_runs` 级联）。
日报的「最早见到」和疑似同款「只在第一次出现时提醒」都靠翻它的老记录（`packages/db/src/queries/digests.ts`），
缩短会让下架又上架的旧货被当新货再发、日期变错。它有 90 天上限，不会无限涨。

同步脚本改前备份：VPS `/usr/local/sbin/jpgr-databricks-sync.bak-20261014`。

## 顺带查清的几件事

| 项 | 数字（10-14） |
|---|---|
| 整库 | 2.26 GB；VPS 磁盘 33 GB，用 26 GB（每天在 25～27 GB 间晃，主要是 Databricks 导出的 2 GB 临时文件） |
| 两张"每轮看到了什么"表的新增 | 10-12 起各约 2.2 万行/天（之前约 1,500 / 2,700），原始数据合计约 50 MB/天 |
| 其中和上一轮一模一样的 | 10-13 当天 76%（只和当天上一条比，跨天没算） |
| 原始响应 `source_response_captures` | 约 250 MB/天，但 3 天后自动删，不会累积 |

**原来设想的"按保留期删旧记录"暂缓**：精简规则（每件商品第一条、每天第一条、每次有变化的都留）
按现有数据只能删掉 7 天前的 6,113 行，不值得冒险；而且 Databricks 的只增不删历史（`jpgr_history`）
目前**不含** `radar_analytics.listing_observations`，本机删了第二天镜像也跟着没了。
要做的话，先把这张表加进同步脚本的 `HISTORY_TABLES`（键 `run_id, source_listing_id`）。

## 怎么复查

```sql
-- 修好后 updated 的涨幅应约等于 inserted 的涨幅（v2 入库时给每条新行补一次商品内容，正常），
-- 不再是每小时几十万
select pg_stat_get_tuples_updated('radar_analytics.listing_observations'::regclass) updated,
       pg_stat_get_tuples_inserted('radar_analytics.listing_observations'::regclass) inserted;
```
