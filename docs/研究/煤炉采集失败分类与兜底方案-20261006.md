## 零、先说结论（三分钟版）

你的担心是：**煤炉一旦被 403，冷却 12 小时，接下来所有煤炉档案都采不到，
而煤炉又不像骏河屋那样有 Firecrawl 兜底。**

查完代码和生产库之后，结论是这样的：

1. **你担心的方向是对的，但"传染"的方式和你想的不一样。**
   代码里，一个煤炉档案撞了 403，只会冷却**它自己这一个档案**，不会直接把别的煤炉档案一起停掉。
   但是——煤炉现在**只有一条路**（Vercel 东京那台中转服务器）。如果煤炉拉黑的是这台中转的
   网络出口，那每个档案轮到自己的时候都会各自撞一次墙、各自冷却。最后的效果和"全部停掉"一模一样，
   而且**没有第二条路可以换**。

2. **真实发生的概率目前很低。** 生产库里从 2026-07-13 到今天（将近三个月），
   煤炉定时采集 1,714 次、手动搜索约 2,400 次，**一次 403 都没有**。
   唯一的一次 403 是 07-12 刚接入煤炉的那天，之后就改走了 Vercel 东京。
   这三个月里煤炉真正出过的问题是另外几种（见第二节），**而那几种问题，换条路同样能救**。

3. **比 403 本身更伤的，是这三点：**
   - 煤炉 10 个关键词档案里有 **9 个是一天只跑一次**。撞墙那一次就是当天唯一的一次，
     **当天不会再试**，这一天的新上架就漏了。12 小时冷却对它们反而没意义（反正明天才跑）。
   - 单个档案的"来源失败"告警要**连续失败 3 次**才发。对一天一跑的档案，就是**第 3 天**才收到。
     （当天日报里会有一行"煤炉采集失败"的提示，但很容易被看漏。）
   - 代码目前**分不清**"煤炉拦了我们"和"我们自己的中转站拦了我们"，两种都会当成煤炉 403 处理。

4. **我的建议：先做"主路 + 备路"，不做"节点轮换池"。**
   - 现成的备路就在手边：VPS 上的采集服务（source-runner）**早就有煤炉的代码**，
     08-21 到 09-09 还以"影子模式"真实跑过三周，只是后来为了省请求量关掉了。
   - 改成：**Vercel 东京失败 → 自动换 VPS 再试一次**。和骏河屋现在的兜底是同一个思路，
     **不花新钱**（VPS 本来就包月）。
   - 冷却从"整个煤炉冷却"改成"**哪条路坏了冷却哪条路**"。
   - 两条路都不通，才判定"煤炉整体出问题"，这时**当场发一封告警**，不等第 3 次。
   - 节点池（很多 IP 轮着用）**现在不做**，理由在第五节。

## 一、先搞懂：煤炉现在是怎么采的

### 1.1 一次煤炉采集走的路

```
  Cloudflare 上的采集程序（collector）
            │  "帮我搜一下这个关键词"（带签名，防止别人冒用）
            ▼
  Vercel 东京中转服务（your-mercari-service.vercel.app，机房在东京 hnd1）
            │  用自己的网络出口去访问煤炉
            ▼
  煤炉官方接口 api.mercari.jp
```

打个比方：采集程序是"你本人"，Vercel 东京是"你在东京雇的跑腿"，煤炉是"商店"。
商店只看得见跑腿，看不见你。**商店要拉黑，拉黑的也是跑腿。**

### 1.2 煤炉能凭什么认出"又是这个人"

煤炉的接口要求每次请求带一个"签名"（技术名叫 DPoP，可以理解成一张一次性的身份牌）。
**我们的代码每次请求都现场生成一张全新的身份牌**，所以煤炉没法靠身份牌认出我们。

那它能凭什么认？剩下的只有：

| 能被认出来的东西 | 说明 |
|---|---|
| **网络出口（IP 地址）** | Vercel 东京用的是亚马逊云（AWS）东京机房的 IP。这是最可能被拉黑的东西。 |
| **请求的"样子"** | 请求头怎么写、多久来一次、一次翻几页。样子太像机器人，换 IP 也会被认出来。 |
| **请求的频率** | 太快会被限速（通常是 429，不是 403）。 |

这一点很重要：**它决定了"换节点"到底有没有用。** 如果煤炉拉黑的是 IP，换节点有用；
如果煤炉认的是"请求的样子"，换多少个节点都一样被拦。

### 1.3 现在有没有备用路？

**代码层面有，开关是关着的。**

- VPS（203.0.113.10）上的采集服务 source-runner 里，**已经写好了煤炉的采集代码**，
  而且只允许访问煤炉的搜索和商品详情两个接口，很安全。
- 有一个开关 `MERCARI_SOURCE_RUNNER_MODE`，三档：
  - `off`（现在）：只走 Vercel 东京。
  - `shadow`（08-21 ~ 09-09 用过）：每次同时走两条路，用 Vercel 的结果，VPS 的结果只用来对账。
    09-09 关掉了，原因是煤炉看到的请求量翻了一倍，而且拖慢了队列。
  - `primary`：整个煤炉改走 VPS。
- **问题在于：这是"整体切换"，不是"坏了才换"。** 没有任何一档是"Vercel 失败了自动换 VPS 再试"。
  骏河屋有这个能力（直连 → Firecrawl → 浏览器 → Vercel，一条一条往下试），煤炉没有。

还有一个**没核实的点**：VPS 的出口在新加坡（代码注释里这么写）。影子模式那三周，
VPS 那条路到底成功率多少，当时只写在 Cloudflare 的运行日志里，没有存进数据库，**现在已经查不到了**。
所以在把 VPS 当备路之前，**必须先实测一次 VPS 能不能正常拿到煤炉数据**（交接文档里写了怎么测）。

## 二、采集失败到底分哪几种

这是这份文档最核心的部分。你说得对：**先分清楚是哪种失败，才知道该怎么办。**
官方挂了就等，节点被拦就换路，我们自己写错了就改代码——**用错药比不吃药还糟**
（比如官方挂了你还拼命换节点重试，只会让自己更像攻击者）。

我把所有可能的失败分成 9 种，按"换条路有没有用"排：

### 总表

| # | 失败类型 | 打个比方 | 煤炉回什么 | 换条路有用吗 | 这三个月真实发生过吗 |
|---|---|---|---|---|---|
| A | **商品本身没了** | 你要找的那件货，卖家下架了 | 403（但正文里写着"商品不可见"）/ 404 / 410 | ❌ 不是故障，不用换 | ✅ 发生过（单品跟踪时），**已经修好**能正确识别 |
| B | **网络抖了一下** | 电话信号断了一秒 | 超时、连接中断 | ✅ 立刻再打一次就行 | ✅ 09-10 一次超时 |
| C | **我们的中转站挂了** | 跑腿的生病了 | Vercel 回 502、回一段不是数据的文字 | ✅ **换个跑腿就行** | ✅ **08-21 ~ 09-04 共 15 次**，最常见的一种 |
| D | **我们的中转站自己拦了我们** | 跑腿的门卫不让你进 | Vercel 回 403（网页而不是数据） | ✅ 换路有用，但根子要去 Vercel 后台修 | ❌ 没发生过，但**代码会把它误判成煤炉 403** |
| E | **被限速** | 商店说"你来得太勤了，过会儿再来" | 429 | ⚠️ 原则上应该**等**，不该换着 IP 硬闯 | ❌ 没发生过 |
| F | **出口 IP 被拉黑** | 商店把这个跑腿列进黑名单 | 403 | ✅ **换个跑腿就行** —— 这就是你担心的那种 | ❌ 三个月 0 次（07-12 接入当天有过 1 次） |
| G | **请求方式被识破** | 商店不认人，认的是"这种问法就是机器人" | 403（所有路都 403） | ❌ 换多少个跑腿都没用，要改请求方式 | ❌ 没发生过 |
| H | **煤炉官方挂了 / 在维护** | 商店今天关门 | 500、502、503，或者维护页 | ❌ 没用，只能等 | ❌ 没发生过 |
| I | **我们自己的代码或签名出错** | 你给跑腿的地址写错了 | 400、401，或者我们自己报错 | ❌ 换路没用，要改代码 | ✅ 09-04 ~ 09-05 那次数据库参数错误（10 次）；跟煤炉无关，但同样让煤炉停了一晚 |

（"煤炉接口改版、我们解析不了"算 I 的一种，代码已经会直接停用并发通知。）

### 怎么分辨？——"换条路试一次"本身就是最好的诊断

你会发现 C、D、F 三种"换路有用"的，和 G、H 两种"换路没用"的，**光看第一次失败是分不出来的**——
它们都可能是 403 或 5xx。

**分辨的办法很简单：换另一条路试一次，看结果。**

| Vercel 东京 | 换 VPS 再试 | 说明是哪种 | 应该怎么办 |
|---|---|---|---|
| 失败 | **成功** | C / D / F —— 问题在 Vercel 这条路上 | 这次用 VPS 的结果，**只冷却 Vercel 这条路**；其他煤炉任务这段时间直接走 VPS |
| 失败 | 也失败，同样的 403 | G（请求方式被识破）或煤炉整体收紧了对机房 IP 的态度 | **整个煤炉暂停**，**当场发告警**，需要人看 |
| 失败 | 也失败，同样的 5xx | H（煤炉官方挂了） | 等。几十分钟后再试，不发吓人的告警 |
| 400 / 401 / 代码错误 | 不用试 | I（我们自己的问题） | 换路没意义，直接报错，发告警 |
| 商品不可见 | 不用试 | A（商品没了） | 现在的处理就是对的 |

这就是为什么我说**两条路就够解决绝大多数问题**——第二条路既是"备胎"，也是"诊断工具"。

## 三、现在的冷却逻辑，具体哪里不对

### 3.1 一个煤炉档案撞了 403 之后，现在实际会发生什么

拿一个"每天跑一次"的煤炉关键词档案举例（10 个里有 9 个是这种）：

| 时间 | 发生了什么 |
|---|---|
| 第 1 天 08:00 | 轮到它，经 Vercel 东京访问煤炉，回 403 |
| 第 1 天 08:00 | 代码一律当成"被煤炉拉黑"：**这个档案冷却 12 小时**；同时在"来源总表"上把煤炉标成 `blocked`、冷却 12 小时 |
| 第 1 天 08:00 | **不会换路，不会重试**——当天这一次就丢了 |
| 第 1 天 稍后 | 当天日报里会多一行"煤炉采集失败"，但这封日报照常发出，**容易看漏** |
| 第 1 天 20:00 | 冷却结束。但这个档案本来就排在明天，所以**冷却对它其实没起任何作用** |
| 第 2 天 08:00 | 再试，如果出口还在黑名单上，再 403，再丢一天 |
| 第 3 天 08:00 | 第三次失败，**这时才发"来源连续失败"告警邮件** |

**也就是说：在最坏的情况下，你要到第 3 天才收到正式告警，这期间煤炉的上新全漏了。**
而煤炉上的东西大多是一次性挂牌（AGENTS.md 里写的：C2C 售出即终局），漏了就是真漏了。

### 3.2 其他煤炉档案会不会被"传染"？

**按代码，不会直接被传染。** 细节是这样的：

- 来源总表上确实会写"煤炉冷却 12 小时"，
- 但这条记录**没写是哪条路被冷却**，代码看到"没写路"就默认是"Cloudflare 直连"那条路，
- 而煤炉根本不走 Cloudflare 直连，所以煤炉的其他定时任务**完全不看这条记录**，照常去请求 Vercel。

结果是：

- 如果 403 只是偶发（Vercel 某一个出口 IP 被临时拦了），其他档案照样能成功 —— 这是好事。
- 如果 Vercel 的出口整体被拉黑，其他档案会**一个接一个地各自撞墙**，每个都丢掉自己当天那一次。
  效果等同于"整个煤炉停了"，只是代码里没有任何一个地方意识到"整个煤炉停了"。
- 管理后台的来源页会显示煤炉"blocked"，**但这个状态对煤炉的采集实际上不起作用**，容易误导人。

### 3.3 问题清单

| # | 问题 | 后果 |
|---|---|---|
| 1 | **煤炉只有一条路** | Vercel 这条路一出问题（不管是 C、D 还是 F），煤炉就整体停摆，没有任何自救 |
| 2 | **403 一律当成"被煤炉拉黑"** | 分不清 D（自己的中转站拦了自己）和 F（被煤炉拉黑）；修错方向 |
| 3 | **冷却是"按档案"或"按来源"，不是"按路"** | 没法表达"Vercel 这条路坏了，但 VPS 那条是好的" |
| 4 | **一天一跑的档案失败后当天不补** | 一次失败 = 丢一整天 |
| 5 | **告警要连续失败 3 次** | 对一天一跑的档案，就是第 3 天才知道 |
| 6 | **来源总表的"blocked"对煤炉不生效** | 后台显示和实际行为不一致 |

## 四、我的建议方案

按"先做最便宜、最管用的"排序。每一层都可以单独上线、单独回退。

### 第一层：给煤炉加一条备路（最重要）

**做什么：** Vercel 东京失败时（403、5xx、超时、回了乱码），**自动改走 VPS 再试一次**。

**为什么是 VPS：**
- 代码现成：VPS 上的煤炉采集代码已经写好、跑过三周；采集程序里调 VPS 的代码也现成。
  要写的主要是"失败后换路"这一段，和骏河屋的兜底链是同一个套路。
- 不花新钱：VPS 本来就是包月的。
- 出口和 Vercel 完全不同：Vercel 是亚马逊云东京的 IP，VPS 是另一家机房、另一个国家的 IP，
  **两者同时被拉黑的概率比"同一家云的两个机房"低得多**。

**前提：** 先实测 VPS 能不能正常拿到煤炉数据（VPS 在新加坡，煤炉对海外 IP 的态度没验证过）。
测不通的话，退到"备选：Vercel 大阪"（见 4.6）。

**要注意的规矩：**
- **只换一次。** 主路失败 → 备路试一次 → 还失败就停。不搞"一直换一直试"。
- **备路成功也要记账**：这次是靠备路救回来的、主路为什么失败，要能在后台看到，
  不然主路烂了几个月都没人知道。（骏河屋现在就是这么记的，可以照抄。）
- 商品不可见（A）、我们自己的错误（I）**不换路**，换了也没用。
- 被限速（E，429）**原则上不换路**，按煤炉说的时间等。换 IP 硬闯是在跟对方的规则对着干。

### 第二层：冷却改成"哪条路坏了冷却哪条路"

**做什么：**
- Vercel 东京被 403 → **只冷却 Vercel 这条路** 12 小时。这 12 小时里，所有煤炉任务**直接走 VPS**，
  不再每次先去 Vercel 撞一下墙。
- VPS 也被 403 → 两条路都冷却，判定为"煤炉整体出问题"（G 或者煤炉收紧了），整个煤炉暂停。
- 冷却到期后，先拿一个任务去试主路，通了再全部切回来。

**好处：** 代码里第一次有了"整个煤炉停了"这个明确的状态，后台显示和实际行为一致了。

**这块代码里已经有一半：** 来源总表本来就有一个"冷却的是哪条路"（`cooldown_route`）的字段，
骏河屋在用，煤炉的失败处理只是没往里写。

### 第三层：失败的每日档案，当天补跑一次

**做什么：** 一天一跑的煤炉档案，如果这次是"两条路都失败"（不是商品没了、不是我们的代码错），
**2～3 小时后再补跑一次**，而不是等到明天。

**为什么间隔 2～3 小时：** 立刻重试大概率还是同样结果，还会让煤炉觉得你在硬闯；
等太久又失去意义。2～3 小时足够让临时性的拦截、官方维护过去。

**只补一次。** 补跑也失败，就等明天。

### 第四层：告警分级

| 情况 | 现在 | 建议 |
|---|---|---|
| 主路失败、备路救回来了 | 无 | **不发邮件**，只在每周一的周报体检里列出"本周煤炉主路失败 N 次，全部由备路救回" |
| 两条路都失败（整个煤炉不通） | 第 3 天才发 | **当场发一封**，标题写清楚"煤炉全线不通"；同一天最多一封 |
| 我们自己的代码 / 签名错误 | 第 3 次才发 | 当场发一封，同一天最多一封 |
| 商品没了 | 不发 | 保持不发（这不是故障） |

这样做也符合 AGENTS.md 里"注意力是最稀缺的资源"那条：**救回来的事不打扰你，救不回来的事马上告诉你。**

### 第五层：把"中转站自己拦了自己"认出来

**做什么：** Vercel 回来的 403 如果**不是**煤炉的数据格式（而是一个网页、一段报错文字），
就说明是 Vercel 那边（防火墙、部署保护之类）拦的，不是煤炉拦的。
这种情况要**单独标记**，告警里写"Vercel 中转被拦，去 Vercel 后台看"，而不是"煤炉封了你"。

**改动很小**，但能避免将来某一天你对着"煤炉 403"查半天，最后发现是 Vercel 后台某个设置被改了。

### 4.6 备路的几个候选，比一比

| 候选 | 出口在哪 | 花钱吗 | 工作量 | 风险 / 不确定 | 我的看法 |
|---|---|---|---|---|---|
| **VPS source-runner** | 新加坡（另一家机房） | 不花（已包月） | 小，代码现成 | 煤炉对新加坡 IP 的态度**没实测** | **首选**，先实测 |

## 五、关于"节点轮换池"——我的看法

你的直觉"一个节点被拦了就换一个"**方向是对的**，但我建议把它改造一下：

**不要"轮换"，要"主备"。**

| | 轮换池（每次请求换一个 IP） | 主备（平时走主路，坏了换备路） |
|---|---|---|
| 煤炉看到的样子 | 同一个"人"的请求从十几个 IP 轮流过来——**这本身就是最典型的爬虫特征** | 平时始终是同一个来源，很正常 |
| 能不能诊断问题 | 很难。失败了不知道是哪个 IP 的问题，还是请求方式的问题 | 很清楚。主路挂、备路通 = 主路的问题；两个都挂 = 不是 IP 的问题 |
| 成本 | 要买节点、要维护节点健康、要写调度 | 两条路都已存在，几乎不花钱 |
| 能覆盖的情况 | F（IP 被拉黑） | C、D、F 都能覆盖 |

而且几个事实让节点池**现在不值得做**：

1. **三个月 0 次 403。** 为一个三个月没发生过的问题投入 1～1.5 天开发 + 每月节点费，不划算。
   而这三个月真正发生过的问题（Vercel 502 十五次、超时一次），**主备两条路就能救**。
2. **之前的评估文档已经定过规矩**（`docs/进行中/服务能力扩张-后续任务-20260909.md` 第 7 项）：
   节点池优先级最低，**数据显示"卡在出口"才做**；并且明确写了
   "不能设计成撞限制就无限换 IP 重试"。
3. **如果哪天真的出现"Vercel 和 VPS 同时被 403"**，那说明煤炉认的不是单个 IP，
   而是"机房 IP"这一整类，或者认的是请求方式。这种情况下，便宜的机房代理节点大概率也一起被拦，
   节点池救不了；真要救只能上住宅 IP（贵，而且你之前对雅虎购物的决定是"不买住宅 IP"）。

**所以我的建议是：先上主备两条路，把"哪条路坏了"的数据攒起来。**
如果某天数据显示"主路和备路轮流被封、封得越来越频繁"，那时再上节点池，而且有数据告诉你需要几个节点。
