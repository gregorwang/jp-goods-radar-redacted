# 煤炉单个 IP 能抓多快 · 实测（2026-10-08）

> 研究文档：记录实测数据和由此得出的判断。会随新数据更新，最后更新 2026-10-08。
> 起因：用户计划以后抓很多商品，想知道一个机场节点抓煤炉的上限，判断要不要做节点池。
> 原始数据：VPS `/root/mercari-ramp/ramp.jsonl`（每次请求一行）、`summary.log`（每档汇总）、`ramp.mts`（测试脚本）。

---

## 一、结论（先看这个）

1. **一个机场节点连续 10 分钟每秒 2 次，煤炉一次都没拦，也没变慢。** 上限在这之上，这次没摸到。
2. **对煤炉来说，"太快"不是主要风险，"被认出是机器"才是。** 所以煤炉的节点池不是为了分摊请求量，
   而是为了一个出口被拉黑时还有备用——这件事 2026-10-08 已经用"Vercel 主路 + VPS 备路"做了（见
   `docs/进行中/煤炉兜底-交接-20261006.md`）。
3. **按现在的业务量，一个出口离上限还差几千倍。** 现在煤炉每天 31 次请求；实测的速度折合每天 17 万次。
   即使以后有 1000 个每日档案（每天约 1000~3000 次），也用不到一个节点能力的 2%。
4. **这不等于可以无限抓。** 下面第四节列了这次没测到的东西，扩量之前要补测。

---

## 二、怎么测的

- **出口**：机场香港节点 `198.51.100.30`（AS38136 Akari Networks）。在 VPS 上另起一个临时代理（mihomo，
  端口 17890），**没用** VPS 自己的 IP、也没用 Vercel，测到被封也不影响生产。测完已关闭、配置已删。
- **请求**：和生产完全一样的煤炉搜索接口（`/v2/entities:search`），每次现场生成新的签名密钥和设备号
  （DPoP，和生产一样）。10 个动漫周边关键词轮换，每次取 30 条。
- **节奏**：5 档逐级加速，每档 10 分钟；同时在途的请求最多 4 个。一出现 403 / 429 就停，转为每 5 分钟试一次，记录多久恢复。
- **时间**：2026-10-08 05:58 ~ 06:48 UTC（北京时间 13:58 ~ 14:48）。

## 三、结果

| 档位 | 速度 | 请求数 | 失败 | 耗时中位 | 耗时 p95 | 最慢 |
|---|---|---:|---:|---:|---:|---:|
| 1 | 每 10 秒 1 次（6 次/分） | 60 | 0 | 305 ms | 579 ms | 726 ms |
| 2 | 每 5 秒 1 次（12 次/分） | 120 | 0 | 312 ms | 484 ms | 598 ms |
| 3 | 每 2 秒 1 次（30 次/分） | 300 | 0 | 265 ms | 439 ms | 629 ms |
| 4 | 每秒 1 次（60 次/分） | 600 | 0 | 260 ms | 450 ms | 930 ms |
| 5 | 每秒 2 次（120 次/分） | 1200 | 0 | 251 ms | 409 ms | 2070 ms |

合计 2280 次，0 失败。越往后反而越快（中位从 305 降到 251 毫秒），说明对方没有在"放慢"我们。

同一天另测：VPS 自己的出口（新加坡 Leaseweb 机房 IP `203.0.113.10`）搜一次 5 条，442 毫秒正常返回。

## 四、为什么这么宽松（推断，未验证）

煤炉的搜索接口就是它自己网页和 App 在用的那个接口。由此推断：

- **一个 IP 背后可能是成百上千个真人。** 手机运营商、学校、公司的出口都是很多人共用一个 IP。
  如果按单个 IP 卡得很严，会大面积误伤真用户，所以单 IP 的线通常放得很宽。
- **它更可能看"像不像机器"，而不是"多快"。** 比如请求签名是否合法、请求头和加密握手的特征像不像浏览器、
  行为像不像人（只搜不点、全天匀速、几小时不停）。我们每次请求都现场生成新签名和设备号、格式与网页端一致，
  在它看来像"很多个刚打开网页的访客各搜了一次"。
- **搜索对它来说很便宜。** 只读、可以缓存；它真正要防的是撞库登录、刷单、批量下单这类会造成损失的行为。

**反例要记住：** 煤炉确实拦过我们一次——`source_registry.last_403_at = 2026-07-12 02:45 UTC`（不在定时运行记录里，
多半是一次手动搜索或连接测试），原因没查清。所以"会不会被拦"是真实存在的风险，只是这次的数据说明它不是由速度触发的。

## 五、这次没测到的（扩量之前要补）

| 没测的 | 为什么重要 | 怎么补测 |
|---|---|---|
| 按小时 / 按天累计的总量 | 只跑了 50 分钟。如果它限的是"每小时多少次"，这次看不出来 | 每秒 1 次连续跑 3~6 小时 |
| 商品详情接口（`/items/get`） | 单品跟踪走的是这个接口，限流规则可能和搜索不同 | 同样的阶梯，换成详情 |
| 更高并发 | 这次同时在途最多 4 个 | 只在真要上量时测 |
| 机房 IP 和机场 IP 待遇是否一样 | 生产用的是 Vercel（东京机房）和 VPS（新加坡机房），这次测的是机场 IP | 用 VPS 本机 IP 测——**会拿生产出口冒险，先问用户** |
| 机场 IP 是多人共用的 | 别人的用量也算在这个 IP 上，测出来的数偏保守，而且每天可能不一样 | 不同时段重测一次 |

## 六、对产品决策的影响

- **煤炉不需要为了"量"做节点池。** 什么时候需要第二个出口：某个出口被拉黑（已经有换路兜着），
  或者第五节的补测发现了按小时 / 按天的上限。
- **别因为宽松就把节奏放开。** 生产现在每个任务带 0~180 秒随机延迟（`index.ts` 的 `randomDelaySeconds`），
  这种"不像机器"的节奏比速度更值得保留。
