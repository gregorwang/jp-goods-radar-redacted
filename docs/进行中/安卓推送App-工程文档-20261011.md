## 0. 一句话

在 `apps/android-push/` 做一个**原生安卓 App**（你自己的小米 14，HyperOS / Android 16），**只有一个功能**：
常驻后台、通过长连接实时收到关键词档案每小时那一轮的新货推送，点开能看清单、点商品跳到煤炉。
推送服务端是一个新的 Cloudflare Worker（`apps/push-relay/`，用 Durable Object 托管长连接）。

## 1. 为什么做、为什么现在做

- 2026-10-11 实测：4 个关键词档案一周漏掉 134 件上架几小时内就被买走的相关货，31 件低于同款行情
  （`docs/研究/当天上架当天售出-漏看实测-20261011.md`）。同日已把这 4 个档案的二手站改成每小时巡回。
- 每小时一轮之后，邮件是瓶颈：邮件本身慢、每小时一封会烦，而且 Resend 每天 100 封上限。
- 推送通道和"每小时还是秒级"无关：先用每小时的日报接上，以后秒级扫描做出来，往同一个通道里推即可（见 §9）。

## 2. 范围

**做：**
- 推送服务端 `apps/push-relay`（Worker + Durable Object），收 collector 的消息、存最近 7 天、通过 WebSocket 推给手机、手机断线重连后补发。
- collector 侧：关键词日报生成后，按开关把这一封的摘要投给 push-relay（复用现有通知投递状态机，见 §5）。
- 安卓 App：常驻长连接、系统通知、推送列表、单次推送的商品清单、连接状态 / 后台保活设置页。

**不做（这一期）：**
- 不做账号体系、不做多用户。只有你一台手机，用一个设备口令鉴权。
- 不上应用商店，不接 FCM / 小米推送（理由见 §3），不做 iOS。
- 不改日报判定逻辑。（10-12 起每小时那几轮已停邮件，见 §13。）
- App 里不放主站后台链接。（10-12 起 App 能做列表标注和「等降价」，走主站的窄接口，见 §13。）

## 3. 关键决定和理由

### 3.1 推送走自建长连接，不走 FCM / 小米推送

| 方案 | 结论 | 理由 |
|---|---|---|
| **自建 WebSocket 长连接（选）** | ✅ | 通道完全自己的，不依赖第三方账号和审核；延迟秒级；服务端用 Durable Object，闲置连接几乎不花钱 |
| FCM（谷歌推送） | 以后作为兜底再考虑 | 要建 Firebase 项目；用户手机的系统版本是否带完整谷歌服务没确认；被系统冻结时最可靠，但多一个外部依赖 |
| 小米推送 | ❌ | 要在小米开放平台注册应用、审核，偏国内版；为一台手机不值得 |
| 借用 ntfy / Bark | ❌（用户选了原生） | 用户要原生 App、UI 对齐本项目 |

**代价要说清楚**：自建长连接在小米上能不能"一直在"，取决于手机设置。HyperOS 杀后台很凶，App 必须：
前台服务 + 电池优化白名单 + 自启动 + 最近任务里锁定。设置页要把这几项做成"一键跳转 + 当前状态"，见 §6.3。
深度休眠时如果没进白名单，消息可能延迟到下一次维护窗口（几分钟到十几分钟）。验收里专门测（§8）。

### 3.2 服务端用 Cloudflare Durable Object，不放 VPS

- 和 collector 同账号，collector 用**服务绑定**调它（同账号 Worker 用网址互调会被拦成 `404 error code: 1042`，
  见 `apps/collector/src/listing-enrich.ts` 顶部注释）。
- 用 **WebSocket Hibernation API**（`state.acceptWebSocket` + `setWebSocketAutoResponse`）：连接闲着时 DO 休眠不计时长费，
  心跳 `ping`→`pong` 由运行时自动应答、不唤醒 DO。
- 用 SQLite 存储的 DO（`new_sqlite_classes`）存最近 7 天消息，供断线补发。
- 不放 VPS：VPS 已经扛着数据库和 source-runner，再加一个常驻连接服务等于多一个单点；VPS 上的东西还要手动发布（memory：source-runner 手动发布漏过两天）。

### 3.3 App 技术栈

- Kotlin + Jetpack Compose，minSdk 31，targetSdk 36（本机已装 platforms android-36 / build-tools 36）。
- 长连接：OkHttp WebSocket。本地存储：Room。图片：Coil。
- 构建环境：本机有 Android Studio（`C:\Program Files\Android\Android Studio`，自带 JBR 作为 JDK），SDK 在 `%LOCALAPPDATA%\Android\Sdk`。
  命令行里 `java` / `adb` 不在 PATH 上，用 Android Studio 的 JBR 和 `Sdk\platform-tools\adb.exe`，或在 Studio 里构建。
- 装机：USB 或无线调试 `adb install`。签名 keystore 放本机、**不进 git**，路径写进本文档 §10。

## 4. 整体链路

```
collector 每小时一轮 → finalizeKeywordDigest 生成 daily_digest 事件
   └→ deliverPendingNotifications
        ├→ 邮件（原有）
        └→ 推送投递（新，开关 owner_push_v1 控制，只投开关里列出的档案）
              └→ 服务绑定 PUSH_RELAY → POST /publish（内部口令）
                    └→ Durable Object：存消息（7 天）→ 推给所有在线连接
                          └→ 手机 App 前台服务里的 WebSocket 收到 → 系统通知
手机断线重连：GET /messages?after=<最后收到的 id> 补发
```

## 5. 服务端与 collector 改动

### 5.1 `apps/push-relay`（新 Worker）

- 路由：
  - `GET /connect`（WebSocket 升级）：请求头 `Authorization: Bearer <PUSH_DEVICE_TOKEN>`，转给唯一的 DO 实例（`idFromName("owner")`）。
  - `GET /messages?after=<id>&limit=50`：同样鉴权，返回 `after` 之后的消息，供重连补发和 App 首次打开拉历史。
  - `POST /publish`：只给 collector 用。服务绑定调用 + 请求头 `X-Internal-Token: <PUSH_PUBLISH_TOKEN>`。按 `eventKey` 幂等（同一封日报重投不产生两条）。
- 心跳：DO 构造时 `setWebSocketAutoResponse(new WebSocketRequestResponsePair("ping", "pong"))`。
- 推给手机的帧：完整消息 JSON（§5.3），App 收到后回 `{"ack": id}`（可选，用于服务端统计"最后送达"）。
- secrets：`PUSH_DEVICE_TOKEN`（手机用，≥32 字节随机）、`PUSH_PUBLISH_TOKEN`（collector 用）。
- 部署：参照其他 Worker 的 wrangler 配置；**不要**挂到 Workers Builds 之前先确认 build 机能构建它（AGENTS.md §1：push 会触发自动部署）。

### 5.2 collector：推送投递

- **复用 `apps/collector/src/hermes-delivery.ts` 的取件 / 认领 / 重试状态机**。那个文件头部注释写明了就是为"换一个通道"预留的，
  并列出了重新启用前必须保留的两条边界（通道启用时间之前的事件不投、失败退避有上限），照抄。
- 新开关：`radar_core.runtime_feature_flags` 加一行 `owner_push_v1`，默认 `enabled=0`，`config_json` = `{"profileIds": [...]}`。
  开关关着或档案不在列表里 → 不投。这符合 AGENTS.md §5「试验靠开关，默认关」。
- 投递记录表：新建（例如 `radar_core.push_deliveries`，结构参照 hermes 用的那张）。迁移按 memory「jpgr 生产库迁移怎么跑」手工执行，
  **改了 SQL 必须跑 `pnpm verify:sql`**（AGENTS.md §1）。
- 只投 `daily_digest` 且 `kind` 为 `keyword_scan_summary` / `keyword_new_listing` 的事件，并且本轮有新货（`items` 非空）。建档回执不推。
- 注意 AGENTS.md §3 的超时成对表：推送投递是一次服务绑定调用，**不能放在数据库事务里等**；超时设短（例如 8 秒，参照 hermes 的 `DEFAULT_TIMEOUT_MS`）。

### 5.3 消息格式

```json
{
  "id": 123,                       // DO 内自增
  "eventKey": "keyword_digest:<profileId>:<scanStartedAt>",
  "kind": "hourly_digest",         // 以后秒级用 "instant"
  "profileId": "...", "profileName": "赛车初音上新",
  "createdAt": "2026-10-11T12:20:00Z",
  "total": 3,
  "items": [
    {
      "sourceId": "mercari_jp", "title": "...", "price": 2900, "auction": false,
      "imageUrl": "https://...", "url": "https://jp.mercari.com/item/m...",
      "listedAt": "...",
      "sales": { "p50": 3400, "n": 116 }   // 有同款成交参考才带；没有就省略，配不准就不显示
    }
  ]
}
```

- 字段从 `events.payload_json` 里取（结构见 `packages/db/src/queries/digests.ts` 组装 payload 那段）。只带渲染需要的字段，单条 ≤ 64KB，items 多于 30 件时只带前 30 件并写 `total`。
- 同名合并、单品在前打包在后：规则在 `packages/email/src/listing-groups.ts`，App 端照同样规则排（可以在服务端先排好再发，App 只管显示——推荐这样，规则只有一份）。

## 6. App 设计

### 6.1 结构（只有三屏）

1. **收件**（首页）：按时间倒序列出每一次推送。每行：档案名（衬线字）、几件新货、时间（天蓝小字）、首件缩略图。
2. **一次推送的清单**：卡片布局**和日报邮件完全一致**——左栏 来源 / 上架时间，中间商品图，右栏价格；标题在下面占满一行；
   同款成交参考作为小标签（低于行情用柠檬荧光底色"便宜"，拍卖 / 贵了用赭红）。点卡片 → `Intent.ACTION_VIEW` 打开商品链接（装了煤炉 App 会直接跳进去）。
3. **连接**（设置）：连接状态（在线 / 重连中 / 最后心跳时间 / 最后收到消息时间）、设备口令输入、后台保活四项检查（§6.3）、"发一条测试推送"按钮（调 relay 的测试接口或让 relay 回显）。

### 6.2 UI 风格：对齐本项目，不要 Material 默认样子

设计语言来源（先读）：`packages/email/src/design.ts`（颜色、字体常量）。

- 白底，1px 发丝线分隔（`#e6e6e6` / `#efefef`）；**不用阴影卡片、不用大圆角、不用 FAB、不用 Material 紫色**。
- 颜色：墨 `#111111`、次文字 `#4a4a4a`、弱文字 `#6b6b6b`、天蓝 `#45bfe8`（文字用 `#1a7ca3`）、荧光笔 `#f1ea8c`、柠檬 `#e8e15d`、赭红 `#c24e1c`（文字 `#a8431a`）、雾灰底 `#f4f6f7`。
- 字体：标题衬线（Noto Serif SC），正文无衬线（Noto Sans SC / 系统），价格数字 Cormorant Garamond。字体文件打包进 `res/font`（都是 OFL 授权）。
- 按钮：主按钮墨色胶囊，次按钮下划线文字。分段选择用下划线标签，不用原生下拉 / Switch 默认样式。
- 系统通知：小图标单色剪影；标题"赛车初音 · 3 件新货"；正文前 2–3 件"标题 ¥价格"；有图时用 BigPicture 展示首件图。点通知进第 2 屏。
- 通知渠道（NotificationChannel）：「新货推送」高重要性（响铃 + 横幅）、「连接状态」低重要性（前台服务常驻通知，静音、不弹）。

### 6.3 后台常驻（小米 / HyperOS 重点）

- **前台服务**，`foregroundServiceType="specialUse"`（加 `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` 说明"实时商品推送长连接"）。
  **不要用 `dataSync`**：Android 15 起它有每天 6 小时上限，到点会被系统停掉。侧载 App 不受商店对 specialUse 的审核约束。
- 常驻通知内容写"保持连接中 · 最后心跳 HH:MM"，低重要性渠道。
- 心跳：每 4 分钟发一次文本 `ping`，10 秒内没收到 `pong` 视为断线，立刻重连。重连指数退避 1s→2s→…→60s 封顶，网络恢复（`ConnectivityManager.NetworkCallback`）时立刻重连。
- 重连成功后先 `GET /messages?after=<本地最大 id>` 补发，再恢复实时。补发的消息照常弹通知（同一 id 不重复弹）。
- 开机自启：`RECEIVE_BOOT_COMPLETED` 拉起前台服务。
- 看门狗：WorkManager 每 15 分钟检查一次服务是否活着，不在就拉起。
- 设置页四项检查，每项显示当前状态 + 一键跳转：
  1. 通知权限（Android 13+ `POST_NOTIFICATIONS`）
  2. 电池优化白名单（`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`；不在白名单，深度休眠时没有网络）
  3. 自启动（小米的自启动管理页，跳 `com.miui.securitycenter` 对应 Activity，跳不过去就提示手动路径）
  4. 省电策略设为"无限制"（应用详情页），并提示在最近任务里下拉锁定
- 不申请任何和功能无关的权限。

## 7. 安全

- 设备口令只存在 App 的 EncryptedSharedPreferences 里；relay 端常量时间比较。
- `/publish` 只接受服务绑定 + 内部口令，公网直接打进来一律 401。
- 消息里只有商品公开信息（标题、价格、图、链接），不含任何账号、邮箱。
- 不在 App 和 relay 里记录手机 IP 以外的信息；relay 日志不打印口令。

## 9. 以后接秒级推送

- 推送通道不关心消息是怎么产生的。以后做秒级扫描，只要往 `/publish` 发 `kind: "instant"` 的单件消息。
- 用户已定的约束：秒级那条路**不调 AI 复核**（成本），要求**一秒内**。判定只用代码能确定的部分（关键词、排除词、型号冲突、最低价），这和 AGENTS.md §4「代码有把握的做厚」一致。
- App 端给 `instant` 单独一个通知渠道，以后可以设成更响 / 振动不同。

## 10. 成本

- Durable Object：休眠中的 WebSocket 不计时长；每小时 4 个档案各推 1 条，一天约 80 条消息，加心跳自动应答不计费 → **≈ $0**，在 Workers 付费计划已有额度内。
- App：无费用（侧载，不上架）。
- 动手前在 `docs/成本/成本账本.md` 加一行。
- 签名 keystore 路径：`C:\Users\me\.jpgr\android-push-release.jks`（别名 `jpgr-push`，密码在 `apps/android-push/local.properties`，都不进 git）。**升级 App 必须用同一个 keystore**，丢了只能卸载重装。
- 设备口令 / 投递口令：Cloudflare secret（push-relay 的 `PUSH_DEVICE_TOKEN`、`PUSH_PUBLISH_TOKEN`，collector 的 `PUSH_PUBLISH_TOKEN`）；设备口令另存一份在 `apps/android-push/local.properties`，打进安装包。

## 13. 2026-10-12：停每小时邮件、App 0.2.0

用户比对过推送和邮件（推送上线后 27 封日报两边一一对上，件数一致；只有两封超过 30 张卡被截断，已把上限提到 120 张 / 480 KiB）后拍板：

**邮件分工（用户定，不要擅自改回）**

| 内容 | 走哪 |
|---|---|
| 4 个关键词档案**每小时巡回（二手站）**的日报 | 只推 App，不发邮件 |
| 同一批档案**一手店每天一轮**的日报 | 邮件照发，也照推 App |
| 精确同款雷达、降价通知 | 只走邮件（低频，用户说现在不做 App 推送、别加复杂度） |

- 开关：`runtime_feature_flags.owner_push_v1.config_json.emailOff=true`。去掉就恢复全部发邮件，不用发版。
- 实现：`packages/db/src/queries/push.ts` 的 `handOverDigestEmailsToPush`——发邮件前把"这一轮里所有来源都是每小时绑定"的日报打上 `email_suppressed_at`（不改 status，推送照投）；推送成功后 `markPushOnlyDigestDelivered` 记成 `status='sent'`，日报标注才能继续按 `status='sent'` 列出来。
- 不做"推送没送到再补发邮件"的兜底（用户选了不加复杂度）。

**每轮心跳**：collector 每跑完一轮关键词巡回（没新货也算）就 POST push-relay `/round`（`publishKeywordRound`），relay 按档案只留最新一条，`GET /rounds` 和 `{"type":"round"}` 帧给 App。
App 首页顶上据此显示「上一轮几点跑完 · 几件新货 · 下一轮几点开跑」，过了下一轮开跑时间 45 分钟还没新的一轮就提示"巡回可能卡住了"。
这一步是为了解决"不知道该不该打开 App"：用一天的数据预测"几点有好货"做不准（上架时间由卖家决定），能确定的只有巡回时间；
系统活着、推送通着，就不需要主动去刷。

**App 0.2.0**
- 已读 / 未读：没看过的推送带天蓝圆点，「全部标为已读」；打开清单就算看过，通知栏那条一起收掉。点进来源看过的卡片标「点开看过」。都只存在手机本地（Room v2）。
- 列表标注：首页右上「标注」。最近 3 天推过的商品一行一件，按天分段，每行「不想看 / 还想看」，再点一次撤销；标完的行变淡留在原位。
  走主站 `GET/POST /api/device/labels`，和主站标注页共用 `apps/web/src/lib/digest-labels.ts`，结论还是写 `digest_item_labels`。
- 等降价：清单每张卡（拍卖除外）有「等降价 / 不等了」。走主站 `/api/device/watches`，和主站商品页共用 `apps/web/src/lib/listing-watch.ts` 建单品档案（默认 3 小时复查、降 100 円以上通知），**降价发邮件**。同时在盯上限 30 件（单品复查和关键词巡回共用 VPS 抓取额度）。
- 主站 `/api/device/*` 用 `Authorization: Bearer <OWNER_DEVICE_TOKEN>`，web 的 secret，和 push-relay 的 `PUSH_DEVICE_TOKEN` 同值。只开了这两件事，不给手机开主站其他接口。
