## 1. 已核实的事实（带出处）

### 1.1 煤炉的调用链（只有一条路）

| 环节 | 位置 | 说明 |
|---|---|---|
| 路由判定 | `apps/collector/src/source-execution.ts:253` `sourceRequestRoute` | 煤炉不在 Cloudflare 直连名单，返回 `mercari_service` |
| 搜索入口 | `source-execution.ts:889` `searchWithConfiguredRoute` | 煤炉先进 `searchMercariDuringMigration`（`:640`），mode=off 时返回 undefined 往下落；最后在函数末尾 `serviceSearch` 走 Vercel。**没有任何 catch / 换路** |
| 详情入口 | `source-execution.ts:1053` `itemWithConfiguredRoute` | 同上，末尾 `callService` 走 Vercel |
| 调 Vercel | `source-execution.ts:389` `callServiceOnce`；`:574` `callService` | `callService` 只对"可重试且 ≥500"的失败**原地**重试一次（1~2 秒后），不换路 |
| 开关 | `apps/collector/wrangler.jsonc:134` `MERCARI_SOURCE_RUNNER_MODE: "off"` | `off / shadow / primary`。shadow 于 2026-09-09（`272cfdc`）关闭，原因：双发让上游请求量翻倍、拖慢队列 |
| Vercel 服务 | `apps/mercari-service`，`vercel.json` 固定 `hnd1` 东京 | 业务错误以 HTTP 200 + `error.upstreamStatus` 回传 |
| VPS 备路 | `apps/source-runner`，煤炉白名单 `apps/source-runner/src/source-policy.ts:47`（只放行 `/v2/entities:search` 与 `/items/get`） | 生产部署在 `/opt/jpgr-source-runner/current/apps/source-runner`，systemd 单元 `jpgr-source-runner.service`，描述写的是 "Singapore Source Runner" |
| Collector 调 VPS | `apps/collector/src/source-runner-client.ts` `searchWithSourceRunner` / `itemWithSourceRunner` | 已支持 `mercari_jp`；任务提交后轮询，总超时 95 秒（`RUNNER_JOB_TIMEOUT_MS`） |
| DPoP | `packages/adapters/src/mercari/dpop.ts` | **每次请求现场生成新密钥对和 deviceUuid**，所以煤炉能稳定识别的只有出口 IP 和请求特征 |

### 1.2 403 是怎么被处理的

| 环节 | 位置 | 行为 |
|---|---|---|
| 适配器把 403 归类 | `packages/adapters/src/mercari/request.ts:50` | 先排除"商品不可见"（`InvisibleItemException` / sub_code 404/410 → `MercariItemGoneError`），剩下的 403 一律 `MercariBlockedError`（`errors.ts:17`，自带 `retryAfterSeconds = 12h`） |
| Vercel 平台自己回 403 | `source-execution.ts:279` `readLimitedJson` 解析失败分支 | 抛 `mercari_service_invalid_response`，**status=403**。下游只看 status，**会被当成煤炉 403，冷却 12h**。这是"中转站自己拦自己"被误判的位置 |
| 定时任务失败落库 | `packages/db/src/queries/bindings.ts:342` `failBinding` | `:351` 起：403 → 档案冷却 12h；`:368` 同时把 `source_registry` 写成 `health_status='blocked'`、`cooldown_until=+12h`，**但不写 `cooldown_route`** |
| 别的档案会不会被拦 | `apps/collector/src/index.ts:638` `runBinding` 只看 `binding.cooldown_until`（档案自己的）；`:2636` `skippedPrimaryFailureForSource` 只在 route==='direct' 时读来源冷却 | **煤炉其他档案不受来源级冷却影响**。来源级 `blocked` 对煤炉定时采集是摆设，只影响后台显示和 `p0-qualification.ts:299` |
| 调度过滤 | `packages/db/src/queries/bindings.ts:100` `dueBindings` | 只按档案自己的 `cooldown_until` 过滤 |
| 手动搜索 | `index.ts` 预览路径（约 `:3381`） | 读来源冷却，但煤炉 `sourceServiceFallbackConfigured` 为真（VPS 已配置），所以冷却期间仍会去请求 Vercel |
| 告警 | `bindings.ts:379` | 同一档案**连续失败 ≥3 次**才插 `source_error` 事件；每段连续失败最多提醒 3 次（`SOURCE_ERROR_REMINDERS_PER_STREAK`） |
| 日报里的失败提示 | `index.ts` 约 `:1653-1686` | 关键词日报的 `sourceIssues/failedSources` 会列出本轮失败的来源（当天可见，但不显眼） |

### 1.3 骏河屋兜底链（可照抄的模板）

- `source-execution.ts:800` `shouldTrySurugayaFallback`：`source_cooldown`、可重试、403、429 都进兜底。
- `source-execution.ts:807` `surugayaFallbackAfterDirectFailure`：直连 → Firecrawl → Browser Run → Vercel，
  每一级失败都 push 进 `failures`，全失败抛 `SourceRouteChainError`（带每条路的证据）。
- 成功时返回 `routeOutcome.kind = "fallback_success"`，带 `primaryFailure` 和 `routeFailures`；
  `requestRoute` 写实际成功的那条路。`SourceRouteSession.directFailure` 用来在同一次运行里记住
  "主路已失败"，后续请求直接跳过主路。
- 来源级冷却按路记：`source_registry.cooldown_route`，`recordPreviewFailure`（`index.ts` 约 `:3066`）
  会写 `cooldown_route=route`。

## 4. 实现步骤（按层，用户拍板后执行）

> 每层独立提交、独立可回退。层与层之间的依赖已标出。

### 第一层：失败换路（依赖第 3 节实测通过）

**目标：** 煤炉 Vercel 失败时自动走 VPS 试一次。搜索和详情都要。

**改哪里：** `source-execution.ts` 的 `searchWithConfiguredRoute` 和 `itemWithConfiguredRoute`
里煤炉那一段。仿照骏河屋写一个 `mercariFallbackAfterPrimaryFailure`：

1. 主路 = Vercel（`serviceSearch` / `callService(..."item"...)`）。
2. 抓到失败后先分类，**以下情况不换路，原样抛出**：
   - `mercari_item_gone`（410）、`mercari_invalid_request`、`mercari_dpop_error`、`mercari_schema_changed`
     ——商品没了 / 我们自己的错，换路没用。
   - 429（`mercari_rate_limited`）——按 `retryAfterSeconds` 等，不换 IP 硬闯
     （`docs/进行中/服务能力扩张-后续任务-20260909.md` 第 7 项的规矩）。**这一条若用户另有意见以用户为准。**
3. 以下情况换路：403（`mercari_blocked` 或 Vercel 平台 403）、`retryable` 的 5xx、
   `mercari_service_timeout`、`mercari_service_network_error`、`mercari_service_platform_invalid_response`、
   `mercari_service_invalid_response`。
4. 备路 = `searchWithSourceRunner(env, "mercari_jp", ...)` / `itemWithSourceRunner(...)`。
5. 备路成功：返回 `routeOutcome.kind="fallback_success"`，`primaryRoute="mercari_service"`，
   `fallbackRoute` 用什么值要看 `@jpgr/core` 里 `SourceRequestRoute` 的枚举——**现在 VPS 和 Vercel
   共用 `mercari_service` 这个名字**（见 `sourceRequestRoute` 的注释），两条路在记录里分不开。
   需要给 VPS 一个独立的路由值，并检查所有 `switch(route)` / 前端 `routeLabel` 是否要跟着加。
   已核实的现状：
   - TS 类型 `packages/core/src/types.ts:22`：`"direct" | "mercari_service" | "vercel_service" | "managed_api" | "browser_run"`。
     `vercel_service` 已在类型里但代码中**没有任何地方使用**，可以考虑启用它（但要想清楚和 `mercari_service`
     的历史含义怎么划分，别让旧数据语义错乱）；或者新增 `source_runner`。
   - **数据库有 CHECK 约束，新值写不进去**：`postgres/schema.sql` 里
     `ck_source_registry_05`（`request_route`）、`ck_source_registry_06`（`cooldown_route`）
     只允许 `direct / mercari_service / managed_api`；`ck_source_probe_windows_02`、
     `ck_source_probe_window_history_02/04` 只允许 `direct / mercari_service`。
     （顺带：骏河屋的 `browser_run` 也不在约束里——写 `source_registry` 前要看现有代码是怎么绕开的，别踩同一个坑。）
   - 要写迁移放宽约束。迁移流程见用户记忆 `jpgr-postgres-migration-procedure`
     （没有自动执行器：手工 psql + 手写 `schema_migrations`）；改完跑 `pnpm verify:sql`。
     **生产库没有定期备份**（用户记忆），跑迁移前先手动备份 `source_registry` 这几张表。
6. 备路失败：抛 `SourceRouteChainError("mercari_jp", failures)`——构造函数的 `sourceId` 类型目前只收
   `CloudflareDirectSourceId | "rakuten_ichiba"`，要放宽。
7. 用 `SourceRouteSession` 记住"本次运行主路已失败"，同一次运行里的后续请求（翻页、详情补抓）直接走备路。

**坑：**
- VPS runner 对**非 403/429 的失败**可能进入"自动修复"流程（`apps/source-runner/src/business-repair.ts:115-123`），
  返回 `source_runner_repair_pending`。作为兜底时，这个状态在 `runBinding` 里会走
  `markRunAwaitingBusinessRepair`（`index.ts` 约 `:1370`），不是普通失败——要想清楚兜底场景下要不要沿用。
- VPS runner 是**排队执行**的，`queue_full / queue_stopping` 是我们自己的背压（`failBinding` 里有专门的分钟级退避），
  不能当成煤炉失败。
- 煤炉翻页的 `pageToken` 在两条路之间**不保证通用**。同一次运行中途换路时，从第一页重新开始最安全。
- shadow 模式那套 `searchMercariDuringMigration` 不要删，保留用于对账；但 mode=`primary` 时，主备关系要反过来
  （VPS 主、Vercel 备），或者明确 primary 模式下不做兜底——二选一，写进注释。

### 第二层：按路冷却（依赖第一层）

**目标：** Vercel 被 403 只冷却 Vercel 这条路；冷却期间煤炉任务直接走 VPS；两条都 403 才整源暂停。

**改哪里：**
- `failBinding`（`bindings.ts:342`）：煤炉 403 时，按"实际失败的是哪条路"写 `source_registry.cooldown_route`。
  现在它不写这个字段。注意 `failBinding` 是所有来源共用的，改动要只影响煤炉，或确认其他来源不受影响。
- `skippedPrimaryFailureForSource`（`index.ts:2636`）：目前只在 `route==='direct'` 时生效，要让煤炉
  （主路 `mercari_service`）也能读到"主路冷却中"，从而把 `skippedPrimaryFailure` 传进
  `searchWithConfiguredRoute`，直接跳到备路。
- **档案级冷却**：主路被 403 但备路救回来时，这次运行算成功，**不要**给档案上 12h 冷却。
  只有两条路都失败时才走 `failBinding`。
- 冷却到期：第一个任务照常先试主路，成功即清除冷却。注意 `completeBinding`（`bindings.ts:214`）
  成功时会把 `source_registry.cooldown_until` 清成 NULL，**但不清 `cooldown_route`**，要补上。
  另外它在**任何**一次成功时都会清来源冷却——备路成功（`fallback_success`）时**不能**清主路的冷却，
  否则下一个任务又会先去撞主路。

### 第三层：每日档案当天补跑一次（独立，可先做）

**目标：** 一天一跑的煤炉档案，两条路都失败时（排除商品没了 / 我们自己的错），2~3 小时后补跑一次，只补一次。

**思路：** 在 `failBinding` 里，对 `schedule_interval_minutes >= 720` 的煤炉档案、且 `consecutive_failures`
从 0 变 1 的那一次，把 `next_run_at` 拉回到 `now + 2~3h`、`cooldown_until` 同步设成这个时间。
第二次失败恢复原有逻辑。
**注意关键词日报**：补跑那一轮不是 cron 派发的那一批，`finalize_keyword_digest` 不会再等它。
补跑的结果怎么进日报（第二天的日报带上？还是补发？）要先问用户，**不要自作主张多发邮件**
（用户记忆：测试邮件只发一封、邮件按给大众看的标准做）。

### 第四层：告警分级（独立）

- **两条路都失败**：当场插一条事件（建议新事件类型或复用 `source_error` 加标记），同一来源同一东京日最多一封。
  标题写"煤炉全线不通"，正文写两条路各自的失败原因（`SourceRouteChainError.routeFailures` 里都有）。
- **主路失败、备路救回**：不发邮件。在每日体检（`packages/db/src/queries/health.ts`）加一项：
  过去 7 天煤炉 `fallback_success` 次数及主路失败原因分布，周一周报里显示。
- 改告警逻辑前先读 AGENTS.md 第 4 节（注意力是最稀缺的资源）。

### 第五层：区分"Vercel 平台 403"（独立，改动最小，可最先做）

**改哪里：** `source-execution.ts:279` `readLimitedJson`。当 Vercel 回的是**非 JSON** 且 status 为 401/403 时，
用独立错误码（例如 `mercari_service_platform_forbidden`），并且**不要**让它触发 12h 的"煤炉被封"冷却；
告警文案指向"去 Vercel 后台检查防火墙 / 部署保护"。
注意 `failBinding` 只看 `httpStatus`，所以要么改传入的 status，要么在 `failBinding` 里按 code 排除。

## 5. 验收标准

每一层上线后，**在生产上**确认：

| 层 | 怎么验 |
|---|---|
| 第一层 | 无法真让煤炉 403。可行办法：临时把 `MERCARI_ADAPTER_URL` 指向一个必然失败的地址（只在一次手动搜索期间，测完立刻改回），在管理后台对煤炉跑一次"真实连接测试"或手动搜索，看结果是 `fallback_success` 且 `requestRoute` 为新路由值。**这一步会动生产配置，先征得用户同意。** |
| 第二层 | 同上手段制造主路失败后，查 `source_registry` 的 `cooldown_route` 是否只记了主路；下一次煤炉定时任务是否直接走了备路（`watch_runs` + Worker 日志）。 |
| 第三层 | 查 `watch_bindings.next_run_at` 在首次失败后是否被拉回到 2~3 小时内。 |
| 第四层 | 看事件表里是否只插了一条、邮件是否只到一封。 |
| 第五层 | 代码层面确认分支即可（难以在生产触发）。 |

**和第 10 节计划不同的地方：**

- **第 2 步没改数据库。** 核实后发现带 CHECK 约束的那几列（`source_registry.request_route/cooldown_route`、探测窗口）
  只会写入**主路**的名字；VPS 当备路时的名字 `source_runner` 只出现在运行结果和分析表（无约束）。
  所以只在 TS 类型里加了 `source_runner`，没跑迁移。
- **冷却时长：** 煤炉 403 → 主路冷却 12h；其余（超时、5xx、平台拒绝）→ 30 分钟。冷却到期后第一个请求先试主路，
  成功即发"主路恢复"。所以一次短暂的 Vercel 故障会收到两封（断了 / 恢复了），这是用户要求的。
- **煤炉来源级冷却只由 `mercari-route.ts` 写。** `completeBinding` / `failBinding` 对 `mercari_jp` 不再清除或覆盖
  `source_registry.cooldown_until`；`recordPreviewSuccess` 的兜底分支对煤炉只更新 `last_success_at`。
  骏河屋 / 雅虎仍是旧行为（第二批再统一）——注意：骏河屋的定时任务在兜底成功后同样会被 `completeBinding`
  清掉冷却，改它之前要先想清楚 Firecrawl 每天 30 次的额度（冷却真生效后，12 小时内的骏河屋任务会先走 Firecrawl）。
- **补跑不改 `next_run_at`。** 改它会让以后每天的运行时间往后漂 2 小时（`reserveBinding` 以它为基准）。
  改成队列里排一条 2h 延迟的 `run_binding`（trigger=`retry`），并同时排一条该档案的 `finalize_keyword_digest`。
  开了自适应节奏的单品档案不排（`failBinding` 已把 `next_run_at` 拉到冷却到期，调度器会自己补跑）。
- **提醒立即投递：** `index.ts` 在模块加载时 `registerRouteAlertDelivery(deliverPendingNotifications)`，
  提醒写入事件表后立刻投递一次，任何入口触发都一样。提醒走 `source_error` 事件类型（payload 带 `routeAlert`），
  模板在 `packages/email/src/templates.ts` 的 `routeAlertEmail`，只发 `ALERT_EMAIL_TO`。
- **翻页换路：** 同一次运行里 Vercel 取到第 1 页、第 2 页失败时，VPS 会接着用 Vercel 给的 `pageToken`。
  两边跑的是同一份适配器、token 是煤炉自己的，预计通用；如果线上出现"VPS 拒绝 pageToken"，改成换路后从第 1 页重来。
