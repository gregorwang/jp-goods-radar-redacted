# 日淘商品雷达 UI 语义与信息架构多轮错误复盘

> 项目：日淘商品雷达
>
> 复盘范围：A1–A7、PR #45–#47，以及后续 Search、Listings、Events 页面反馈与发布工作区问题
>
> 日期：2026-07-14
>
> 主题：为什么界面越来越精致，页面职责却一度越来越混乱
>
> 结论类型：产品语义复盘、信息架构纠偏、后续 UI 审查基线

## 0. 一句话结论

这几轮修改确实都围绕 UI 设计语义展开，但反复返工的根因不是颜色、字号或卡片不够精致，而是最初没有先定义“商品记录、关注档案、变化事件、数据分析”四种产品实体的职责与操作所有权。

当数据库表、API 返回值和组件能力被直接投射到页面时，一个页面会因为“技术上拿得到这些数据”而同时展示事实、运行、提醒、历史、删除和扩展来源。页面看起来功能丰富，用户却无法回答三个最基本的问题：我现在在哪、我是在看什么、这个操作会改变什么。

正确方向不是继续给重复区域换样式，而是先建立产品语义模型，再让路由、页面、组件、按钮和文案服从这个模型。

## 2. 三轮修改实际在解决什么

### 2.1 第一轮：先区分“监控目的”

第一轮修复了底层业务语义：

- 单品价格与库存监控；
- 关键词上新监控；
- 关键词市场行情采样；
- 商品价格快照；
- 市场分析样本。

这一步是必要的，但它主要解决“数据为什么被采集”，还没有完整解决“这些数据应该在哪个页面被看见和管理”。

结果是领域模型已经开始分化，页面模型仍延续旧的混合结构。

### 2.2 第二轮：A4/A5 拆分“单品档案”和“关键词雷达”

A4/A5 暴露的问题包括：

- 一个“建立关注档案”表单同时承载单品和关键词；
- 用户无法直观看出正在建立哪种档案；
- 单品档案详情仍允许添加关键词绑定；
- 关键词来源只能单选，与跨站扫描语义冲突；
- 暂停和删除同时出现在列表页与详情页；
- 删除缺少明确二次确认；
- 轮询历史没有稳定的长度边界与滚动语义；
- “立即运行”是否影响下次调度没有解释。

PR #46 的正确修复是：

- 用两个重叠、可切换的建立卡片表达两种档案；
- 单品档案只绑定具体来源商品；
- 关键词雷达允许多来源选择；
- 暂停、删除、立即巡回收敛到详情页；
- 删除增加影响范围说明和确认弹窗；
- 轮询历史变成有界滚动区；
- 明确手动巡回不会顺延下一次定时巡回。

### 2.3 第三轮：A6/A7 拆分“商品记录”和“关注档案”

A6/A7 暴露的问题包括：

- 商品库卡片出现“查看历史、正在监控、查看关注”三种互相重叠的动作；
- “查看历史”实际进入的是一个完整商品详情，而不是单纯历史页；
- 商品详情再次显示监控状态和关注入口，和关注档案详情重复；
- 一个价格快照也绘制大面积“价格曲线”，视觉上暗示了不存在的趋势；
- 商品事件与全局事件页的关系没有说明；
- 页面之间缺少清楚的正向与反向链接；
- 路由存在，但用户不知道各页分别负责证据还是运行。

PR #47 的正确修复是：

- `/listings` 定义为已存商品记录索引；
- `/listings/[id]` 定义为单件商品的事实与变化证据；
- `/watches/[id]` 定义为监控计划与运行记录；
- `/events` 定义为跨商品的全局变化收件箱；
- 商品记录与关注档案只通过链接关联，不复制操作面板；
- 单快照展示为基线证据，至少两个有效价格点才绘图；
- 快照和事件均设置有界读取与滚动区域；
- Dashboard 增加明确的全局变化入口。

PR #47 解决了 A6/A7 截图中最明显的职责重复，但独立前向审查又发现两个仍待处理的边界：

- `/listings` 仍内嵌一套可配置的“建立监控”表单，而 `/listings/[id]` 又提供固定 180 分钟和固定降价阈值的一键建档；同一创建动作存在两个入口和两套默认副作用；
- `/listings` 首次读取失败会被吞掉，随后复用“尚无商品记录”的空状态，无法区分加载失败与真实空库。

因此，本轮上线可以表述为“A6/A7 的记录/档案/事件主边界已经建立”，不能表述为“整个商品记录链已经不存在任何语义问题”。

## 3. 最根本的错误：把数据结构当成页面结构

技术实现天然会看到这些对象：

- `listings`；
- `listing_snapshots`；
- `watch_profiles`；
- `watch_bindings`；
- `watch_runs`；
- `events`；
- `market_observations`。

错误做法是按“某条 API 返回了什么”来决定页面展示什么。

例如，商品详情 API 能查到关联 Watch，不代表商品详情应该复制暂停、恢复、立即运行和删除操作。它只需要表达“存在关联关注档案”，然后给出清晰链接。

同理，关注档案能通过绑定找到商品，不代表关注档案应该重新展示完整价格历史。它只需要表达“这个监控计划对应哪一条商品记录”。

数据关系是多对多或可联查的，不代表 UI 职责也应该混合。

## 4. 四张截图中的关键语义错误

### 4.1 A4：列表页承担了详情页的操作责任

A4 的列表卡同时出现：

- 查看档案；
- 暂停；
- 删除。

这会产生两个问题。

第一，列表页和详情页拥有同一组高风险操作，用户无法形成稳定预期。

第二，删除离上下文太远。用户还没有看到档案包含的来源、历史、提醒和资产范围，就可以直接删除整份档案。

正确规则是：列表页负责识别、状态摘要和进入详情；运行及破坏性操作只属于详情页。

### 4.2 A5：单品档案允许扩展关键词来源

A5 下方的“添加关键词绑定”把两种完全不同的身份塞入同一档案：

- 单品档案的身份是“来源 + 商品 ID”；
- 关键词雷达的身份是“关键词条件 + 多来源集合 + 分析目的”。

它们可以在分析层相关联，但不应该在同一个运行档案里混合。

一旦混合，暂停、提醒、基线、运行历史和删除范围都变得难以解释。

### 4.3 A6：“查看历史”不是准确的目的地名称

A6 的“查看历史”进入 A7，但 A7 实际包含：

- 商品身份；
- 当前价格；
- 来源状态；
- 关联监控；
- 价格快照；
- 商品事件。

因此“查看历史”缩小了真实目的地的语义，也让用户误以为 A7 只是 A6 的展开层。

正确名称是“打开商品记录”。它描述的是一个稳定产品实体，而不是其中某一个区块。

### 4.4 A7：一个点被画成曲线

A7 只有一个真实价格快照，却绘制了大面积价格图表。

这不是单纯的空状态不好看，而是证据表达错误：

- 一个点只能证明基线；
- 两个点才能证明方向；
- 多个点才能讨论趋势；
- 无价格点时不能用状态快照冒充价格曲线。

视觉组件必须服从证据强度，不能为了填满版面制造趋势感。

## 5. 根因分析

### 5.1 缺少领域词典

“档案、商品档案、历史、记录、关注、绑定、事件、分析”被交替使用，但没有一对一含义。

当名词不稳定时，路由、按钮和页面职责必然漂移。

### 5.2 缺少页面职责矩阵

实现前没有写清每个页面：

- 代表哪个实体；
- 回答哪个用户问题；
- 拥有哪些操作；
- 明确禁止哪些操作；
- 和其他页面如何互链。

因此组件每获得一个能力，就倾向于把能力直接展示出来。

### 5.3 缺少操作所有权

暂停、恢复、立即巡回、删除、重试邮件等动作没有唯一归属页。

重复按钮表面上提升了“方便”，实际上增加了误操作风险，并让页面边界失效。

### 5.4 先做卡片，再做信息架构

重叠卡片、雾蓝纸张、明朝标题和细线都可以成立，但它们不能替代产品模型。

错误职责被做得越精致，后续越容易误以为问题只是局部文案或间距。

### 5.5 只检查单页，没有检查完整路由链

单看 A6，三个按钮似乎都说得通；把 A6、A7、关注档案和事件页连起来看，重复才显现。

UI 审查必须沿真实任务路径检查，而不是只看一个组件截图。

### 5.6 没有提前设计稀疏数据和长数据

只有默认数据量被设计，导致：

- 单快照被迫填成图表；
- 零事件只剩空白；
- 轮询历史增长后可能无限延伸；
- 长标题和移动端才暴露布局问题。

### 5.7 危险动作被当成普通按钮

删除不是红色按钮样式问题，而是资产边界问题。

必须说明：

- 删除什么；
- 保留什么；
- 是否可撤销；
- 影响哪些来源、运行记录和未来计划；
- 是否需要二次确认。

### 5.8 视觉参考与产品语义的优先级倒置

参考站适合提供：

- 构图；
- 字体角色；
- 留白；
- 材质；
- 动效节奏。

参考站不能替本项目决定：

- 路由层级；
- 监控实体；
- 操作所有权；
- 删除范围；
- 证据强度。

视觉语言可以借鉴，产品信息架构必须来自日淘商品雷达自己的领域模型。

### 5.9 混合工作树增加了语义污染风险

A6/A7 发布前的类型检查发现 `watch-detail.tsx` 混入未完成的日/周调度模型。

这说明 UI 文件也可能携带尚未发布的数据语义。发布隔离不仅是 Git 清洁问题，也是产品语义隔离问题。

### 5.10 状态沟通没有始终领先于执行

本地完成、CI 完成、部署完成和生产验收完成是四个状态。

如果没有先说明当前处于哪一层，用户会把安全发布时间理解为“又在生产重新改 UI”。

流程本身可以正确，沟通仍然可能失败。

## 6. 正确的领域语义模型

### 6.1 搜索请求

回答：“我现在想找什么？”

包含关键词、来源、价格、成色、可购状态和历史模式。

它可以产生商品记录，也可以被保存为关键词雷达，但本身不是长期监控档案。

### 6.2 商品记录

回答：“这件来源商品是什么，曾经观察到什么？”

稳定身份是：

`来源 + 来源商品 ID`

包含：

- 来源事实；
- 当前保存价格与状态；
- 价格/状态快照；
- 该商品自己的变化事件；
- 与关注档案的关系。

不包含：

- 暂停、恢复；
- 立即巡回；
- 删除整份关注档案；
- 邮件重试；
- 跨商品分析控制。

### 6.3 关注档案

回答：“系统以后如何继续等待和提醒？”

包含：

- 监控目的；
- 来源绑定；
- 巡回频率；
- 下一次计划；
- 目标价和提醒；
- 基线状态；
- 每次运行证据；
- 暂停、恢复、立即巡回和删除。

单品档案和关键词雷达必须保持不同身份。

### 6.4 变化事件

回答：“什么发生了变化，通知处理到哪一步？”

单件商品页展示该商品事件；`/events` 负责跨商品筛选、通知送达、失败重试和抑制。

### 6.5 数据分析

回答：“跨时间和商品，能得到什么趋势或判断？”

分析使用商品快照与市场样本，但不接管监控计划，也不把行情样本伪装成单品价格历史。

## 7. 页面职责矩阵

| 页面 | 核心实体 | 首要问题 | 允许的主要动作 | 明确禁止 |
| --- | --- | --- | --- | --- |
| `/search` | 搜索请求 | 现在能找到什么 | 搜索、筛选、保存条件、从结果建立单品关注 | 管理既有档案运行 |
| `/watches` | 关注档案索引 | 正在等待什么 | 新建单品档案或关键词雷达、进入档案 | 直接删除、直接暂停 |
| `/watches/[id]` | 关注档案 | 如何继续等待 | 改频率、提醒、来源；立即巡回、暂停、删除 | 复制完整商品证据页 |
| `/listings` | 商品记录索引 | 系统见过哪些商品 | 筛选、打开商品记录、跳转关联档案 | 暂停、删除档案 |
| `/listings/[id]` | 商品记录 | 这件商品有什么事实和变化 | 打开来源、查看快照和商品事件、跳转档案 | 运行、暂停、删除档案 |
| `/events` | 全局变化收件箱 | 全局发生了什么 | 筛选、重试通知、抑制、打开商品记录 | 修改巡回计划 |
| `/analytics` | 聚合分析 | 长期趋势是什么 | 查询与解释聚合结果 | 伪装成单品证据或档案控制台 |
| `/dashboard` | 摘要 | 今天值得看什么 | 跳转到责任页面 | 复制所有管理控件 |

## 8. 操作所有权矩阵

| 操作 | 唯一主页面 | 其他页面如何表达 |
| --- | --- | --- |
| 新建关键词雷达 | `/watches` | 搜索页可带入条件，但进入明确的新建流程 |
| 从商品建立监控 | 搜索结果或商品记录 | 创建后跳转/链接到关注档案 |
| 暂停/恢复巡回 | `/watches/[id]` | 列表与商品页只显示状态摘要 |
| 立即巡回 | `/watches/[id]` | 其他页面不复制按钮 |
| 修改频率/目标价/提醒 | `/watches/[id]` | 其他页面只显示摘要或链接 |
| 删除整份档案 | `/watches/[id]` | 其他页面不提供快捷删除 |
| 查看价格快照 | `/listings/[id]` | Watch 提供反向链接 |
| 查看运行历史 | `/watches/[id]` | 商品记录不复制每次运行 |
| 查看单件商品事件 | `/listings/[id]` | 全局页可链接回商品 |
| 重试/抑制通知 | `/events` | 单件商品页只读展示事件 |

## 9. 路由与文案规则

### 9.1 按实体命名，不按局部区块命名

- 使用“打开商品记录”，不用“查看历史”；
- 使用“打开关注档案”，不用含糊的“查看档案”；
- 使用“全局变化记录/收件箱”，不用不说明范围的“事件流”；
- 使用“监控计划与运行记录”，不用把所有证据统称为“历史”。

### 9.2 页面标题必须能独立回答当前位置

页面 Hero 不是装饰文案。它必须明确：

- 当前实体；
- 当前页负责什么；
- 哪些相关能力属于其他页面。

### 9.3 跨页关系用链接，不复制控制面板

关联实体应该双向可达：

- 商品记录 → 关注档案；
- 关注档案 → 商品记录；
- 商品记录 → 全局变化；
- 全局变化 → 商品记录。

双向可达不等于双向复制操作。

## 10. 证据展示规则

### 10.1 价格快照

| 数据量 | 正确展示 |
| --- | --- |
| 0 | 明确空状态，说明第一次观察会建立基线 |
| 1 | 基线卡：时间、价格、来源状态；不绘图 |
| 2+ 有效价格点 | 绘制曲线，同时保留明细 |
| 多条状态但少于两个价格点 | 展示状态证据，明确暂不绘图 |

### 10.2 轮询历史

- 有界读取，例如最近 100 次；
- 页面显示区域有最大高度；
- 超过可见数量后提供键盘可达滚动；
- 区分手动、Cron、重试和复核；
- 显示成功、失败、耗时、结果数量和覆盖范围；
- 不无限推动页面向下增长。

### 10.3 手动巡回

文案必须说明：

- 会立即排入一次真实扫描；
- 结果照常写入证据；
- 仍按现有提醒规则处理；
- 不把原定下一次巡回向后顺延；
- 限流与阻断仍遵守冷却规则。

### 10.4 来源状态

`success`、`empty`、`failed`、`disabled`、`cooldown` 必须保持一对一语义，不以颜色相近或统一“异常”文案抹平差异。

## 11. 危险动作规则

删除整份档案必须满足：

1. 只出现在档案详情；
2. 使用明确的危险文案；
3. 打开确认对话框；
4. 对话框说明删除与保留的资产；
5. 明确不可撤销；
6. 默认焦点不落在确认删除；
7. 支持取消与 Esc；
8. 验收时只打开并取消，不删除真实生产资产。

应明确区分：

- 删除关注档案；
- 移除某个来源绑定；
- 删除商品记录；
- 清除分析样本。

它们不是同一个动作，也不应该复用模糊的“删除”确认内容。

## 12. 视觉设计与产品语义的正确顺序

正确顺序是：

1. 领域实体；
2. 页面职责；
3. 操作所有权；
4. 路由与跳转；
5. 信息层级；
6. 组件模型；
7. 排版、颜色、材质；
8. 动效；
9. 响应式与无障碍；
10. 生产验收。

本项目的近白纸张、雾蓝透明层、明朝大标题、细线和编辑式构图应继续保留。

但视觉设计必须帮助用户区分实体，而不是把所有页面做成外观相似、职责相同的大卡片。

## 13. 后续 UI 任务的强制工作流

### 阶段 A：建立真实基线

- 读取仓库与 Web 规则；
- 查看生产页、本地页和参考站；
- 查看相关路由的完整任务链；
- 保存桌面、移动端和关键状态证据；
- 记录工作树与生产版本。

### 阶段 B：先写语义合同

在改 TSX/CSS 前写出：

- 领域名词表；
- 页面职责矩阵；
- 操作所有权矩阵；
- 路由跳转图；
- 数据量为 0、1、长列表时的展示；
- 危险动作影响范围。

如果无法用一句话说明每个页面，就不能开始视觉实现。

### 阶段 C：审查重复与越权

对每个按钮问：

1. 它改变的是哪个实体？
2. 哪个页面拥有这个实体？
3. 当前页面应该操作，还是只应该链接？
4. 同一动作是否在另一个页面重复？
5. 用户是否能预知副作用？

### 阶段 D：实现

- 先修 DOM 与组件语义；
- 再做布局和视觉；
- 复用设计 token 与无障碍 primitive；
- 不为了省事把不同实体塞入同一表单；
- 不因为 API 能联查就复制完整管理区。

### 阶段 E：验收

- 桌面与约 390×844 移动端；
- 默认、加载、空、错误、长列表、单条证据；
- 键盘、焦点、Esc、reduced motion；
- 无横向溢出；
- 控制台无错误；
- 真实数据，不用假记录填图；
- 沿完整路由链检查重复操作。

### 阶段 F：发布

- 从最新 main 建立干净发布范围；
- 防止夹带未完成的数据模型；
- 使用 Linux CI OpenNext artifact；
- 部署后重新检查生产页面；
- 清楚区分本地完成、CI 完成、已部署和生产实测。

## 14. 快速否决规则

出现以下任一情况，应暂停实现并重新做语义审查：

- 一个页面同时出现“记录证据”和“控制运行”的完整面板；
- 同一暂停、删除或立即运行按钮出现在列表和详情；
- 单品档案可以加入关键词绑定；
- 按钮名称描述的是局部区块，目的地却是完整实体页；
- 一个数据点被展示成趋势；
- 历史列表没有读取和显示边界；
- 删除按钮没有说明保留与删除的资产；
- 页面需要靠长段说明才能解释自己和另一个页面的区别；
- 参考站视觉决定了本项目的业务路由；
- 只检查一个截图就宣称跨页流程完成。

## 15. 这几轮做对的事情

复盘不是否定全部工作。以下做法应保留：

- 用户基于真实截图指出混合与重复，而不是接受“功能能用”；
- 关注档案最终拆成单品与关键词两种创建语义；
- 删除加入明确确认和资产保留说明；
- 手动巡回与下一次定时巡回的关系被写清；
- A6/A7 最终建立商品记录与监控档案的双向链接；
- 单点价格改为基线证据；
- 历史和事件有界读取；
- 发布时从最新 main 隔离 Web 改动；
- 类型检查及时发现未完成调度模型被误夹带；
- 生产验收没有点击删除、立即巡回或制造假数据。

## 16. 对 Agent 工作方式的反思

### 16.1 应更早从系统层回答问题

最初更关注“把用户指出的控件改好”，没有先对整个 Search → Watches → Listings → Events → Analytics 路由链做职责审计。

这是导致修完 A4/A5 后，A6/A7 又暴露同类问题的直接原因。

### 16.2 不应把功能齐全当成信息架构完整

页面拥有更多入口、状态和按钮，不代表用户更容易理解。

真正的完整是每个能力有唯一归属，并在其他页面以最小链接建立关系。

### 16.3 不应让视觉完成度掩盖语义冲突

编辑式构图、纸张材质和精细排版让页面看起来成熟，但成熟外观会提高错误结构的迷惑性。

以后必须先通过语义矩阵，再允许进入视觉精修。

### 16.4 应把用户的疑问当成架构信号

“为什么这里也有”“查看历史和查看档案是不是重复”“我只是看档案为什么还能添加关键词”都不是单点抱怨。

它们是操作所有权或实体边界失效的信号，应立即扩展检查同类页面。

### 16.5 应更早说明交付状态

发布流程长并不等于开发又做了一遍。以后进入 CI、artifact、部署或生产验收时，应主动说明正在跨越哪个边界，以及为什么这一层不能跳过。

## 17. 独立前向测试发现的剩余问题

### 17.1 单品建档入口仍不唯一

当前 `origin/main` 中：

- `listing-manager.tsx` 在商品库卡片内展开频率、首次巡回、目标价和提醒配置，然后 POST 建档；
- `listing-detail.tsx` 也可以 POST 建档，但直接采用固定 180 分钟和 `minDropAmount=100`。

这不是简单的“两个地方都能进入建档，所以更方便”。两个入口对副作用的解释和默认值不同，用户从不同路径创建同一实体可能得到不同计划。

最小纠偏建议：

1. `/listings` 只显示“尚未关联关注档案”和“打开商品记录并建立关注”；
2. `/listings/[id]` 成为唯一单品建档入口；
3. 提交前明确展示频率、首次巡回、降价阈值和提醒默认值；
4. 建档后只显示关系摘要与“管理关注档案”链接；
5. 所有后续编辑仍归 `/watches/[id]`。

### 17.2 读取失败仍可能伪装为空状态

商品库首次加载使用 `.catch(() => undefined)`，失败后 `items` 保持空数组，并显示“完成一次真实搜索或监控基线后，来源商品记录会出现在这里”。

这会把网络、认证或 API 失败解释成真实空库，违背产品对可审计状态的要求。

最小纠偏建议：

- 为商品库建立独立的 `loading / loaded / failed` 状态；
- 只有 `loaded && items.length === 0` 才显示真实空态；
- `failed` 显示可理解错误和重试动作；
- 筛选请求失败也保留旧结果或明确失败，不能清空后假装没有记录。

### 17.3 这次前向测试说明了什么

测试实例只读取 `audit-ui-semantics`、A6/A7 原图和当前代码，没有读取本报告，也没有得到预设结论。

它能复现已知问题并发现两个新缺口，说明 Skill 的页面职责矩阵、操作所有权和状态证据检查具备迁移能力，而不是只会背诵 A4–A7 的答案。

## 18. 后续完成定义

同类 UI 任务只有同时满足以下条件才算完成：

- 每个领域名词有唯一解释；
- 每个页面能用一句话说明职责；
- 每个破坏性或运行操作有唯一所有者；
- 跨页关系通过明确链接表达；
- 列表页不复制详情页控制台；
- 0、1、长列表和失败状态均有真实设计；
- 数据可视化不超过证据强度；
- 参考资产只影响视觉原则，不替代产品判断；
- 桌面、移动端和完整路由链经过浏览器核验；
- 发布范围不夹带其他业务模型；
- 生产页面实际可见且控制台干净。

## 19. 本报告与 Skill 的关系

本报告保存项目背景、错误证据和完整推理。

配套 Skill `audit-ui-semantics` 只保留后续执行所需的紧凑流程，并把日淘商品雷达的领域模型放在按需读取的 reference 中。

以后遇到以下请求应触发该 Skill：

- “这个页面和另一个页面是不是重复了”；
- “为什么这里也有暂停/删除/监控”；
- “路由逻辑很混乱”；
- “结合参考站重新设计这个页面”；
- “顺手巡查其他页面有没有同类问题”；
- “先别无脑画 UI，想清楚语义”；
- 大范围 UI 重构或跨页面信息架构审查。

## 20. 后续真实反馈补充：信息减法、增长边界、操作反馈和视觉层级

前一版复盘已经建立了“实体—页面—操作”的主框架，但后续截图证明，仅解决路由和操作所有权仍然不够。页面还会因为无决策价值的说明、没有增长策略的列表、缺少过程反馈的慢操作，以及被错误提升到前景的装饰素材而再次变得难用。

### 20.1 重复标签和说明性噪声不是“小文案问题”

商品记录页同时出现“筛选单品档案”和“按标题或来源商品 ID 搜索”，前者没有补充任何信息。搜索页又展示来源适配服务、Cookie、代理、覆盖窗口等长段实现说明；结果区还用“跨站结果会在这里展开”描述显而易见的布局。

这些文案共同的问题是：它们没有帮助用户作出当前页面上的决定。

以后每段可见文字必须至少回答一个问题：

- 这是什么；
- 我现在能做什么；
- 当前处于什么状态或为什么失败；
- 执行操作后会发生什么。

如果删除一句话不会改变任何决定、状态理解或副作用预期，就删除它。输入框仍必须有无障碍名称，但不能为了无障碍再制造一份与 placeholder 完全重复的可见标题。来源基础设施、合规边界和覆盖说明应放到来源状态、帮助或审计语境；只有它会改变本次选择或解释本次异常时，才进入主流程。

### 20.2 实时搜索不能默认展开关注档案配置

搜索请求回答“现在能找到什么”，关注档案回答“以后如何继续等待”。把关注目的和巡回频率常驻在搜索表单中，会让一次即时检索看起来像必须建立长期任务。

正确方式是先完成搜索主流程；只有用户明确点击“保存为关注”后，才逐步展开目的、频率和通知后果。多来源关键词雷达共享一份关键词、目的和调度，来源之间只保留各自状态与证据，不能为每个来源复制一整套配置和运行面板。

### 20.3 “最近搜索”必须先设计 100 条时怎么办

横向卡片轨道加原生滚动条在少量记录时看似省空间，记录增长后会带来三个问题：发现成本高、键盘和触控导航不稳定、一次性 DOM 数量持续增长。

这类区域在实现前必须同时回答：

- 查询最多读取多少条；
- 页面一次渲染多少条；
- 用户如何知道当前位置和总量；
- 0、1、4、30、100 条时分别如何表现。

本轮采用有边界的历史读取和每页四条的响应式网格，以明确分页替代原生横向滚动条。具体数字可以随产品调整，但“查询有界、DOM 有界、导航可见”是不可退让的语义要求。

### 20.4 慢操作必须在当前视口证明系统已经响应

多来源搜索存在真实等待时间。只把按钮文字改成“正在搜索”仍不足够，尤其结果区域在当前视口之外时，用户只能反复观察页面有没有新增内容。

搜索开始后应立即在操作附近显示真实活动状态，并保留本次已提交的关键词与来源集合。反馈只能表达已知阶段和来源，不伪造百分比；恢复历史快照必须与重新访问来源明确区分；失败后要保留来源级结果；所有装饰性运动必须支持 `prefers-reduced-motion`。

### 20.5 背景素材不能被组件化成前景卡片

参考素材中的蓝色场和树影用于建立纸张后的环境层。实现却曾把树影放进 Hero 右上角的有边框、有阴影、大面积占位元素，结果装饰层与正文争夺阅读层级。

`position: absolute` 不等于“已经是背景”。每个视觉素材必须先被归类为背景、内容、控制或证据，再检查它的边框、阴影、不透明度、层叠顺序和空间占用。背景素材不能获得内容卡片的边界，也不能占用正文列。代码意图不能替代实际渲染验收：只有在目标路由的截图中不抢标题、不压缩正文、不制造伪组件，才算背景成立。

## 21. 本轮新增的强制审查门槛

### 21.1 文案决策门

逐句写出它支持的用户决定、状态或副作用。写不出就删除；不能用长段解释补救错误的信息架构。

### 21.2 增长门

所有历史、卡片流和来源结果都先验证 0、1、10、100 条，并同时定义查询上限、DOM 上限、分页或滚动语义。原生横向滚动条不能作为主要导航。

### 21.3 延迟反馈门

所有明显非即时的动作都必须在触发处或同一视口给出真实反馈，区分实时请求、快照恢复和保存任务；不使用虚假进度，并提供 reduced-motion 降级。

### 21.4 视觉分层门

每个素材先标注背景、内容、控制或证据。背景不得被边框、阴影或独立卡片容器提升到前景；实际截图的阅读竞争关系高于 CSS 属性名称和实现者意图。

### 21.5 发布工作区卫生门

同一组连贯修改只维护一个隔离发布工作树，后续修正复用它，不为每个小任务创建新的 `qianfantian-*` 目录。PR、合并或部署结束后及时清理可再生成的 artifact 和已经由远端保留、确认干净的临时工作树；绝不删除脏工作树、未推送提交或受保护的用户文件。工作区卫生不是磁盘整理的附属任务，而是避免旧代码、旧产物和错误发布范围再次混入的发布正确性条件。

### 21.6 实际渲染门

静态类型、Lint 和 CSS 选择器只能证明实现可编译，不能证明阅读层级正确。涉及构图、动效或长列表时，必须在目标路由检查真实渲染；未执行浏览器验收时要明确标注，不得把代码检查表述为视觉验收。

## 22. 最终结论

这几轮修改的主线不是把某张截图做得更漂亮，而是逐步把产品从“数据库能力的可视化集合”改成“用户可以理解的观测系统”。

最重要的教训是：

> 先决定事实、计划、事件和分析分别属于谁，再判断每句话是否支持决策、每个列表如何增长、每个慢操作如何反馈、每个素材属于哪一层。

只要页面职责、操作所有权和证据强度先被固定，参考站的视觉语言才能真正提升产品；否则，再高级的 UI 也只是在美化混乱。

当前商品记录链还应继续收敛单品建档入口，并补齐加载失败语义。这两项仍是单独的后续业务任务，不应借本轮前端语义清理静默夹带。
