## 1. 这件事要解决什么

关键词档案（`watch_profiles.dossier_kind='keyword'`）每天巡回各来源，把"上一轮没见过的商品"判为上新并推送。

原实现有两个根本缺陷：

1. **只读一页**。每轮实际只取第一页（270/274 次运行 `page_depth=1`），而 Mercari 这类来源单日真实上新量超过一页，落在第二页之后的新品永远读不到。
2. **收敛判据是顺序判据**。原规则等价于"撞上任意一个已知 ID 就停"。但只有 mercari / animate / charaon / amiami 按上架时间倒序；rakuten 按 `-updateTimestamp`、surugaya 按 `modificationTime` 排序，一个改过价的老商品被顶回首页就能把整轮回溯截断在它上面。

**重构方案（用户已选定"水位线重构"）**：

- 收敛改成**集合判据**：一页里只要还存在「没见过」或「比水位线新」的商品就继续往回翻，整页都既见过、又不比水位线新时才停。对非单调来源同样安全，最坏只是多翻几页。
- 每个绑定新增两个字段：`new_listing_anchored_at`（是否已建立可信基线）、`new_listing_watermark`（已覆盖到的最新上架时间）。
- **首次锚定轮**：预算加深到 8 页（`ANCHOR_PAGE_FLOOR`），把存量一次性挖出来，并且**不推通知**——深挖出来的是早就在架的老货，当成今天的新品会直接刷屏。
- 锚定完成后转入日常巡回预算。

## 4. source-runner 瘦身（09-06）

### 起因：雅虎商城深度恒为 2

09-05 晚间锚定轮里 yahoo_shopping 的深度**从来没有到过 3 页**。查下来既不是雅虎拒绝，也不是关键词没有第 3 页——本地 IP 和生产 VPS IP 用纯 fetch 都能读到第 8 页（`total=570`、`totalPage=19`），连"每页新开会话"的生产模式都复现成功。

根因在我们自己的传输层 `apps/source-runner/src/adaptive-fetch.ts`：

- 每个响应先用 `response.clone()` 复制一份做"取证快照"，累计预算 `MAX_TOTAL_CAPTURE_BYTES = 2.6 MB`。
- 雅虎搜索页每页约 1 MB，一个 `pageToken=3` 的任务要顺序走 1→2→3 三页，**第三页必然撑爆预算**。
- 撑爆后 `boundedText` 对着 clone 分支调 `reader.cancel()`。clone 出来的两个分支共用一条 tee，**取消其中一个分支会让另一个分支永远读不出来**——`transport.fetch` 的 await 不落地，任何 AbortSignal 都够不着。

隔离实验（生产 release、同一个 URL 连抓三次，与翻页无关）：

```
fetch #1   1484ms  200  交给解析器的正文 1,031,813  __NEXT_DATA__ 在
fetch #2    529ms  200  交给解析器的正文 1,031,813  __NEXT_DATA__ 在
fetch #3  30001ms  FETCH_TIMED_OUT_30s  —— 第三份快照根本没被记录
```

这一个原因同时解释了：雅虎深度永远卡在 2 页、`yahoo_next_data_missing`、以及 09-05 18:45 那次 `source_runner_job_watchdog_expired`。**它不是雅虎专属**——任何一次任务里连抓几个大响应的来源都会中招。

### 改了什么（三刀，commit `931bb78` + `a2dea9b`）

**第一刀 · 取证不再碰功能正文**

`clone()` 与 `reader.cancel()` 全部移除。正文一次读成字节，取证从这份字节里切，适配器拿到的是按同一份字节重建的 `Response`。取证预算从此只决定"留存多少"，碰不到解析器能读到什么。新增 `MAX_RESPONSE_BYTES = 3 MB` 作为单次响应读进内存的硬上界，越界判 `response_too_large`。

同时停止回传 HTML 正文：`source-capture.ts` 的 `persistedRawPayload` 和建表约束 `ck_source_response_captures_html_metadata_only` 本来就拒绝存 HTML 正文——**近 7 天回传 118 MB、落库 0 字节**，还白占任务响应的 4 MB 上限。现在只回传大小与哈希，`payloadBytes` 记的是真实体积而不是截断后的数字。

**第二刀 · Playwright 下线**

证据：VPS 上 chromium 二进制最后一次执行是 **2026-07-28**（`relatime` 挂载，atime 可信），近 7 天日志 0 次浏览器事件。而整套 clone-取证机制存在的唯一理由，就是给 `shouldRenderFallback` 判"要不要转浏览器渲染"。

移除代码、`package.json`、lockfile、systemd 的 `PLAYWRIGHT_BROWSERS_PATH`；`/healthz` 的 `runtime` 从 `node-playwright` 改为 `node-fetch`。人机验证页不再自愈，改为打 `source_runner_challenge_detected` 日志，由适配器自己的判定把该轮判失败、业务自愈闸门接手。

⚠️ **`/opt/jpgr-playwright`（646 MB）故意保留**：上一个 release `ac1bbd2` 的 node_modules 里还有 playwright，真要回滚需要这个二进制。跑顺几天再删，届时可连同旧 release 一起回收约 3 GB。

**第三刀 · 雅虎商城 / PayPay 跳蚤退回 Cloudflare 直连**

`YAHOO_CLOUDFLARE_DIRECT_ENABLED` 与 `YAHOO_FLEAMARKET_CLOUDFLARE_DIRECT_ENABLED` 早就是 `true`，但 `searchWithConfiguredRoute` 里 runner 的短路排在前面，这两个开关**从未生效**。改为：直连开关一开，它就是主路径（`sourceRequestRoute` 与 search / item 两处闸门同步）。

上线前用一个临时 worker 从 Cloudflare 出口实测（验完即删）：

| | 第 1 页 | 第 2 页 | 第 3 页 |
|---|---|---|---|

| PayPay 跳蚤 | 200 / 1003ms | 200 / 1033ms | 200 / 651ms |

## 7. 排查用 SQL

数据库访问：`ssh root@203.0.113.10 "sudo -u postgres psql -X -d jpgr"`
（大段 SQL 写进本地文件再 `< file` 管道，heredoc 直塞会断连）

```sql
-- A. 锚定与水位线总览（本地时间列）
SELECT p.name, b.source_id, b.new_listing_anchored_at, b.new_listing_watermark,
       b.last_run_at, b.next_run_at,
       to_char(b.next_run_at::timestamptz AT TIME ZONE 'Asia/Shanghai','MM-DD HH24:MI') AS next_local
FROM radar_core.watch_bindings b
JOIN radar_core.watch_profiles p ON p.id=b.watch_profile_id
WHERE b.enabled=1 AND p.dossier_kind='keyword'
ORDER BY p.name, b.source_id;

-- B. 今晚的运行结果（把时间换成实际时刻）
SELECT p.name, b.source_id, r.status, r.result_count, r.new_count, r.coverage,
       r.error_code, left(coalesce(r.error_message,''),70) AS msg, r.started_at, r.finished_at
FROM radar_core.watch_runs r
JOIN radar_core.watch_bindings b ON b.id=r.watch_binding_id
JOIN radar_core.watch_profiles p ON p.id=b.watch_profile_id
WHERE r.started_at >= '2026-09-05T10:30:00Z'
ORDER BY r.started_at;

-- C. 翻页深度（只有成功轮才写得出真实值；失败轮的 page_depth 恒为 1，不能用来判断）
SELECT s.source_id, s.page_depth, s.cursor_termination_reason,
       s.raw_result_count, s.normalized_result_count, s.state, s.observed_at
FROM radar_core.source_health_snapshots s
WHERE s.observed_at >= '2026-09-05T10:30:00Z'
ORDER BY s.observed_at;

-- D. 上新事件（锚定轮应为 0）
SELECT e.event_type, count(*) FROM radar_core.events e
WHERE e.created_at >= '2026-09-05T10:30:00Z' GROUP BY 1;

-- E. 错误分布
SELECT r.error_code, left(coalesce(r.error_message,''),80) AS msg, count(*),
       max(r.started_at) AS last_seen
FROM radar_core.watch_runs r WHERE r.started_at >= '2026-09-05T10:30:00Z'
GROUP BY 1,2 ORDER BY 3 DESC;

-- F. 采集量（AI 任务条数是未被失败污染的深度证据）
SELECT b.source_id, j.status, j.total_items, j.completed_items, j.failed_items, j.created_at
FROM radar_core.gemini_jobs j
JOIN radar_core.watch_bindings b ON b.id=j.binding_id
WHERE j.created_at >= '2026-09-05T10:30:00Z' ORDER BY j.created_at;
```

## 9. 踩过的坑（别重复）

1. **写了 SQL 不在真库上跑就部署** —— 今天最大的教训，闸门就是为此加的。
2. `AGENTS.md` 说"不要跑测试"，但 `pnpm verify:sql` **不是测试**，是部署前的真库校验，必须跑。
3. `grep -rn` 全仓扫描会 120s 超时，用 Grep 工具。
4. SSH heredoc 直塞大段 SQL 会断连（`Connection closed`），写文件再 `< file`。近万行的脚本用 `scp` + `psql -f`，stdin 会 `spawnSync ssh EOF`。
5. `mergedRequestEvidence` 的 `pagesFetched` 在精确同款里是**跨查询变体求和**，不等于翻页数，别用它证明翻页生效。
6. **失败轮的 `source_health_snapshots.page_depth` 恒为 1**（错误处理路径写的默认值），不能用来判断深度。用 `gemini_jobs.total_items`。
7. 统计 `min(next_run_at)` 时注意排除 `enabled=0` 的绑定，否则会看到假的"卡住"。
8. 用户时区 **UTC+8**，汇报时间一律换算，别只给 UTC。

09-06 追加：

9. **`response.clone()` + `reader.cancel()` 是致命组合**。clone 的两个分支共用一条 tee，取消其中一个会让另一个永远读不出来，`await` 不落地且 AbortSignal 够不着。要"边读边留证"就一次读成字节再重建 `Response`，别 clone。
10. **取证 / 日志预算绝不能作用在功能正文上**。判据很简单：问一句"这条预算耗尽时，业务功能会不会退化"——会，就是设计错了。
11. `atime` 在 `relatime` 挂载下是可信的"最后一次执行"证据（先 `findmnt -no OPTIONS -T <path>` 确认挂载选项）。用它判断一个二进制是不是死代码，比翻日志快得多。
12. VPS 上**没有全局 pnpm**，部署要用 `corepack pnpm`；且必须在仓库目录里跑，才会按 `packageManager: pnpm@9.4.0` 解析版本（在 `/root` 里跑会拉到最新版）。
13. 改了 `apps/source-runner/package.json` 的依赖必须同步 `pnpm install --lockfile-only` 并提交 lockfile，否则 VPS 的 `--frozen-lockfile` 会失败。
14. `SOURCE_RUNNER_*_IDS` 有**两份**：`apps/source-runner/src/source-policy.ts`（服务端 URL 白名单）和 `apps/collector/src/source-runner-client.ts`（客户端路由）。决定实际路由的是**后者**——骏河屋在前者里但不在后者，所以它一直是 Cloudflare 直连，不是 VPS 采集。
15. Collector Worker 是 `workers_dev: false` 且没有 HTTP 路由，`/internal/*` 端点**外部打不到**，只能由 cron / 队列触发。要验证生产行为就改 `next_run_at` 触发一次真实轮次，**记得还原**（还原时顺延一天，别把当天的时间档冲掉）。
16. VPS 的 release 目录用 `cp -a` 复制会**打断 pnpm store 的硬链接**，1.1 GB 一份而不是 27 MB。发完版记得清掉多余的 release。
