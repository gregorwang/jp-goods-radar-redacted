# 精确同款采集成本削减：7 天观察口径

改动日期：2026-09-07
部署时间：**2026-09-07 09:13 UTC**（commit `79b9c29` push 到 main，Cloudflare Workers Builds 自动部署）
观察窗口：**2026-09-08 ~ 2026-09-14**（09-07 只有部署后的半天，不算干净的第一天）
结论方式：**只看生产历史数据**。下面每条判据都给了可直接跑的 SQL，跑完再决定留、调、还是退。

---

## 1. 改了什么

两处，都只作用于**巡检路径**（`executeExactProductSearch`，`apps/collector/src/index.ts`）。
手动搜索 / 建档路径一行没动，仍然全量扇出 + 多页预算——那是一次性成本，值得花。

### P1 主查询优先（fan-out）

```
先打完整商品名
  ├─ 本轮已有 exact / probable_exact 候选 → 收手
  ├─ 一条都没有 → 追加下一条短召回，最多再追 2 条
  └─ 主查询整个失败（429/封锁）→ 立即停，不再追加
```

- 判据函数：`hasQualifiedExactCandidate()`
- 上限常量：`EXACT_PRODUCT_WATCH_FALLBACK_VARIANTS = 2`
- 判据**不看在售状态**：问的是「这条查询能不能搜到这件商品」，一条已售出的确认同款
  同样证明查询有效。在售与否交给后面的清洗和送达门槛。

### P0 详情补抓去重（hydration）

原来那道 `rawMetadata.detailHydrated` 守卫是**死的**：这个字段全仓库只有
`surugaya-direct.ts` 会写，其余来源的搜索结果里根本没有它，于是同一件商品每轮
都被重复补抓。

- 新列：`radar_core.listings.detail_hydrated_at`
  （migration `20260907120000_listing_detail_hydrated_at`，已于 2026-09-07 应用到生产）
- 新方法：`RadarRepository.storedListingDetails()`
- TTL 常量：`EXACT_PRODUCT_DETAIL_HYDRATION_TTL_MS = 12h`
- 跳过抓取**不让匹配器变瞎**：`applyStoredListingDetail()` 把库里上一次补抓的描述与
  结构化属性贴回本轮搜索结果，价格/在售仍用本轮最新值。判定证据和真抓一次是同一份。
- `applyStoredListingDetail` 刻意**不打** `detailHydrated` 位——打了水位会自我续期，
  补抓从此永不发生。只有真发出过详情请求的 `mergeSearchAndDetailListing` 才打。

### 这里有一条必须盯住的事实

**`match_relation='exact'` 在整个基线期恒为 0。**

P1 的收手判据是 `exact` **或** `probable_exact`，而 `exact` 实际上从来没出现过——
也就是说**这个判据完全靠 `probable_exact` 撑着**。

推论：如果哪天匹配器收紧到 `probable_exact` 也变稀有，主查询会被判成「没捞到」，
fallback 每轮必发，改动直接退化成「K=3 + 详情去重」，扇出那一半的收益归零，
而且**不会有任何报错**。这是本次改动最安静的失效模式，第 5 节有专门的检测 SQL。

### Q1 — 成本：每轮上游请求数（主指标）

```sql
SELECT substr(r.started_at,1,10) run_day,
       count(*) runs,
       round(avg(c.reqs)::numeric,2) avg_req_per_run,
       max(c.reqs) max_req,
       sum(c.reqs) total_req,
       round(avg(r.duration_ms)::numeric) avg_ms,
       round(avg(r.result_count)::numeric,2) avg_results
FROM radar_core.watch_runs r
JOIN radar_core.watch_bindings b ON b.id=r.watch_binding_id
LEFT JOIN LATERAL (
  SELECT count(*) reqs FROM radar_core.source_response_captures sc WHERE sc.run_id=r.id
) c ON true
WHERE b.source_config_json LIKE '%exact_product%'
  AND r.started_at >= '2026-08-31'
GROUP BY 1 ORDER BY 1;
```

### Q2 — 成本：按来源拆，确认 Mercari / Yahoo 真的降了

```sql
SELECT sc.source_id,
       count(*) reqs,
       count(DISTINCT sc.run_id) runs,
       round(count(*)::numeric/NULLIF(count(DISTINCT sc.run_id),0),2) req_per_run
FROM radar_core.source_response_captures sc
JOIN radar_core.watch_runs r ON r.id=sc.run_id
JOIN radar_core.watch_bindings b ON b.id=r.watch_binding_id
WHERE b.source_config_json LIKE '%exact_product%'
  AND sc.captured_at >= '2026-09-08'
GROUP BY 1 ORDER BY 2 DESC;
```

### Q3 — 召回：确认同款有没有掉（**这是唯一的否决项**）

```sql
SELECT substr(o.observed_at,1,10) run_day,
       count(*) observations,
       count(*) FILTER (WHERE o.match_relation='exact') exact_rel,
       count(*) FILTER (WHERE o.match_relation='probable_exact') probable_rel,

FROM radar_core.watch_run_listing_observations o
JOIN radar_core.watch_bindings b ON b.id=o.watch_binding_id
WHERE b.source_config_json LIKE '%exact_product%'
  AND o.observed_at >= '2026-08-31'
GROUP BY 1 ORDER BY 1;
```

## 5. 判据：什么算成功

| 指标 | 基线（09-07） | 期望 | 不及格线 |
|---|---|---|---|
| 每轮上游请求（Q1） | 13.79 | **≤ 5** | > 9 说明 fallback 在频繁触发 |
| Mercari 每轮请求（Q2） | 23.04 | **≤ 8** | > 15 |
| 每日 confirmed（Q3） | 6 ~ 19 | **持平**（7 天总量不低于前 7 天的 90%） | **低于 80% 直接回滚** |
| 有命中的绑定数（Q3） | 23 ~ 27 | 持平 | 少 3 个以上要逐个排查 |
| `detail_hydrated_at` 非空（Q4） | 0 | **> 0 且持续增长** | 恒为 0 = P0 没生效 |
| failed 轮次（Q5） | 3 ~ 8/天 | 持平或更低 | 明显上升 |

**只有 confirmed 掉超过 20% 才是回滚理由。** 请求数没降到预期只是调参问题
（`EXACT_PRODUCT_WATCH_FALLBACK_VARIANTS`、`EXACT_PRODUCT_DETAIL_HYDRATION_TTL_MS`
两个常量都在 `apps/collector/src/index.ts` 顶部）。

### 静默失效检测（对应第 3 节的警告）

-- probable_exact 是否还在产出。如果这一列变成 0，收手判据永远不成立，

SELECT substr(observed_at,1,10) run_day,

`qualified` 连续两天为 0 → 收手判据失效，去看是不是匹配器被改严了。

## 6. 已知混淆项（读数时别被骗）

1. **09-04 之前的请求数基线不可信。** `avg_req_per_run` 是 0.4~0.8，即多数轮次
   一条 capture 都没记——说明那段时间 capture 录制不完整，不是「当时真的这么便宜」。
   **只用 09-05 ~ 09-07 做对照。**
2. **09-05 是异常日。** 扇出上线当天，failed 21（平时 3~8），observations 3420
   （平时 1200 左右），probable_exact 1074（平时 100~200）。做平均时要单独看。
3. **09-07 的数据只有半天。** 38 轮 vs 平时 60~70。
4. **绑定数会变。** 用户随时可能加/删档案。所有「总量」指标都要除以当日 runs 或
   绑定数再比，别直接比绝对值。
5. **TTL 是 12h、巡检一天多轮**，所以详情补抓不会归零，预期是砍掉约一半。
   如果 7 天后召回没有任何损失，可以把 TTL 拉到 24h 再砍一半。

## 7. 这次**没有**做的

- **每条 query 的历史 precision 自动降权。** 现在做不了：
  `search_query_variants` / `search_candidate_hits` 两张表**只有手动搜索路径会写**
  （`index.ts` 的 `INSERT INTO search_query_variants`），巡检路径的
  `executeExactProductSearch` 返回时把 hits 归属信息丢掉了，只返回 listings。
  要做得先补埋点（按 binding 记录每条 variant 的候选数 / 同款数），再攒几周样本。
  等这次的数据出来、确认 fallback 的实际触发频率之后再决定值不值得做。

- **recallQueries 的「只增不减」修复。** 核实后不成立：`index.ts` 的回填被
  `aiExtracted !== true` 守着，一个绑定一辈子只跑一次；而
  `fingerprintFromJapaneseProductName`（`packages/core/src/product-search.ts`）的
  `recallQueries` 恒为 `[]`，所以那个 union 里的 `previous` 只可能是用户手填的，
  manual-first 是对的。`watch-detail.tsx` 的用户编辑走的是纯 replace。没有旧值堆积的路径。

- **手动搜索路径的任何改动。** 建档要看清卖家怎么写标题，那是一次性成本。

# 追加：2026-09-08 复盘与处置

观察窗口还没跑满就提前收口了，因为 Q4 直接判死：**P0 从来没生效过，是 bug 不是数据不够。**

## Q4 的判决：水位恒为 0，根因已定位并修复

`detail_hydrated_at` 全库 0 行非空，但同期：部署后落库 812 条 listing、真发出 35 次
详情请求、`storedListingDetails` 的 SELECT 在 `pg_stat_statements` 里有执行记录、
带 `detail_hydrated_at` 的新 INSERT 有 858 次调用。所以不是"没攒够"，是标记丢了。

丢在哪：**精确同款路径根本不走 `index.ts` 里那个 `persistListing`**——排完 AI 任务
就 `return` 了。listings 的唯一写入点是 `gemini-jobs.ts` 的 `persistListing`，
而它拿到的 listing 来自 `prepareListingDerivative`，那里有一句 `rawMetadata: undefined`
（引入于 `b58437b`，为的是别给清洗模型送用不上的字节）。`detailHydrated` 这一位
就是在这里被抹掉的，于是水位恒写 NULL，`COALESCE` 永远保留 NULL。

修法：`prepareListingDerivative` 只保留 `detailHydrated` 这一位，其余 rawMetadata
照旧丢弃。AI 成本不受影响，水位恢复推进。

## P1 的判决：判据的前提是错的，不是"匹配器变严"

第 3 节把"qualified 变稀有"写成一种失效模式。实际不是：**59 个精确同款绑定里
34 个从来没产出过 qualified**，而且分界不是稀有度，是**来源的一手/二手性质**——
绝版限定品在 animate、cospa、charaon 这类新品店里结构性地不存在，搜不到是正确行为。

全历史确认同款只来自 5 家：煤炉 14 件、雅虎拍卖 6、雅虎二手 2、骏河屋 1、乐天 1。
其余 6 家一手来源合计 0 件。其中 cospa 与 charaon 连一条观测都没有过。

于是 `hasQualifiedExactCandidate` 在一手店恒不成立，追加召回每轮必然打满，
为一件结构上不可能发生的事长期付费。

## 下一个观察窗口：2026-09-09 ~ 2026-09-15

Q1~Q5 照旧，但换基线，并且加两条：

- **Q1 的对照值改用 8.88**（09-06 ~ 09-07 09:13 的实测），不是正文里的 13.79。
  13.79 是 09-07 半天的读数，全天重算是 10.16，不可复现。
- **Q4 现在必须非空。** 再为 0 就是修复没生效，不是数据不够。
- 第 5 节的静默失效 SQL **少了绑定过滤器**，它扫的是整张
  `watch_run_listing_observations`，混进了 keyword 绑定，读数偏乐观。
  加上 `JOIN watch_bindings ... LIKE '%exact_product%'` 再跑。
- 新增：确认同款要**按去重商品数**看，不要按观测条数。同一件在架商品每天被扫到
  会产生几十条 confirmed 观测，但对用户只是 1 件。

## 仍然没有答案的问题

**追加召回到底救回过东西没有。** 现有埋点答不了：只有煤炉的响应体里能还原出实际
查询词（2246 次请求里 114 次，5%），其余来源全部是 NULL 或 HTML。所以
"扩写贡献为 0"这个结论只覆盖煤炉一家——这也是这次降到 1 而不是归零的原因。

要判死这条，得给 `watch_run_listing_observations` 补 `matched_query` /
`variant_index` 两列（`candidate.hits` 本来就持有这两个字段，落库即可）。
