# AI 清洗成本削减：7 天观察口径

改动日期：2026-09-07
部署时间：**2026-09-07 10:03 UTC**（commit `da3e8e9` push 到 main，Cloudflare Workers Builds 自动部署）
观察窗口：**2026-09-09 ~ 2026-09-15**
（09-07 只剩部署后的小半天；09-08 是缓存重建的尖峰日，见第 6 节第 1 条——两天都不算干净）
结论方式：**只看生产历史数据**。下面每条判据都给了可直接跑的 SQL。

> **和上一份文档的关系**：`精确同款采集成本削减-待观察-20260907.md` 量的是**上游采集请求数**，
> 这一份量的是 **Gemini token**。两者改的是完全不相交的代码路径（那份改采集阶段的扇出与详情
> 补抓，这份改派单阶段的提示词与缓存键），观察窗口可以重叠，指标不会互相污染。详见第 6 节。

## 1. 现象

近 7 天 Gemini 消耗接近数百万 token。触发排查的直觉是对的：**漏斗确实存在，但它装在
手动搜索那条路上，没装在每小时跑的巡检路上。**

- 手动搜索路径有硬上限：`selectProductSearchAiReviewCandidates`
  （`packages/core/src/product-search.ts:1221`），确定性 exact 与硬冲突先出局，
  剩下的模糊尾部按 `PRODUCT_SEARCH_AI_REVIEW_LIMIT = 24` 截断。
- 巡检路径没有这一层：`apps/collector/src/index.ts:993` 的 `deterministicListings`
  是整个过滤后的窗口，`index.ts:1118` 原样丢进 `enqueueKeywordGeminiJob`。

**但整窗口派单本身是对的，不能改。** `finalizeKeywordJob`
（`apps/collector/src/gemini-jobs.ts:1573`）那个循环不只在读 AI 结论——整窗口的
`persistListing`、价格对比和 `evaluateListingEvents` 全在里面。把已判过的商品从
payload 里裁掉，等于让这些商品的降价、补货、售罄、到达目标价通知全部消失，
而这些恰恰是已确认相关、用户最在意的那批商品。

所以省钱的正确位置不是"少送商品"，而是"同一条商品语义没变就别再问一次模型"。
这层机制**一直都在**：`processGeminiJob`（`gemini-jobs.ts:2200`）的 `cachedResult()`
按 `inputHash` 逐条命中 `radar_analytics.ai_enrichments` 并跳过模型调用。

**它一直在跑，只是钥匙配错了。**

## 2. 改了什么

一处，在派单阶段。采集阶段一行没动。

### 根因：inputHash 覆盖了每轮都在变的字段

`inputHash` 原来对整条 normalized listing 取哈希，其中包含 `currentPrice`、
`availability`、`sourceUpdatedAt`、`facts.imageUrls`、以及 `displayFacts` 里的
收藏数与评价数。卖家改一次价、bump 一次、收藏数动一下 —— 钥匙就变了，
Postgres 里那条已清洗结果配不上锁，整条商品重付一遍。

巡检每小时一轮、Mercari 窗口约 200 条（`marketDefaultPages = 4`，实测一页约 52 条），
`schedule_interval_minutes` 默认 60、最低 30。缓存全 miss 时，**单个 Mercari 关键词
绑定就是每天数百万 token 量级。**

### 改法：提示词与缓存键收敛到同一份语义投影

新增 `listingSemanticProjection()`（`packages/ai/src/listing-enrichment.ts`），
`listingEnrichmentMessages` 与四处 `inputHash` 计算
（`gemini-jobs.ts:796 / 930 / 1000 / 1072`）共用它。

**两者必须共用一份**：缓存键覆盖的字段比提示词少，就会把两次内容不同的提问当成
同一条缓存命中 —— 那是错误答案，不是省钱。

| 剔掉 | 理由 |
|---|---|
| `imageUrl`、`facts.imageUrls`、`facts.provenance` | 模型读不到图片；URL 上挂着缓存破坏用的时间戳；provenance 是采集溯源 |
| `currentPrice`、`originalPrice`、`availability`、`sourceUpdatedAt`、`facts.priceContext`、`facts.priceReferences`、`facts.sourceAvailabilityLabel` | 提示词本来就写着「价格、库存、首次出现、涨跌和数量由程序计算」，`listingEnrichmentSchema` 里也确实没有任何价格或库存字段 |
| `displayFacts` 的 commerce / seller / shipping / other 四组 | 四个 adapter 里这四组的全部字段：`like_count`、`seller_review`、`product_review`、`image_count`、`discount_rate`、`auction_end_at`、`source_status`、`delivery`、`shipping_code`、`point_rate`、`list_price` —— 每一个不是每轮在变就是程序侧数据，没有一个带商品身份语义 |
| `variants[].priceJpy` / `.availability` | 只留 `name` / `value`。尺寸颜色是语义，报价不是 |

保留：`identity` 与 `catalog` 两组 displayFacts（`source_condition`、`category_path`、
`author`、`publisher`、`genre_id`…）、`title`、`descriptionExcerpt`、`condition`、
`facts.manufacturer` / `series` / `characters` / `specifications` / `tags` 等全部身份证据。

`payload.items` 与写进分析库的快照仍是完整商品，`persistChunk` 一行未动。

### 实测

拿 `local-exports/2026-07-18T06-25-53-587Z-…/normalized-snapshots` 里
**309 条真实商品**跑投影：

```
before 529127 bytes (~264564 est tokens)
after  235739 bytes (~117870 est tokens)
saved  55.4%   avg/item 1712 -> 763 bytes
```

这 55.4% 只是**单条商品的体积**。缓存重新开始命中之后省下的比这多得多。

### 顺带：让缓存不再静默失效

`cachedResult` 原来是 `catch {}` —— Hyperdrive 连不上、Postgres 抖一下，它就静悄悄
返回"全部未命中"，整个窗口重新全量送模型，日志一片干净。**这正是能让账单烧一整周
而无人察觉的形状。** 现在：

- 缓存查询失败 → `gemini_listing_cache_unavailable`
- 每次 `processGeminiJob` → `gemini_listing_cache_outcome`，带
  `totalItems` / `reusedFromCache` / `pendingItems`

### 没有 bump prompt version

投影已经让每一条 `inputHash` 都和旧值不同（`availability` 是 `normalizedListingSchema`
的必填字段，永远会被剔掉，所以新旧哈希不可能相撞），**读到脏缓存在结构上不可能**。
而这三个版本串还会以 `watch_listing_matches.semantic_prompt_version` 落库当作匹配
来源，churn 它会让历史匹配的来源标注失真。

## 3. 基线不用抢跑

和上一份文档最大的不同：**这次的基线可以事后补。**

`radar_analytics.ai_processing_batches` 和 `radar_analytics.ai_enrichments` 都是
append-only 带 `created_at` 的证据表，08-31 ~ 部署日的历史不会因为部署而消失。
下面每条 SQL 的时间窗口都从 `2026-08-31` 起，**同一条查询同时给出改动前后的对照**，
不需要在部署前抢一份快照。

一条前提：`ai_processing_batches` 每一行 = **一次真实的 Gemini 调用**
（`persistChunk` → `ingest_ai_enrichments`，`postgres/schema.sql:225`），
`metadata->>'estimatedInputTokens'` 是这次调用的估算输入 token，
`parsed_count` 是这次调用里清洗成功的商品数。这就是账单的直接代理。

## 4. 七天后跑什么

全部在 VPS 上跑：

```powershell
ssh root@203.0.113.10 "sudo -u postgres psql -X -d jpgr"
```

### Q1 — 成本主指标：每天的调用数与估算 token

```sql
SELECT date_trunc('day', created_at)::date AS day,
       count(*)                                              AS provider_calls,
       sum(parsed_count)                                     AS items_cleaned,
       sum((metadata ->> 'estimatedInputTokens')::bigint)     AS est_input_tokens,
       round(avg((metadata ->> 'estimatedInputTokens')::numeric), 0)
                                                             AS avg_tokens_per_call,
       round(sum((metadata ->> 'estimatedInputTokens')::numeric)
             / NULLIF(sum(parsed_count), 0), 0)              AS tokens_per_item
FROM radar_analytics.ai_processing_batches
WHERE purpose = 'listing_semantics'
  AND created_at >= '2026-08-31'
GROUP BY 1 ORDER BY 1;
```

`tokens_per_item` 是**体积**指标，直接对应第 2 节的 55.4%。
`est_input_tokens` 是**总账单**指标，它还包含缓存命中率的收益。

### Q2 — 缓存命中率：同一条商品一天被送进模型几次（**最关键的一条**）

```sql
SELECT date_trunc('day', created_at)::date  AS day,
       count(*)                             AS enrichments,
       count(DISTINCT source_listing_id)    AS distinct_listings,
       round(count(*)::numeric
             / NULLIF(count(DISTINCT source_listing_id), 0), 2)
                                            AS per_listing_per_day
FROM radar_analytics.ai_enrichments
WHERE purpose = 'listing_semantics'
  AND created_at >= '2026-08-31'
GROUP BY 1 ORDER BY 1;
```

**`per_listing_per_day` 就是这次改动的成败。** 改动前它应该接近"每天巡检轮次"
（24 ~ 48）；改动后应该向 **1.0** 收敛（一条商品语义变了才该重清洗一次）。

稳态里它不会正好是 1.0，见第 6 节第 3 条（详情补抓造成的 title 振荡，上界是 2）。

### Q3 — 质量否决项：确认同款有没有掉（**唯一的回滚理由**）

```sql
SELECT substr(o.observed_at, 1, 10)                                   AS run_day,
       count(*)                                                       AS observations,
       count(*) FILTER (WHERE o.decision_status = 'confirmed')         AS confirmed,
       count(*) FILTER (WHERE o.decision_status = 'rejected')          AS rejected,
       count(*) FILTER (WHERE o.decision_status = 'uncertain')         AS uncertain,
       count(DISTINCT o.watch_binding_id)                              AS bindings_with_hits
FROM radar_core.watch_run_listing_observations o
WHERE o.observed_at >= '2026-08-31'
GROUP BY 1 ORDER BY 1;
```

投影剔掉的字段里如果混进了模型真正在用的判据，症状就是 `confirmed` 掉、
`uncertain` 涨。**这是唯一的回滚理由。**

### Q4 — 相关性判定的分布有没有漂移

```sql
SELECT date_trunc('day', created_at)::date        AS day,
       output ->> 'relevance'                     AS relevance,
       count(*)                                   AS n,
       round(100.0 * count(*)
             / sum(count(*)) OVER (PARTITION BY date_trunc('day', created_at)), 1)
                                                  AS pct
FROM radar_analytics.ai_enrichments
WHERE purpose = 'listing_semantics'
  AND created_at >= '2026-08-31'
GROUP BY 1, 2 ORDER BY 1, 2;
```

relevant / irrelevant / uncertain 三者的**比例**在部署前后应当基本持平。
`uncertain` 占比明显上升 = 模型在抱怨证据不够 = 投影剔多了。

### Q5 — 静默失效检测

```powershell
npx wrangler tail jp-goods-radar-collector --format json --profile <你的账号>
```

盯两个 event：

- `gemini_listing_cache_unavailable` — **出现任何一条都要查**。它意味着 Postgres
  查询失败，缓存整体失效，账单会立刻回到改动前。
- `gemini_listing_cache_outcome` — 稳态下 `reusedFromCache / totalItems` 应当很高。
  这条日志给的是**当天就能看到的反馈**，不用等 7 天。

Workers Logs 有保留期，长期结论以 Q1 / Q2 的 Postgres 数据为准。

## 5. 判据

| 指标 | 改动前 | 期望 | 不及格线 |
|---|---|---|---|
| `tokens_per_item`（Q1） | 跑 Q1 读 09-01~09-07 | **降约 55%** | 降幅 < 35% 说明投影没生效，去查是不是还有别的路径在拼提示词 |
| `est_input_tokens` 日总量（Q1） | 同上 | **降一个量级** | 降幅 < 50% 说明缓存仍未命中，看 Q2 |
| `per_listing_per_day`（Q2） | 接近当日巡检轮次 | **≤ 2.5，并向 1.x 收敛** | **> 5 说明缓存还是没命中，这是主要故障模式** |
| `confirmed` 日均（Q3） | 跑 Q3 读 09-01~09-07 | **持平**（7 天总量 ≥ 前 7 天的 90%） | **低于 80% 直接回滚** |

| `gemini_listing_cache_unavailable`（Q5） | — | **0 条** | 出现即查 |

按 Q2 往下查，不用回滚。

## 6. 已知混淆项（读数时别被骗）

1. **09-08 必然是尖峰，那不是失败。** 投影改变了**每一条** `inputHash`，
   所以上线后每条商品都要重新清洗一次才能重新建立缓存。Q1 在 09-08 大概率比
   改动前更高。**从 09-09 起才开始读数**，观察窗口已经按这个排除掉了。

2. **观察窗口和上一份文档重叠，但指标不共用。** `精确同款采集成本削减` 那份量的是
   `radar_core.source_response_captures`（上游请求），这份量的是
   `radar_analytics.ai_processing_batches`（Gemini 调用）。两次改动没有共享的
   代码路径：那份改 `executeExactProductSearch` 的扇出与补抓（采集阶段），
   这份改 `listingEnrichmentMessages` 与 `inputHash`（派单阶段）。可以并行观察。

3. **`per_listing_per_day` 不会收敛到 1.0，上界是 2。** 09-07 上线的详情补抓
   （TTL 12h）让同一条商品在两个 hash 之间来回摆：
   `mergeSearchAndDetailListing`（真抓）做 `{...searchListing, ...detailListing}`，
   会用详情页的值覆盖 `title`；`applyStoredListingDetail`（回贴，`index.ts:2932`）
   只贴 `descriptionExcerpt` 和 `facts`，`title` 仍是搜索页的。`title` 在投影里，
   所以每条商品会稳定占用**两条**缓存记录，两边都命中。**有界，不是漏。**
   要收掉这半点浪费，正确的改法是让两个函数对齐字段（回贴时也贴回 title），
   那是 09-07 那块代码的收尾，**建议等它的观察窗口结束再动**。

4. **`estimatedInputTokens` 不是 Google 的计费 token。** 它是
   `estimateGeminiInputTokens()`（`packages/ai/src/gemini-scheduler.ts:17`）的
   UTF-8 字节 / 2，对中日文混合 JSON 是刻意保守的估算。**只能做趋势对比，
   不能当账单核对。** 要真实数字得看 Google AI Studio 控制台。

5. **09-05 是异常日**（扇出上线当天，observations 3420 vs 平时 1200），
   **09-07 只有半天**。做改动前基线时这两天要单独看。

6. **绑定数会变。** 所有"总量"指标都要除以当日 runs 或绑定数再比。

## 7. 这次**没有**做的

- **按 `sourceItemId` 在 enqueue 前裁掉已判过的商品。** 最初的方案，核实后否掉：
  会让这些商品的降价 / 补货 / 售罄 / 到达目标价通知全部消失（见第 1 节）。
  而且做完投影之后它也没有必要了 —— `radar_analytics.ai_enrichments` 本来就是
  那本台账，`cachedResult` 本来就在查它。**不需要第五张表，需要的是配对的钥匙。**

- **按天 / 按周的 token 预算与熔断。** 现在只有 `reserveGeminiCapacity` 的
  TPM / RPM 滑窗（`GEMINI_SCHEDULER_TPM_BUDGET = 200_000`、
  `GEMINI_SCHEDULER_RPM_BUDGET = 18`），**没有任何累计预算或告警**。
  这次的漏法之所以能跑一周，就是因为它每一分钟都在限额内。
  Q5 那条日志是最小可用的替代品；要不要做真正的日预算 + 告警，
  **等这 7 天的数据出来，看稳态到底是多少 token 再定阈值**，
  现在拍一个数字只会误报。

- **`GEMINI_REQUEST_INPUT_TOKEN_BUDGET = 80_000` 的调整。**
  `takeGeminiTokenBudgetBatch` 无论第一条多大都会收下，所以单次调用上限就是这个数。
  投影降了 55% 体积之后，同一个预算能装下的商品数翻倍，**先看这个副作用有多大
  再决定要不要调**。`LISTING_PROVIDER_MAX_BATCH_ITEMS = 10` 仍然是硬上限。

- **手动搜索路径的任何改动。** 它的漏斗（24 条硬上限）本来就是对的。
