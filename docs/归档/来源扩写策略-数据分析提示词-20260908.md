# 提示词:精确同款采集的「按来源决定是否扩写召回」数据分析

> 用途:把下面整段(从「任务」开始)贴给另一个 AI,让它连生产库做分析。
> 它没有本项目的上下文,所以背景、库结构、坑都写在里面了。

---

## 任务

你要为一个日本二手商品比价/监控系统(jpgr)做一次数据分析,产出一份**按采集来源
分级的召回策略建议**。分析完不要改代码,只出结论和数据。

## 业务背景(必读,数据里看不出来)

系统帮用户盯一件**具体商品**(不是关键词),比如
`ぬいぐるみ エミリア ふわかわロリータぬいぐるみ「Re:ゼロから始める異世界生活」F:NEX限定`。
每轮巡检拿商品名去 11 个来源搜,把搜到的东西判定是不是同一件商品。

判定结果两层:
- `match_relation`:匹配器的机器判定,取值 `exact` / `probable_exact` / `uncertain` / `irrelevant`
- `decision_status`:AI 清洗后的最终裁决,取值 `confirmed` / `rejected` / `uncertain`
  → **`confirmed` 才是真正送到用户面前的结果,是唯一的价值指标。**

### 11 个来源的性质(这是分析的核心分界)

| 来源 | 性质 | 说明 |
|---|---|---|
| `mercari_jp` 煤炉 | **二手** | 个人二手市场,量最大 |
| `yahoo_auctions_jp` 雅虎拍卖 | **二手** | 拍卖 |
| `yahoo_fleamarket_jp` 雅虎二手 | **二手** | 雅虎的闲置市场,和拍卖是两个不同的场 |
| `surugaya` 骏河屋 | **二手中古** | 中古连锁店 |
| `rakuten_ichiba` 乐天 | **一手为主** | 平台,有少量二手但比煤炉少得多 |
| `yahoo_shopping` 雅虎商城 | **一手为主** | 平台,同上 |
| `animate` | **一手** | 单店 |
| `cospa` | **一手** | 单店 |
| `charaon` | **一手** | 单店 |
| `amazon_jp` | **一手** | 平台 |
| `amiami` | **一手为主** | 但按二手的方式扩写查询(业务已定) |

### 关键业务常识

1. **绝版限定商品在一手店里搜不到是正常的**,不是系统故障。F:NEX 限定这类东西
   早就卖完了,animate 现在当然没有。
2. **但一手店不能停止监控**,因为存在**再販(重新发售)**:一手店可能过一段时间
   重新开卖。再販的频率业务方也不清楚,所以策略定为「每天查一次」。
3. 因此一手店的合理预期是:**绝大多数时候 0 结果,偶尔因为再販突然有货。**
   这跟二手市场「随时可能有人挂出来」是完全不同的节奏。

### 当前系统的行为,和要解决的问题

巡检时先用完整商品名搜一次(主查询)。**如果主查询没搜到够格的候选
(`exact` 或 `probable_exact`),系统会自动扩写召回词,再追加最多 2 条更短的查询。**

问题:对一手店来说,主查询返回 0 是常态,于是扩写**每轮必然触发**,等于每轮
问三遍、三遍都没有。这是纯浪费。

**业务方已初步决定:一手店只发主查询,不扩写;二手市场保留扩写;amiami 例外,
按二手方式扩写。**

**你的任务是用数据验证/修正这个决定,并给出每个来源的具体建议。**

## 数据库连接

```bash
ssh root@203.0.113.10 "sudo -u postgres psql -X -d jpgr"
```

PostgreSQL 17,库名 `jpgr`,主要 schema:`radar_core`。

### 相关表(建议先用 `\d radar_core.表名` 确认列名,下面是已核实过的部分)

- `radar_core.watch_bindings`:一个「绑定」= 一个用户盯的商品 × 一个来源。
  关键列:`id`, `source_id`, `source_config_json`, `query`, `profile_name`,
  `monitoring_purpose`, `watch_profile_id`。
  **精确同款绑定的筛选条件:`source_config_json LIKE '%exact_product%'`**(目前 59 个)。
- `radar_core.watch_runs`:每一轮巡检。`id`, `watch_binding_id`, `started_at`,
  `status`(success/failed/skipped), `duration_ms`, `result_count`。
- `radar_core.source_response_captures`:每一次上游请求。`id`, `run_id`,
  `source_id`, `request_url`, `captured_at`。**这是成本的唯一计量口径。**
- `radar_core.watch_run_listing_observations`:每一条被观测到的候选商品。
  `watch_run_id`, `watch_binding_id`, `observed_at`, `match_relation`,
  `decision_status`。**注意这张表没有 `id` 列。**
- `radar_core.listings`:商品主表。`source_id`, `source_item_id`, `last_seen_at`,
  `first_seen_at`, `availability`, `current_price`, `detail_hydrated_at`。

### 三个必须注意的技术细节

1. **所有时间列都是 `text` 类型的 ISO 字符串**,不是 timestamp。
   用 `substr(started_at,1,10)` 取日期,用字符串比较做区间过滤
   (如 `started_at >= '2026-09-01'`),不要 `::timestamp` 转换后再比,没必要。
2. `day` 是保留字,不能直接用作列别名,写 `run_day`。
3. 请求数要 `LEFT JOIN` 或 `LATERAL` 到 captures,因为有的轮次一条请求都没有。

## 数据陷阱(不看这段会得出错误结论)

1. **2026-09-04 之前的请求数不可信。** 那段时间每轮平均请求数是 0.4~0.8,
   说明大多数轮次一条 capture 都没录到——是埋点不全,不是「当时真的便宜」。
   **成本分析只用 09-04 及以后的数据。**
2. **2026-09-05 是异常日。** 那天上线了一个 AI 回填任务,失败轮次 21(平时 3~8),
   观测数 3420(平时 1200 左右)。做平均时单独标出来,不要混进去。
3. **2026-09-07 09:13 UTC 部署了一次改动**(主查询优先 + 详情去重)。
   这一天前后行为不同,要按这个时刻切开,不要按自然日。
4. **绑定数会变**,用户随时加删商品。所有总量指标必须除以当日轮次数或绑定数,
   不要直接比绝对值。
5. **`match_relation='exact'` 在全部历史里恒为 0。** 所有判定实际上靠
   `probable_exact` 撑着。分析时不要假设 `exact` 有数据。

## 要回答的问题

### 第一优先(直接决定策略)

1. **每个来源的产出**:各来源累计 confirmed 多少条?去重后覆盖多少个不同商品?
   用尽可能长的历史窗口(不止 09-04 起),看是否有来源在更早期出过货。
2. **每个来源的性价比**:每个 confirmed 花了多少次上游请求?
   按二手/一手分组后差多少倍?
3. **扩写到底有没有救回来过东西**:能否从数据判断,某一条 confirmed 是由主查询
   命中的,还是由扩写后的追加查询命中的?
   (提示:`source_response_captures.request_url` 里能看到实际发出的查询词;
   主查询用的是完整商品名,扩写用的是更短的词。可以按 URL 里查询词的长度或
   同一轮内的请求先后顺序来区分。如果这个区分做不到,明确说做不到,
   并说明需要补什么埋点才能做到。)
   **这是整个分析里最有价值的一问**——如果扩写从来没救回过任何 confirmed,
   那所有来源都该关掉扩写,不只是一手店。
4. **一手店的再販有没有在数据里出现过**:一手来源的商品,有没有出现过
   「消失一段时间后又重新出现」的情况?间隔多久?
   (看 `listings` 的 `first_seen_at` / `last_seen_at` / `availability` 变化,
   或同一个 `source_item_id` 的重新出现。)
   **这直接决定一手店该多久查一次**——如果再販间隔是以月计的,每天查一次太密了。

### 第二优先(改进业务逻辑)

5. **骏河屋的异常**:它产出了 89 条 `probable_exact`,但 confirmed 是 0。
   它搜得到东西,却从来没有一条被判成同款。是匹配器对它的标题格式不适应,
   还是它卖的确实都是不同款?抽 10~20 条它的 `probable_exact` 候选,
   把商品标题和用户要盯的目标商品名列出来,人工能看出问题在哪。
6. **cospa / charaon / amazon_jp 连 `probable_exact` 都是 0**:
   它们是真的一条相关商品都没搜到,还是搜到了但全被判成 irrelevant?
   如果是前者,这些来源对精确同款可能整体没有价值(注意:一手店的再販逻辑
   仍可能让它们有价值,结合第 4 问一起看)。
7. **来源的必要性**:有没有哪些商品的 confirmed **只**来自某一个来源?
   如果某来源是某些商品的唯一来源,它就不能按平均性价比砍。
8. **按商品品类分**:不同品类(ぬいぐるみ / フィギュア / アクリルスタンド 等)
   在各来源的命中率是否明显不同?如果是,策略应该按「品类 × 来源」而不只是
   「来源」来定。
