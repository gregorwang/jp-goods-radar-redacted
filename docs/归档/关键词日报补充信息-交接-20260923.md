## 1. 做了什么（一句话）

三个关键词日报（爱蜜莉雅 / 路人女主｜加藤惠 / 冰菓·千反田爱瑠全品类）在发信前，把这封信里的商品整批交给
`teika-lookup` 的 `POST /enrich`，每件商品下面加一个信息框：官方定価、AI 测算原价（带 80% 区间）、
**逐条核对过标题的**同款成交、拍卖状态、平台上架/更新时间。只服务关键词日报，不碰其他档案。

## 2. 代码在哪

| 文件 | 作用 |

## 3. 二手行情依赖的是另一条数据链路 ⚠️

**邮件里的定価和二手成交，都不是日淘自己抓的**，是 `jp-market-databricks` 那边的 `price_reference` 库
（同一台 VPS 上的另一个数据库）。它**每天同步一次**，接口返回的 `data_as_of` 就是最后同步时间。

后果：

- **对方同步一断，二手行情就停在旧日期**，而邮件照样发、照样显示成交记录——只是越来越旧。
  目前邮件底部会写「价格参考数据截至 X」，但**代码不会因为数据过期而隐藏行情，也不会报警**。
- 对方接口整个挂掉时，日报会不带信息框照常发（这是设计好的），只在 collector 日志里留一条
  `digest_enrich_failed`，**同样没有报警**。
- 行情的覆盖率和准确性上限由对方决定：我们只能从对方给的每档 `recent_sold`（最多 3 条）里筛，
  对方的「标题相似 / 同作品同品类」两档实测大量配错，已全部弃用。

**这是一个应该单独立项探查的课题**：对方的同步任务怎么跑、断了谁知道、`data_as_of` 超过多久该算故障。
建议的最小改动（未做）：`data_as_of` 超过 48 小时 → 信息框里的成交行不显示，并发一封来源故障提醒。

## 4. 其他隐患（按严重程度）

1. **同款核对的「泛用词表」只按 Re:ゼロ / 冴えカノ 两个作品调过**（`sale-evidence.ts` 的 `WORK_WORDS` / `GENERIC_WORDS`）。
   加新作品时要补作品名别名，否则作品名会被当成身份词，导致该作品几乎所有商品都「全不符」、不显示行情（偏保守，不会配错）。
2. **煤炉拍卖在库里的 `price_basis` 被记成 `listing_price`**（事实只在 `product_facts_json` 里）。
   日报这边已绕过，但**降价提醒等其他用到 `price_basis` 的逻辑可能把拍卖出价当一口价**。未排查。
3. **AI 测算原价在冰菓 / WHITE ALBUM2 / 高木さん 上没验证过**，邮件里会注明，但数字照样显示。
4. **等待时间**：接口冷启动约 25–30 秒，客户端最多等 120 秒 + 502 时隔 60 秒重试一次（最坏约 5 分钟）。
   等待发生在事务外（已登记在 `docs/常用/行情邮件未送达-排查手册-20260922.md` 的成对数值表）。
   以后若把调用挪进 batch 里，必须和 `jpgr_app` 的 3 分钟 `idle_in_transaction_session_timeout` 成对。
5. **payload 变大**：每件商品存整段接口 JSON，一封信最多 100 件。`prepareKeywordDigest` 去重时会读 180 天内所有日报 payload，时间长了会变慢。
6. **完整说明页不在任何 git 仓库里**（`C:\Users\me\gyxl-legal`），机器坏了就没了。建议 `git init` 或并入某个仓库。
7. **本地 `.dev.vars` 的 `RESEND_API_KEY` 是一个名为 test 的 key**，只用于本地预览发信；线上用的是另一份 secret。
8. **声明里「在网页端监控设置中停用」**只对你自己成立；将来给其他用户用，需要退订链接或联系邮箱。
