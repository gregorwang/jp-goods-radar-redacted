### `a635eb8` 的连带处理

- `PRODUCT_TARGET_PROMPT_VERSION` v1 → **v2**。prompt 文本一个字没改，升版**只为作废缓存**：
  `dedupe_key = sha256({kind, model, promptVersion, input})`，v1 下已落库的 5 条任务是解析失败洗出来的
  空结果却挂着 `completed` 状态，不换 key 就会被 `(kind, dedupe_key)` 唯一索引永久复用，解析器修好也读不到新答案。
- `processProductTargetJob` 里，信息量为零的抽取记成 `failed`（`product_target_extraction_empty`）而不是 `completed`。
  `failSingleJob` 置 `next_attempt_at=NULL`，是终态不是重试循环；上游读不到结果就保留启发式指纹，
  符合 `AGENTS.md §4`「抽取失败只能降级，不能拦住建档」。
- `productTargetExtractionIsEmpty()`（`packages/core/src/product-search.ts`）同时守住指纹合并与回填写回。
  **注意它不把「characters 为空」当空** —— 那是抽取器给出的结论（`メダリスト展 アートブック` 确实没有角色），
  必须原样采纳（`docs/常用/同款匹配-验证说明.md §6.3`）；只有所有槽位同时为空才算没抽到。

## 3. `bf4712d` 修的两条规则

### 3.1 粘连词拆解

`canonicalIdentityTokens` 那道过滤用的是**等值**比较，所以尺寸单独成词（`Lサイズ`）时能被认成软属性、
交给 `explicitConflict`；一旦和品类粘成一个词（`A3プリモアート`）等值就比不出来，整块被当成原子身份词。
**同一种缺失，一种写法致命、另一种无害。**

`composedOfKnownParts(token, genericTargetValues)`：能由已知槽位（品类 / 尺寸 / 颜色）拼完且无剩余的词，
不再当原子身份词。品类仍单独在身份词全集里；尺寸与颜色回到自己的冲突检测——**写了 A4 才是反证，
没写只是没写**（`AGENTS.md §4`「没找到证据和找到了反证不能同分」）。差异里新增 `unconfirmed` 字段记录
未证实的软属性。

**用户已就此拍板**（本次会话）：尺寸缺失**不算**缺身份。代价是"卖家没写尺寸的 B2 版可能被当 A3 确认"，
由差异说明里那句「尺寸 A3 商品未注明，请自行核对」承担。改这条前先回看这个决定。

### 3.2 补全值不作负证据

抽取器被允许把作品名补成官方全名（`高木さん` → `からかい上手の高木さん`，`docs §6.1` 明确容许）。
补出来的词随后被当成必须命中的身份词，于是**与目标逐字相同的真品**实测 100 分却判 `uncertain`，
理由写着「缺少『からかい上手の高木さん』」——要求卖家写出用户自己都没写的词。

现在：抽取出的槽位值必须在用户写的 `canonicalName` 里有依据才当身份词；它仍参与加分与召回。
**只对 `aiExtracted` 生效**——启发式指纹的槽位本来就从名字切出来，而建档表单里手填的厂商 / 系列 / 型号
是显式输入，不该被商品名反过来否决。

`PRODUCT_MATCH_VERSION` → `product-match-v8`。

## 5. 欠着的三件

### 5.1 未确认属性提示进邮件（**等用户点头，别擅自做**）

`4f49ede` 让「尺寸 A3 商品未注明，请自行核对」跟着确认理由落进
`watch_run_listing_observations.decision_reason`，所以它只出现在 `/changes` 的巡回明细里。
**邮件里看不到**：`prepareKeywordDigest` 的确认条目来自 `events` join `listings`
（`packages/db/src/repository.ts` ~2930），payload 的 `items` 只有 `category/sourceId/title/url/price/imageUrl`，
根本没有理由字段——理由字段只给「疑似同款」分区用。

要做的话：digest 那条查询去够 `watch_run_listing_observations` 取该 binding+source+item 最近一次的
`decision_reason`（或专门存一列），payload 的 item 加一个 `note`，`packages/email/src/templates.ts`
的 `keywordDigestEmail` 渲染出来。

**为什么要等点头**：那是全系统最要紧的一条 SQL，而且会改变**所有档案**（含关键词档案）的邮件长相，
`docs/常用/同款匹配-验证说明.md §4.2` 那张表要跟着更新。用户在 09-06 会话结束前没有答复这个问题。

### 5.2 B2 · 详情与语义复核名额怎么分

**现状**：`apps/collector/src/index.ts:770` 每来源每轮只取 **4 条**商品详情，`.sort(按 match.score 降序).slice(0, 4)`。
Mercari 搜索接口不返回描述，只有单独抓详情才有。名额按分数发，于是死循环：
**分数低 → 拿不到详情 → 读不到描述里的判别信息 → 分数还是低。**
`m11562761890` 09-06 那轮排第 6，描述里明明写着 `A3サイズプリモアート` 却从没进过比对文本。
语义复核名额是 `PRODUCT_SEARCH_WATCH_AI_REVIEW_LIMIT = 16`（`index.ts:800`），09-05 之前是 8，
那次也是这条商品被挤掉。

**建议改法**：名额不变（4 条 = 4 次 HTTP，零 AI 成本），分配改成「2 条最高分 + 2 条差异最小
（`difference.missing.length` 最少）」。可选：4 提到 6，代价是每来源每轮多两次 HTTP。

**优先级已下调**：`bf4712d` 之后那条 4 万商品光靠标题就确认了，不再依赖描述。这条现在是通用漏报修复，不是阻塞。

**验证**：改完用 `docs §2` 那组 14 条候选核对名额落在谁身上；再用生产库某轮的候选集比对新旧分配差异。

### 5.3 B3 · 首次观察闸门（结构性的洞）

**现状**：`packages/db/src/repository.ts:3032`（`strong_suspects`）与 `:3054`（`all_suspects`）都有这一句：

```sql
AND (COALESCE(o.match_relation,'uncertain')='probable_exact'
 OR NOT EXISTS (SELECT 1 FROM watch_run_listing_observations p
      WHERE … AND p.observed_at < ?))
```

弱证据只在**本轮首次观察**时露出，只有 `probable_exact` 豁免。后果：**判错一次就永久埋葬**。
`m11562761890` 从 08-31 起天天被观察，relation 是 `related`，所以 `confirmed_only` /
`strong_suspects` / `all_suspects` **三档门槛全都看不到它**——用户放宽门槛也救不回来。
09-06 没踩到，只是因为它升到了 `probable_exact`（有豁免）；换个只升到 `uncertain` 的照样被埋。

**建议改法**：把「本轮判定档位相对上一轮发生变化」也列为豁免条件（relation 或 decision_status 变了）。
代价：改匹配器的那一轮会一次性补发一批存量。这通常正是想要的（等于自动补发被埋的），但用户要知情。

**验证**：`docs/常用/同款匹配-验证说明.md §4.1` 那张门槛表要加一行「非首次观察但档位变化」的用例；
§4.5 的音量查询要在改动前后各跑一次，单轮超过 ~15 条说明放得太宽。

## 6. 别踩的坑

1. **不要跑测试套件**（`AGENTS.md §1`）。本次匹配器改动是这样验的：用仓库自带的 esbuild 把
   `packages/core/src/product-search.ts` 打成 ESM 直接调真实函数，跑 `docs §1` 的 10 条兄弟款用例
   和 `docs §6.4` 的表，再灌进生产库某一轮的真实候选标题。**不要手抄一份逻辑镜像去验**，
   那验的是抄写质量。
2. **改匹配行为必须升 `PRODUCT_MATCH_VERSION`**，否则前端不会重算旧记录。
3. **`pnpm verify:sql`** 是部署闸门不是测试，由 `.githooks/pre-push` 在 push 时触发
   （仅当改动涉及 `apps/collector/src`、`apps/web/src`、`packages/db/src`、`postgres/`）。
   5.1 那条改动会踩到它，属正常。
4. **`aiExtracted: true` 会永久关掉回填重试**（`index.ts` ~685 的 `aiExtracted !== true` 守卫）。
   任何往 `productTarget` 写回的新逻辑，先想清楚写坏了怎么解锁——§2 那条 UPDATE 是现成的解锁手段。
5. **push 即部署**：`jp-goods-radar-web` 与 `jp-goods-radar-collector` 都由 Cloudflare Workers Builds
   在 push 时构建。查状态：`gh api repos/gregorwang/jp-goods-radar/commits/<sha>/check-runs`。
6. **Mercari 页面上的相对时间是 `updated` 不是 `created`。** 09-06 排查时验证过：
   `m59761959196` created 2025-07-06 / updated 2026-07-12，页面显示「1か月前」；
   `m11562761890` created 2026-05-01 / updated 2026-06-30，显示「2か月前」。
   卖家改价或改描述都会顶起 `updated`，**页面时间新不代表上架晚**。
   排查漏报时不要拿这个时间反推"商品是不是被隐藏过"。

## 7. 已知的能力边界（不是缺陷，别当 bug 修）

卖家漏写**软属性**（尺寸、颜色）现在能确认；用**简称**写（`冴えカノ`、`育て方`）靠召回词能搜到。
真正无解的只剩一类：**卖家漏写判别符**（`♭`、`深崎暮人イラスト`、`レーシングVer.`）。
「有 ♭」和「没 ♭」是两件不同的商品，卖家不写，标题里就真的没有这个信息，系统不该猜——
猜了就是 09-05 那次把 `Fes. Fine` 判成同款、戴着「确认同款」帽子发信的事故。
正确行为是标成「证据不足」交给用户，而不是丢掉；这个已经有了。
