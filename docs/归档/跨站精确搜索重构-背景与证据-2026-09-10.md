## 1. 用户已经明确的前提

### 1.1 每次搜索都指向一个具体商品

用户提供的是要寻找的具体商品，不是希望浏览某个角色、作品或商品类别。此次修改不增加“宽泛商品搜索”目标，也不把“找某个具体商品”改造成“列出相关商品让用户自己挑”。

用户进一步纠正了前一轮讨论中的方向：

> 不接受把候选膨胀解释成“用户输入信息不足”，也不接受以“让用户先补充信息”作为本轮方案的前置流程。

因此，本轮的固定前提是：

1. 原始商品输入就是系统需要忠实处理的目标定义。
2. 系统解析时丢字段、混淆版本、生成过宽查询，属于系统问题。
3. 候选卖家省略身份信息，属于候选侧证据问题，应该通过详情等手段处理。
4. 系统暂时没有判清，不能反过来证明用户没有说清。
5. 禁止通过扩大“同款”的定义，让更多商品看起来符合目标。

本文中的“缺失”“不确定”，指候选证据缺失、系统处理失败或判定尚未解决，不指责用户输入，也不引出新的用户补全流程。

### 1.2 用户关心结果与体验，不是省模型费用

用户明确表示目前使用的 Lite 模型便宜或免费，不把模型调用费用作为主要约束。

因此不应继续围绕“先用规则省掉尽可能多的 AI 调用”组织整个架构。规则的价值在于可验证的处理；模型调用的价值在于解决语义问题。拆任务、分批、缓存的首要目的应是减少串项、保留证据、缩短有效反馈时间和提高稳定性。

网络请求仍有实际约束：来源响应时间、请求失败、分页、限流、运行时资源和详情适配能力。这些与模型账单不是一回事。

### 1.3 几百、上千候选不是目标

用户提到“一千个”是在质疑不合理的候选膨胀，并非要求召回至少一千个。

本轮要解释并修复的是：为什么搜索一个具体商品，会走到宽泛查询、跨来源堆积、少量复核、大量机械拒绝的链路。不能用“最后再筛一下”掩盖前面的失控，也不能用更小的截断数假装已经解决问题。

### 1.4 保留仓库现有产品原则

依据 [AGENTS.md](../AGENTS.md)：

- 系统产出是值得用户关注的商品。
- 判定状态和通知门槛分开。
- 默认只通知确认同款；放宽门槛属于每个档案的用户设置。
- 缺少证据与明确反证分开；未经复核不能伪装成已经排除。
- 已经有能力判错的商品，不再包装成待用户判断。
- 使用已有的 confirmed / uncertain / rejected 语义，避免另造无人处理的静默业务状态。
- 不运行测试。本轮没有运行测试；后续验收安排遵守同一要求。

### 3.2 如何解释基础设施错误

T1 是“任务 completed、AI 实际失败”的早期当天样本。当前 Workflow 已有精确搜索 AI 未完成就抛错的保护；精确搜索的模型执行也改为由 queue consumer 承担。

T5、T6 后续成功，支持“后续运行已经能完成模型请求”。不能因此保证所有来源、所有时段都不会再失败；也不能继续把 T1～T4 的传输错误归因于小模型智力。

本轮评估模型内容和最终判定机制，主要采用 T5、T6。T1～T4 可用于观察错误传播、候选数量、复用行为。

## 4. 当前实际链路

以下根据当前代码还原，不是拟议架构：

~~~text
具体商品输入
  → 目标字段抽取，同时生成 recallQueries
  → buildProductSearchPlan 生成多个 variants
  → 各来源运行查询，逐轮并入候选
  → 字面匹配评估，按 relation 顺序挑选少量详情
  → 发现 exact / probable_exact 后可停止该来源后续查询
  → 必要时本地历史补回 / 网页补漏
  → 合并所有候选，按 relation 顺序截取最多 24 条 AI 复核
  → 同一次输出 relevance、翻译、分类、品相等字段
  → 解析与缓存，等待选中清单完成
  → 对全部候选形成成员判定
  → 挂到目标商品变体，供结果和其他链路消费
~~~

重要纠正：当前代码已经有顺序执行和 break，不是所有 query 都无条件并行执行。问题不是“补一个 break 就好”，而是查询锚点、停止依据、反馈时机和覆盖语义不可靠。

## 5. 关键发现及证据

### B01：大量返回后，真正复核的只是固定小部分

证据等级：D + C。

T5 为 866 条候选、24 条模型复核；T6 为 577 条候选、24 条模型复核。24 是代码中的 PRODUCT_SEARCH_AI_REVIEW_LIMIT，不是模型已经看过其余条目后挑出的 24 条。

当前排序：

~~~text
exact → probable_exact → bundle → variant → related → uncertain → irrelevant
~~~

AI 选择器只允许 probable_exact / related / uncertain 入选，再沿此顺序截取。uncertain 名义上可以复核，实际上排在全部 related 后面。

| 任务 | probable_exact，已复核 / 总量 | related，已复核 / 总量 | uncertain，已复核 / 总量 |
| --- | ---: | ---: | ---: |
| T5 徽章 | 22 / 22 | 2 / 598 | 0 / 162 |
| T6 画作 | 2 / 2 | 22 / 402 | 0 / 80 |

合计 242 条 uncertain 无 AI 复核。不能断言其中全部是真品，也不能断言全部应抓详情；能确认的是当前分配规则没有让这组候选获得语义复核机会。

### B02：没有复核或模型没判清，被转成拒绝

证据等级：D + C。

T5 有 596 条、T6 有 380 条 related 候选，在成员 evidence 中没有 AI 输出，最终却是 rejected。总计 976 条。

exactProductIdentityDecision 的 related 分支：

~~~text
AI relevant   → uncertain
AI irrelevant → rejected
其他情况      → rejected，workflow_matcher，high
~~~

“其他情况”包括模型 uncertain 和根本没有模型输出。这与“拒绝要有反证”的产品规则冲突。

具体样本：

~~~text
source: yahoo_fleamarket
sourceItemId: z586078304
ai_enrichments.id: 16994
title:
レア　冴えない彼女の育てかた 冴えカノ　タペストリー　C93 コミケ　特典　缶バッジ　ジャンク　加藤恵
AI relevance: uncertain
AI confidence: medium
最终：related / rejected
~~~

AI 理由为：

> 属于同作品周边但夹杂了挂毯等其他物品，且徽章为垃圾品（有凹陷），难以确认具体同款身份

这条还提示翻译和主售对象解析需要分开。本文不认定它是正确同款；事实是“难以确认”被下游变成了“已经拒绝”。

其中一个模型理由是：

> 属于同一系列的情人节双人徽章，包含加藤惠

“包含加藤惠”说明角色相关，不能证明它就是用户指定的那一款。修复方向是恢复对具体目标的严格判断，不是把用户目标改成“这些都可以”。

不能根据此表断言哪一条才是目标，也不能据此给 22 条全部标错。可以确定的是：不同系列及不同销售对象不应仅因共同词命中就获得同一具体款式的确认。

代码中的一个关键条件是：

~~~text
identityProven = missing.length == 0 && conflicting.length == 0
~~~

对 probable_exact + AI relevant，满足该条件即可 confirmed；另一个可确认分支依赖 AI high 和未检测出多件、缺件。

missing/conflicting 来自系统已经构建的字段和词组。如果系统漏保留区分性信息，“所有剩下的词都命中”可能只是在证明同角色同品类。字段覆盖完整不等于具体商品身份成立。

### B05：Schema 与解析器未形成可靠的输出契约

证据等级：C；具体批次后果见 B04，不能把所有 permissive 行为都算成今日事故。

listingEnrichmentProviderRequest 把 Schema 文本拼进 prompt，generationConfig 设置 responseMimeType = application/json，但该请求对象没有设置供应商结构约束 Schema 参数。

这不证明供应商完全不支持结构约束；渠道是否支持和透传，是实施前需要核验的能力。

listingEnrichmentSchema 对许多字段使用 .catch 默认值，且 passthrough。字段错误可能被转换成 uncertain、unknown、空数组或 null，成为调用者眼里的解析成功。

部分批次解析器按 index 建 Map，重复 index 保留首次；无效、缺失和额外条目的处理缺少完整批次异常报告。容错可以回收部分结果，但不能证明全部输出完整可靠。

### B06：目标身份信息、召回提示和模型判据混在一起

证据等级：C + D。

目标抽取器一次拆字段并生成最多四条 recallQueries。prompt 要求保留角色/作品和品类线索，但 T5 保存的查询里有：

~~~text
冴えカノ 加藤恵 缶バッジ
冴えない彼女の育てかた 加藤恵
加藤恵 缶バッジ Fine
冴えカノ 缶バッジ
~~~

第二条丢了商品类型。此前查询命中记录显示，该宽查询关联 254 条候选，其中 240 条只记录到这一条查询命中。该统计针对保存的命中记录，不是“240 条已人工标注无关”。

productSearchRelevanceContext 又把 recallQueries 塞进 includeTerms。程序想表达“用于找到候选”，模型可能收到的是“这些也是目标允许词”。

target.edition 没有作为独立结构化字段列入该函数的 facts；目标描述还会截到 1000 字符。完整商品名仍在输入中，不能说版本信息全部消失；但结构化传递并不完整。

目标抽取 prompt 的 edition 混装作品副标题、活动、版本、作者等不同概念，增加后续比较歧义。

buildProductSearchPlan 先插原始长标题，再加 recallQueries，source_native 最多五个槽位，JAN / 型号查询在更后面添加。前面的条目占满时，标识符查询可能没有槽位。这是代码机制风险，不是本文已验证的某次 JAN 漏搜事故。

### B07：已有 break，但依据可能过早

证据等级：C；T6 运行提供 D 支持。

hasQualifiedExactCandidate 检查 assessProductMatch 得出的 exact / probable_exact，以及要求的 liveVerified 命中。它在全局模型复核之前执行，不以最终成员 confirmed 为条件，也不要求商品在售。

T6 煤炉来源观察到两次详情尝试：

- 一个 Mercari Shops 候选，当前详情路径不支持。
- m88835489224，详情为电影特典色纸，类型不符合画作目标。

随后仍有列表层 probable_exact 候选，来源停止后续查询。“列表预判可能同款”不能证明已经完成具体商品确认。

另有：

- m97171084630：标题含 Fes. Fine A3 プリモアート，预判 uncertain、分数 100，未获详情或 AI 复核。
- m21636898439：标题含相关画作线索，预判 related、分数 52，未获 AI 复核，最终 rejected。

这些不是本文认证的真品；它们说明有明显身份线索也未必能进入证据补全链路。

### B08：候选混合累积，分页又未完整表达覆盖

证据等级：D + C。

| 任务 | 非历史补入候选 | 仅历史补入候选 | 合计 |
| --- | ---: | ---: | ---: |
| T1 毛绒 | 373 | 8 | 381 |
| T5 徽章 | 725 | 141 | 866 |
| T6 画作 | 404 | 173 | 577 |

这些是来源商品记录数，不是具体款式数；按稳定商品 ID 去重，不代表跨来源同款已经完成归并。

部分来源观察：

- T1 煤炉实际返回 117 条，元数据 numFound 为 1094，仍有 next cursor。
- T5 煤炉实际返回 117 条，元数据总量 237，仍有 next cursor。
- T6 煤炉一次实际返回 59 条，元数据 numFound 为 21。不能直接把元数据当可靠唯一总量。
- T5 Yahoo 拍卖合并 271 条，但组级主查询 totalAvailable 为 17。
- T6 Yahoo 拍卖合并 218 条，主查询 totalAvailable 为 8。

组级 totalAvailable / nextCursor 主要继承主查询，不能表达全部查询各自的页数、游标和覆盖。跨查询合并量与某一个查询的 total 混在一起，造成“很多候选但不知道搜完没有”。

不能由此推出统一的“正确候选数”。能推出的是：需要解释每条查询新增了什么、为什么继续和停止，而不是只展示合并数量。

### B09：字段损失和合并方式可能削弱证据

证据等级：原始字段存在为 D；normalizer 与合并机制为 C；具体误判归因为待验证 I。

T6 煤炉列表项不带 description；原始项有类别字段，少部分有品牌字段。当前 normalizeMercariListing 主要保留首图、标题、价格、状态等，未完整映射这些结构。

descriptionExcerpt 在 normalizer 中截到 1500 字符。身份信息若在后半段，摘要可能缺失。

addCandidate 对重复商品遇到 liveVerified 新命中，会直接 current.listing = listing。后到列表对象可能替换已有更丰富对象。本文没有证明今日某件正确商品正是因此丢失详情，实施时需要按事件顺序核对。

“不允许字段退化”也不等于永远使用旧详情。卖家可能改写描述，应同时记录内容版本和新鲜度。

### B10：归并和任务完成需要更准确的语义

证据等级：D + C。

成员表已有 membership_version、valid_from、valid_to、is_current、supersedes_membership_id，适合保留判定修订历史。

身份计算使用规范化目标 hash 和 canonical name 复用。normalizedIdentityTarget 未显式包含 edition，虽然 canonicalName 可能携带它。不能直接认定今日发生 hash 碰撞；需要审查哪些身份维度参与解析与复用。

T5、T6 的任务完成证明选中的 24 条 AI 清单完成，不证明全部候选经过充分复核，也不证明各来源分页覆盖。

下一版不能简单撤掉今天的 AI 失败保护。应同时表达执行是否正常结束、判定是否有有效证据、哪些候选未解决、哪些来源尚未覆盖。

## 7. 对既有讨论的取舍

| 既有意见 | 本轮处理 |
| --- | --- |
| 保留有辨识度锚点，避免整段标题硬搜 | 接受；不硬编码单一角色或商品类别 |
| 列表找候选、详情核实 | 接受；已有充分证据时不机械重复抓详情 |
| 先召回再确认 | 接受；不等于无条件放宽到作品/角色浏览 |
| 加一个 break 就能解决 | 诊断不准确，代码已有 break，需改停止依据和反馈 |
| 固定正常 1～2 次搜索、最多 3 次 | 不作为未经验证的通用目标 |
| 角色品类加减分就能稳定筛掉绝大多数 | 只能辅助路由，不能充当同款裁决器 |
| 搜索命中说明 description 包含目标词 | 可用于补详情排序；不能当成原文存在的证明 |
| 多调用同模型投票可以保证正确 | 不接受，一致回答可能来自同一误解 |
| Schema 可以解决小模型问题 | 只能解决部分结构问题 |
| 用户输入不足，先让用户补全 | 不纳入本轮，与用户明确前提冲突 |
| 历史库可以随便宽搜 | 不接受无边界，仍需约束与覆盖记录 |
| 找到一个同款就停所有来源 | 不作为跨站搜索默认行为 |

## 8. 尚未证明的事项

1. 当前模型在多类具体商品上的准确率和困难负例区分能力。
2. 缩小批次、拆任务后能改善多少，以及改善来自哪个环节。
3. 模型渠道对原生结构约束的支持和透传。
4. 每个来源的搜索范围、分词、AND/OR、类目筛选、总量和游标语义。
5. T5 哪些 confirmed 才是目标；本轮发现混款机制，不能用共同词倒推正确款。
6. T6 未复核候选哪些是真品；需要商品证据，不能以“有希望”当标签。
7. 错误关系是否已经造成具体错误价格分析或邮件；本文没有核实送达事故。

9. 新合并逻辑、详情补充、完整字段保留的实际收益。
