## 项目是干什么的

jpgr，一个日本二手商品监控系统。用户盯的是**一件具体商品**（不是关键词），
比如「ぬいぐるみ エミリア ふわかわロリータぬいぐるみ F:NEX限定」。
系统每隔一段时间拿商品名去 11 个来源搜，判断搜到的是不是同一件东西。

两层判定：
- `match_relation` — 匹配器的机器判定：`exact` / `probable_exact` / `uncertain` / `irrelevant`
- `decision_status` — AI 清洗后的最终裁决：`confirmed` / `rejected` / `uncertain`
  **只有 `confirmed` 会送到用户面前，是唯一的价值指标。**

## 数据库连接

```bash
ssh root@203.0.113.10 "sudo -u postgres psql -X -d jpgr"
```

PostgreSQL 17，库 `jpgr`，主 schema `radar_core`。相关表：

- `watch_bindings` — 一个绑定 = 一件商品 × 一个来源。
  精确同款筛选：`source_config_json LIKE '%exact_product%'`。
  列：`id`, `source_id`, `enabled`, `interval_minutes`, `source_config_json`。
- `watch_runs` — 每轮巡检。`id`, `watch_binding_id`, `started_at`, `status`, `result_count`。
- `source_response_captures` — 每次上游请求，**成本的唯一计量口径**。
  `id`, `run_id`, `source_id`, `request_url`, `payload_kind`, `raw_payload`,
  `payload_bytes`, `captured_at`。
- `watch_run_listing_observations` — 每条被观测到的候选商品。
  `watch_run_id`, `watch_binding_id`, `source_id`, `source_item_id`, `availability`,
  `observed_at`, `match_relation`, `decision_status`。**这张表没有 `id` 列。**
- `listings` — 商品主表。`source_id`, `source_item_id`, `first_seen_at`, `last_seen_at`,
  `availability`, `detail_hydrated_at`。

### 三个技术细节

1. **所有时间列都是 `text` 类型的 ISO 字符串**，不是 timestamp。用
   `substr(started_at,1,10)` 取日期，用字符串比较过滤区间。
2. `day` 是保留字，列别名写 `run_day`。
3. 请求数要 `LEFT JOIN` 或 `LATERAL`，有的轮次一条 capture 都没有。

## 数据陷阱（不看会得出错误结论）

1. **`confirmed` 必须按去重商品数看，不能按观测条数。** 同一件在架商品每天被扫到
   多轮，一周能产生几十条 confirmed 观测，但对用户只是 1 件。
   用 `count(DISTINCT source_item_id) FILTER (WHERE decision_status='confirmed')`。
2. **绑定数和巡检频率这次都变了**，所有总量指标必须除以当日轮次数再比，
   绝对值没有可比性。
3. **`match_relation='exact'` 在全部历史里恒为 0**，所有判定靠 `probable_exact` 撑着。
   不要假设 `exact` 有数据。
4. **2026-09-04 之前的请求数不可信**（埋点不全，每轮平均 0.4~0.8）。
   成本对照只用 09-04 及以后。
5. **2026-09-05 是异常日**（failed 21，observations 3420，平时 1200 左右），单独看。
6. **`yahoo_fleamarket_jp` 与 `yahoo_shopping` 的全部绑定在 2026-09-08 01:07 被健康
   探针自动停用**（`probe_no_go`，「成功率低于 95%」）。如果窗口内它们仍是停用状态，
   这两家的数据会缺失，**不要读成「改动导致产出下降」**。见下面第 8 问。

## 要回答的问题

### 必答（决定留 / 调 / 退）

1. **成本**：每轮上游请求数，按日、按来源。对照 8.88。
   同时算**每天的总请求数**——频率变了，每轮降了但总量可能涨，两个都要看。
2. **产出（唯一的否决项）**：确认同款的**去重商品数**，窗口内 vs 改动前 7 天。
   按天、按来源都要。**掉超过 20% 才是回滚理由**，其余都是调参。
3. **详情去重有没有生效**：
   ```sql
   SELECT count(*) FILTER (WHERE detail_hydrated_at IS NOT NULL) hydrated,
          count(*) FILTER (WHERE detail_hydrated_at IS NULL) never_hydrated,
          min(detail_hydrated_at) oldest, max(detail_hydrated_at) newest
   FROM radar_core.listings;
   ```
   **这次必须 > 0 且持续增长。** 再是 0 说明修复没生效，是 bug，不是数据不够。
   同时算详情请求（URL 含 `items/get`）占总请求的比例，改动前约 1:1，预期砍掉约一半。
4. **煤炉提频到底值不值**：频率翻 4 倍之后，煤炉的确认商品数有没有相应增加？
   算「每件确认商品消耗多少请求」，跟改动前的比。
   **如果提频没带来更多确认商品，就把煤炉退回 720 分钟。**
5. **一手店降频有没有漏东西**：一手店改成两天一次之后，有没有出现过
   「本来该抓到但没抓到」的情况？看 `listings` 里一手来源的商品有没有出现过
   短暂在售又消失。这直接决定 2880 分钟是不是太长。
6. **稳定性**：失败轮次有没有上升。基线是每天 3~8 次。
