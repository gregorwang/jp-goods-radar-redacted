## 1. 不可更改的任务定义

### 1.1 用户输入的是一个具体商品

本计划不建立“用户输入不足 → 要求用户补全 → 才能开始搜索”的流程，不将任务降级为作品、角色或品类浏览，也不把返回几百上千个候选解释成用户没有说清。

系统需要做到：

~~~text
用户指定的具体商品
  → 忠实保留该商品身份
  → 生成适合卖家表达和来源语法的查询
  → 找到候选中的那件商品
  → 对其他商品给出有依据的排除
  → 返回可行动、可追溯的同款结果
~~~

如果字段抽取丢失原始商品名中的内容，这是内部处理失败，应自动修复该步骤。候选卖家没写版本，则补候选详情。这两种问题都不能转化为要求用户重新描述商品。

### 1.2 优先级

1. 确认同款的正确性，避免把版本、系列、图案、销售对象不同的商品发给用户。
2. 找回本可通过详情识别的正确商品，避免标题缩写、无 AI 复核造成机械漏判。
3. 控制无效召回和有效结果等待时间。
4. 让处理失败、证据不足、覆盖不足具有准确含义。
5. 保留可重算、可审计的数据。

模型费用不是本轮优化目标。网络请求和运行时仍需边界，但边界不能通过伪造拒绝或完成来实现。

### 1.3 不能采用的“捷径”

- 把 24 改成 100 或 1000 就宣称解决了问题。
- 只增加 prompt 长度或重复强调“必须正确”。
- 用模型 high confidence 代替证据。
- 用两个相同模型回答一致代替验证。
- 用更小分页上限让候选数好看。
- 删除所有 related / uncertain，以提高展示精度。
- 将 uncertain 全部发给用户，以提高表面召回率。
- 将同角色、同品类、不同系列都视为具体同款。
- 找到一个列表层 probable_exact 就停止。
- 原地清空历史表来消除旧错误。

## 3. 拟议链路

~~~mermaid
flowchart TD
  A[用户指定的具体商品] --> B[冻结原始目标与受验证身份字段]
  B --> C[按来源生成有约束的查询]
  C --> D[执行当前查询页并记录覆盖]
  D --> E[合并来源证据并去重]
  E --> F{证据足够处理哪一步}
  F -->|可靠冲突| G[有反证的拒绝]
  F -->|可靠商品标识与销售对象一致| H[确认同款]
  F -->|需要语义判断| I[短任务模型判断]
  F -->|需要详情证据| J[补详情或已有快照]
  I --> K[结构、引用、业务一致性校验]
  K -->|仍需事实| J
  J --> E
  K -->|可形成结论| L[统一裁决]
  H --> L
  G --> L
  L --> M{该来源目标与覆盖是否满足}
  M -->|继续当前页或换受约束查询| D
  M -->|当前轮结束| N[判定、覆盖和执行结果分别落库]
  N --> O[展示和每档案通知门槛]
~~~

图中的循环不意味着无限运行。每个动作必须受来源速率、运行期限、重试和可恢复任务预算约束。模型只能提出候选判断或证据需求，不能直接扩张网络请求或修改目标。

和现有链路最主要的差别：

1. 详情和语义反馈进入查询控制环，不再等所有来源搜索完才做一次固定 Top 24。
2. 最终成员判定只接受经过校验的证据与模型表态，不复用字面 relation 的早期结论当最终真值。
3. 发现候选、完成裁决、覆盖来源是三件事。

## 4. M1：目标保真，而不是重新定义用户目标

### 4.1 原始输入不可被派生字段覆盖

保留完整 rawInput、已有目标档案中的原始身份字段和来源引用。normalize、抽取和别名展开均产生派生对象，不原地改写原始目标。

拟议逻辑对象：

~~~ts
type TargetIdentity = {
  targetId: string;
  revision: string;
  rawInput: string;
  canonicalName: string;
  identityFacts: TargetFact[];
  identityAliases: ApprovedAlias[];
  recallAliases: ApprovedAlias[];
  unresolvedExtractionSpans: SourceSpan[];
  extractionStatus: "valid" | "retry_required" | "failed";
};
~~~

这里的 extractionStatus 是内部处理状态，不是“用户输入质量”档位。unresolvedExtractionSpans 保存原文里系统尚未正确归类的内容，确保这些内容不会被静默丢弃。它们仍可随完整原文进入受约束判断，不自动变成搜索放宽理由。

### 4.2 字段拆分的最低边界

| 逻辑字段 | 含义 | 不能混入 |
| --- | --- | --- |
| work | 作品、季数或剧场版等有类型的名称 | 活动发行版 |
| character | 角色、人物 | 作者、品牌 |
| productType | 商品类别原词及受验证等价词 | 更宽类别的同款等价 |
| series / releaseEvent | 商品系列、发行活动 | 泛化的“限定”一词 |
| variant / artwork | 具体版本、画面、服装等区分信息 | 单纯作者姓名 |
| creatorMention | 原文作者/绘师线索 | 自行扩写的“某某イラスト” |
| identifier | JAN、型号、来源目录号及其作用范围 | 卖家库存号、其他商品代码 |
| size / color | 商品规格及对象类型 | 包装尺寸冒充画面尺寸 |
| manufacturer | 原文或可信来源标注的厂商 | 模型记忆推断 |
| saleUnit | 用户原始目标中明确的单品、套装、BOX 等 | 卖家品相描述 |

不要求第一版建立覆盖所有周边的本体。要求是同一字段有稳定语义，未知归类保留原文，不强塞进 edition。

### 4.3 抽取与规范化分开

每个字段保存：

~~~ts
type TargetFact = {
  field: string;
  rawValue: string;
  normalizedValue?: string;
  evidence: SourceSpan;
  normalizationRule?: { id: string; version: string };
};
~~~

例如原文“深崎暮人”可原样提取。若模型写成“深崎暮人イラスト”，增加的部分不属于原文，应拒收该派生值或保留为未采纳提议，不能作为新目标身份。

平假名、片假名、英文品牌、IP 简称的转换需要可追溯映射。全局字符串相似不能自动建立“Fine = Fes. Fine”之类版本等价。

### 4.4 两类别名必须分开

- identityAliases：允许用于证明同一概念的等价表达。
- recallAliases：允许用来找到候选的搜索表达；可能更宽。

例：“プリモアート / PrimoArt”可在核验映射后进入同款等价；“複製原画”可作为搜索候选类别，不自动等价于所有 PrimoArt。

查询组合、词序、搜索次数不参与商品身份 hash。改变查询策略不能创建另一件商品。

### 4.5 目标抽取失败的处理

1. 原始输入保持不变。
2. 返回具体失败路径，例如 creator 字段无引用、版本词未被保留。
3. 对失败字段或失败抽取任务作有限重试。
4. 未能修复时可使用完整原始商品名及已验证字段进行受约束处理，不将低质量结构化结果伪装成成功。
5. 若必要内部步骤不可用，明确记录技术失败；不得自动切换到作品级宽搜。

本轮没有“要求用户先补资料”这一阶段。

## 5. M2：让小模型成为受约束的组件

### 5.1 拆成三种职责

| 任务 | 输入 | 输出 | 何时执行 |
| --- | --- | --- | --- |
| 身份判断 | 冻结目标、候选身份相关原文 | 同款/冲突/未决、引用、缺少的候选证据 | 规则不能可靠裁决时 |
| 定向事实抽取 | 指定候选快照、需要的字段 | 带原文依据的字段 | 解决版本、尺寸、主售对象等疑问时 |
| 展示处理 | 已验证事实、原始标题 | 翻译、摘要、展示标签 | 有展示价值的结果；不阻塞身份裁决 |

不机械要求每件商品都跑三次。已经有可靠冲突的记录无需生成翻译和完整品相清洗；需要确认版本的候选先解决版本，不先填二十个无关字段。

### 5.2 身份判断不再使用宽泛 relevance 含义

新契约采用明确名字，示意：

~~~ts
type IdentityAssessment = {
  candidateKey: string;
  assessment: "same_product" | "different_product" | "insufficient_evidence";
  matchedFacts: FactComparison[];
  conflicts: FactComparison[];
  missingEvidence: EvidenceNeed[];
  saleRelation:
    | "target_unit"
    | "multiple_target_units"
    | "contains_target"
    | "component_only"
    | "random_assortment"
    | "different_unit"
    | "unknown";
  reasonCode: string;
};
~~~

这是逻辑契约，具体枚举和字段名需结合现有 validation/domain 类型落地，不直接把示意接口粘成实现。

若旧消费者仍需 relevance，通过显式兼容层投影；新契约的 same_product 不能被解释成“同作品相关”。模型原始表态保留，下游校验否决也单独记录。

### 5.3 模型最小输入

必须提供：

- 目标原始商品名和受验证的身份字段。
- 本次有关的用户原始限制、被批准的等价表达。
- 稳定 candidateKey 和候选来源快照 ID。
- 候选标题；已有详情时提供身份相关原文片段。
- 可信类别、商品代码、规格及其来源。

不整包提供：

- recallQueries 作为允许匹配条件。
- 无解释的评分、价格与销量，用来暗示“这大概就是目标”。
- 另一件商品的模型输出、其他候选的缓存事实。
- 与身份无关的大段品相、翻译和行情上下文。

查询命中信息保留在调度侧。除非需要明确解释来源搜索语义，否则不传入最终身份判断；即使传入也只能标注为检索来源，不能当成商品原文证据。

### 5.4 结构契约

模型渠道支持原生结构约束时，使用实际支持的参数；实施前核验当前网关和模型路径，不凭模型名猜测。若渠道不支持，保留明确兼容路径和本地严格校验，不声称“已经启用 Structured Output”。

身份结果不再用大量 .catch 把无效字段洗成合法业务结论：

- 缺 assessment 是 contract_error，不是自动 insufficient_evidence。
- 非法枚举是 contract_error，不是默认 unknown 后算成功。
- 缺 candidateKey、未知 ID、重复 ID 都要报告。
- 可选字段合法为空与字段类型错误分开。
- 展示字段允许降级，但不得污染身份字段。

### 5.5 批次对应关系

使用稳定 candidateKey，不仅靠数组 index。每批冻结 expectedCandidateKeys 和对应 snapshotHash：

~~~text
收到 ID 集合与预期集合比较
  → 缺失 ID：该条待重试
  → 重复 ID：该 ID 的结果全部暂不采纳，不选 first/last
  → 额外 ID：不入库，记录协议错误
  → 输入快照不匹配：旧结果，不应用到当前候选
  → 其余逐条做结构和证据校验
~~~

如果整个 JSON 无法解析，整批记录为结构失败，不能用正则拼凑出可确认结果。若外层合法、部分条目错误，可以回收其他独立且有效条目，但批次状态仍是 partial。

index 可为兼容旧协议保留，最终绑定以稳定 ID + 快照版本为准。

### 5.6 证据校验分四层

| 层 | 检查内容 | 失败动作 |
| --- | --- | --- |
| 结构 | 类型、枚举、集合完整性、版本 | 拒收有问题的结果，有限重试 |
| 引用 | 来源、字段、快照、原文位置一致 | 无效字段不成为事实 |
| 语义支持 | 引用是否支持所声称字段、对象和否定关系 | 可确定的矛盾由程序拦截，歧义进入定向复核 |
| 业务一致性 | 版本冲突却 same_product、BOX 当单枚等 | 暂不形成确认，返回具体原因 |

引用可以用 field + quote + occurrence 或片段 ID 表达，由程序解析到位置。不要要求小模型计算容易出错的字符偏移后不经校验直接信任。

“引用存在”不是“引用支持”。程序可以校验单位换算、ID、显式否定和部分类型映射；不能宣称它可以证明所有日文语义。复杂歧义交给定向语义复核，仍无证据则未决。

### 5.7 模型表态如何参与决策

模型不是只生成解释文字：通过校验的不同商品结论必须参与拒绝，通过校验的同款结论必须有机会把早期低分候选提升为确认。

模型也不是无条件裁决者：无效引用、原文不存在的字段、与已知硬证据矛盾的表态不能直接入最终决策。

不设置“模型永远只作参考、规则始终说了算”的短路。应保存：

~~~text
原始模型结论
契约/证据校验结果
有效语义判断
最终业务决策
二者不同的明确原因
~~~

### 5.8 翻译、分类、官方属性

- 日文原名始终可用。翻译失败使用原名，不回滚正确身份判断。
- “額”的解释、方向、サイズ、单品/BOX 等术语有独立词义约束，避免自由摘要覆盖事实。
- 韩文等异常语言混入展示字段，触发该字段修复，不重跑整批身份判断。
- 卖家声称正品、系列官方授权、该实物真伪是不同字段。厂商名出现不能证明该件实物官方正品。
- 类别作为受验证辅助事实，不让 marketCategory 的宽泛枚举替代具体 productType。
- 所有外部知识补充与来源抽取分别保存，第一阶段不依赖模型记忆补厂商或 JAN。

### 5.9 重试和升级

| 失败 | 优先处理 | 禁止处理 |
| --- | --- | --- |
| 401 / 地区限制 | 技术错误分类，检查路由与已有失败保护 | 改 prompt 连续重试 |
| 限流 / 临时错误 | 现有队列退避和运行期限 | 无界并发 |
| JSON 损坏 | 缩小批次或缩短任务输出，有限重试 | 把 repaired JSON 默认算正确 |
| 漏项 / 重复项 | 仅重做受影响 ID | 每次重做全部已成功商品 |
| 抽取无引用 | 针对失败字段修复 | 用默认值掩盖成功 |
| 语义矛盾 | 补事实、定向复核 | 相同输入重复投票 |
| 候选证据不足 | 获取详情/明确位置的原文 | 凭空填版本 |
| 展示错误 | 字段级修复，保留原文 | 让翻译阻断同款结果 |

建议初始小批配置为列表短判断最多 8 条、详情判断最多 2 条；这是待核查的起始参数，不是模型能力事实。组批还需按输入/预期输出长度和任务形状约束，单条很长则独立处理。

同一契约或字段错误建议最多两次修复尝试；之后保留具体失败，避免无限生成。传输重试沿用现有队列策略并计入期限，不能再叠一套隐藏无限重试。

更强模型可以作为未来可选困难复核后端，但本计划不把“更换付费模型”设为成功前提，不自动引入新供应商或新付费依赖。

## 6. M3：查询规划与自适应覆盖

### 6.1 生成的是可选择动作，不是必须全部执行的清单

~~~ts
type PlannedQuery = {
  queryId: string;
  sourceId: string;
  lane: "source_native" | "history" | "web";
  text: string;
  anchorIds: string[];
  purpose: "identifier" | "precise" | "alias" | "bounded_fallback";
  preconditions: string[];
  parentQueryId?: string;
  plannerVersion: string;
};
~~~

query 由已验证锚点和来源模板构造。模型可提出别名或查询候选，但程序只有在锚点来源和语法校验通过后才执行。

### 6.2 查询守门规则

普通周边查询保留主体锚点与商品类型，必要时加入版本、系列、尺寸等区分信息。禁止普通路径自动退化到“作品 + 角色”。

不能把“每条都必须含品类”写成不分情况的死规则：

- 可靠的完整商品代码可以独立成为标识符查询。
- “角色 + 已验证的具体版本专有词”可用于补漏，前提是被明确归类为受约束策略，并追踪结果。
- 作者、作品、普通尺寸、限定等宽词不能单独被模型评分成“高辨识度”后放行。
- query 无效时修生成器，不自动删除锚点直到能搜出东西。

字符归一化、假名/英文等价、来源语法由程序控制。召回别名可以比身份等价宽，但不能越过允许的查询范围。

### 6.3 主查询排序

先构造所有合法候选，再排序和分配槽位，解决当前原始标题 + AI 四条先占满、后面标识符挤不进去的问题。

优先依据：

1. 来源已验证可搜索的可靠商品标识符。
2. 具体类型与版本/系列组合。
3. 在该来源历史运行中有有效同款证据的别名组合。
4. 受约束的其他表达。
5. 原始完整标题作为可选查询；不固定永远第一，也不永远禁用。

这不是要求所有商品都用“角色 + 品类”第一枪。毛绒、徽章、复制画、型号商品的区分信息不同。不得硬编码加藤惠案例的词序或分值。

**2026-09-12 修订：版本词升为独立查询轴。**

原实现只在「主体 + 版本 + 品类」三连里使用版本词，于是 `角色 + 版本`、`品类 + 版本`
这两种最窄的组合根本不会被生成；而 `角色 + 品类` 被归在受约束档（第 4 位），5 个槽位
从来轮不到它。结果是发出去的五枪全部是「往主体上不断加属性」的长查询——越长越像官方
标题，越不像卖家会写的标题。

改后的排序依据改成**判别力角色**，不是词的数量：

1. 可靠商品标识符（JAN / 型号）
2. 版本轴：`主体 + 版本`、`品类 + 版本`、`主体 + 版本 + 品类`
3. `主体 + 品类`
4. 已验证的召回别名
5. 原始完整标题（保留一枪，不再是主力）
6. 厂商 / 系列 / 尺寸等「再加一个属性」的组合

这里排的是**要素角色**，不是某个商品的词。版本轴对型号商品走的是型号，对毛绒、徽章走
的是各自的限定标记；没有版本词的商品自动跳过该轴，不会被凑出一条查询。§6.2 的守门
规则同步放宽一处：查询保留了目标自己声明过的版本词或型号时，只需再保留一个身份要素
（主体或品类）即可放行——`品类 + 版本` 比 `作品 + 角色` 窄得多，不是整站浏览。放行
依据仍然只有程序可核验的事实（这个词在不在目标身份里、在不在查询里），不是「辨识度
高不高」的模型评分。

版本词用作查询串时去掉末尾的 `Ver.` / `バージョン`：`バースデーデート` 严格包含
`バースデーデートVer.`，召回更宽且不丢命中。判定侧仍用完整版本词。

**2026-09-12 第二次修订：一次真实搜索暴露的三件事。**

实搜 `冴えない彼女の育てかた Fine ふわぷち Mぬいぐるみ “加藤恵” 私服Ver.`，
Mercari 463 候选 / 骏河屋 65 候选，确认同款 1 条。逐条追下来是三个独立缺陷：

1. **表记噪音被当成身份。** 输入里 `“加藤恵”` 带一对全角引号，紧凑化函数没有去掉
   引号，于是「目标名里有 `“加藤恵”`，商品标题里没有」→ 记一条缺失 → 得分 100、
   作品/品类/尺寸/版本/角色全部命中的逐字相同标题被判成「待定·需要详情」。同样的
   标题有十几条。紧凑化改为去掉全部标点、括号、引号与记号；发出去的查询串同样清洗
   （平台不保证这些字符有检索含义，Mercari 只提供正式的「除外キーワード」字段）。

2. **版本轴取错了词。** 抽取结果是 `edition: ["Fine", "ふわぷち", "M", "私服Ver."]`
   ——`Fine` 属于作品名，`ふわぷち` 是产品线（series 里已有），`M` 是尺寸（size 里
   已有），真正的版本词 `私服Ver.` 排在第四。取 `edition[0]` 的结果是 `Fine` 上了
   最高权重，连发两枪整站浏览式查询。改为：先剔掉已被其他字段认领的词，再优先取带
   明确版本标记（`Ver.`/`バージョン`/`限定`/`版`）的那一个。

3. **整页照单全收。** 平台搜索本身按相关度排序，一页 100~120 条。旧实现把整页全部
   收成候选（五枪 × 一整页 = 463 条），再用有限的详情预算去里面捞。改为每条查询只
   收上游名次前 40 条；挑哪几条抓详情时，上游名次参与排序（同等待解决问题下名次靠
   前的先问）。名次不是同款证据——它还受价格、新旧、卖家影响——所以它只决定「收哪些、
   先问哪一条」，不参与判定。

同时把抽取器给的召回表达（`冴えカノ 加藤恵 ぬいぐるみ`）从兜底档提到具体查询档：
它专治卖家缩写，过去排在同档长查询之后，5 个槽位轮不到。

**2026-09-12 第三次修订：品类写了别的 = 冲突，不是缺失。**

改完前两轮后重搜同一商品：候选 528 → 63，确认 1 → 3，三条确认全部正确。但 12 次
详情请求里有 10 次花在 `フィギュア`、`ラバスト`、`アクリルスタンド`、`缶バッジ` 上。

原因是判定把两种情况混成了一种：

```
标题里没写品类        → 卖家可能偷懒        → 值得读正文
标题里写了另一个品类  → 这是另一样东西      → 应该直接排除
```

旧实现两种都记成「缺失身份要素」，于是有限的详情预算被花在明摆着不是同款的商品上。
现在标题里声明了另一个已知品类词时记为 `品类冲突：<词>`，按硬冲突处理（程序可核查
的反证，落到 `deterministic_conflict`，不再请求详情）。

三道约束防止把「卖家换了个说法」误判成冲突：目标自己的品类必须是已知品类词；商品
文本里只要出现过目标品类（正文、分类都算）就不算冲突；只看标题，正文提一句「他にも
アクリルスタンドあります」不是这条挂牌在卖的东西。

实测 8 条明显异类被拦下，两条应确认的仍然确认，同品类的兄弟款（`制服Ver.`）仍然是
待定而不是被排除，标题很短的卖家（`加藤恵 ふわぷち 私服`）仍然拿得到详情请求。
标题里只写品牌线而不写品类的（`Luminasta`）仍然走详情——那正是详情该花的地方。

### 6.4 每次只决定下一步

每个来源先执行一个合法查询页，观察实际返回，再选择：

| 观察 | 下一步 |
| --- | --- |
| 命中有希望、缺候选版本 | 优先补详情，而不是立即增加宽查询 |
| 当前页出现大量可证实类型/版本冲突 | 收紧锚点或换经过验证的别名组合 |
| 返回 0，但查询和来源正常 | 换另一个合法表达，不能直接判全站无货 |
| 高质量查询仍有下一页 | 根据有效命中和新增结果继续翻页 |
| 主要重复旧候选 | 降低重复查询优先级，按覆盖和新增证据判断停止 |
| 来源出错或游标异常 | 标记覆盖未知/部分，不算结果为 0 |
| 确认同款但全部已售 | 可证明查询有价值；不能说明当前在售目标已经满足 |
| 单一来源有确认结果 | 不自动取消其他已选择来源 |
| 有列表层 probable_exact | 只说明值得核验，不触发最终成功停止 |

下一步依赖经过验证的局部判定。网络搜索不等待无关展示字段；也不等待所有来源凑齐再统一启动身份复核。

### 6.5 控制候选膨胀的指标

每查询记录：

~~~text
rawReturned
uniqueNewListings
duplicateListings
newEvidenceForExistingListings
hardConflictCount
confirmedCount
unresolvedCount
pendingAssessmentCount
reportedTotal
reportedTotalReliability
nextCursor
pagesFetched
latency
searchRequestCount
detailRequestCount
stopReason
~~~

不得把未经判断的记录算成“无关”，据此停止。新增候选少不一定没有价值：旧候选可能获得新详情或新的在售状态，应单独记录新增证据。

不把“最终候选必须少于 20 / 50”当准确性规则。要求是大集合能解释来自哪些合法查询，宽查询扩张可被发现和纠正，已抓取候选不被无理由丢弃。

### 6.6 查询覆盖是逐查询账本

~~~ts
type QueryCoverage = {
  queryId: string;
  requestFingerprint: string;
  pages: PageObservation[];
  nextCursor: string | null;
  stopReason:
    | "exhausted"
    | "refined"
    | "duplicate_yield"
    | "source_error"
    | "deadline"
    | "budget"
    | "objective_met";
  coverage: "exhausted" | "partial" | "unknown";
};
~~~

游标绑定 query + source + filters + sort + lane，不跨查询复用。source total 不准确时保留原值和不可靠标记，不推导“还剩几件”。

exhausted 只表示该查询在当时返回的分页已耗尽，不表示整个市场已搜尽。多个合法查询结束也不能保证绝对全召回。

### 6.7 请求预算

明确区分：

- 来源限流和并发保护。
- 单个 HTTP 超时。
- 本轮用户可等待期限。
- 查询页和详情动作预算。
- 模型契约修复次数。

首版保留来源已有可验证的安全限制，先改变预算分配方式和停止理由。模型复核的 24 条总上限改为任务期限内的分批队列；不能暗中取消所有资源边界。

细节起始方案：同一来源详情先串行，跨来源并发由现有路由限制约束；长文模型批次单独组批。最终数值在实施阶段结合已有配置确定，必须落在版本化配置中，不能散落魔法数字。

达到预算后，未解决候选仍未解决，不作拒绝。完成多少、缺哪一段覆盖要准确展示。

### 6.8 历史和网页补漏

历史 PostgreSQL 查询和实时来源网络查询使用不同 lane、预算和覆盖记录；当前生产是 PostgreSQL，不将 Databricks 当作本轮运行依赖。

历史搜索也要保留身份锚点、使用索引并限制返回窗口。查询多次不是免费无限扫描，不能“本地随便炸”。

历史身份事实可复用；历史在售状态不可直接当本轮可购买。用于实时结果时需重新验证相应状态。

网页补漏作为已有能力的受约束 fallback：限定来源允许的详情页域名和路径，保存搜索摘要来源，打开原页面后再形成商品证据。搜索摘要不能证明完整详情或当前在售。

**2026-09-12 修订：手动精确搜索默认开启网页补漏。**

搜索引擎抓过的商品正文（含已售、旧商品）常比平台站内搜索更容易翻出标题写得不全的
商品，这正是站内召回最薄弱的一段。默认开启后仍受两道约束不变：只有站内没有找到合格
同款时才发起，且受 `OPENWEBNINJA_RUNTIME_BUDGET` 月度预算（默认 80 次，含 20 次
应急储备）约束。

**巡检（cron / 队列）仍然默认关闭**，原因是成本而不是能力：巡检是持续扇出的，按当前
预算会在很短时间内把额度耗尽，并连带让手动搜索一起失败。要在巡检里也开，先调高该预算。

Mercari Shops 与个人商品页等能力差异显式进入来源能力表。不支持详情时不消耗一连串相同失败请求，也不把 unsupported 当作不是同款。

## 7. M4：候选证据与详情调度

### 7.1 先保存观察，再形成合并视图

~~~ts
type SourceObservation = {
  sourceId: string;
  sourceItemId: string;
  snapshotId: string;
  contentHash: string;
  observedAt: string;
  origin: "search" | "detail" | "history" | "web";
  queryId?: string;
  rawCaptureId?: string;
  fields: Record<string, unknown>;
  fieldProvenance: Record<string, EvidenceRef>;
};
~~~

优先复用现有响应 capture 和 analytics observation 结构，避免创建第二套原始数据仓库。逻辑对象是否独立落表，由读取需求和体量决定。

### 7.2 合并规则

- 同来源商品 ID 用于挂牌去重，不代表跨来源实体去重。
- 重复搜索命中追加 query provenance，不覆盖已有详情。
- 新价格、新状态按实际观测时间更新；历史状态不能盖过新状态。
- 详情缺字段与详情显式删掉字段要分开。
- 较新的列表标题若与旧详情内容冲突，标记需要刷新，不能拼成看似一致的假对象。
- 每个被模型使用的字段都能追到同一候选的具体快照。
- 不能把 A 商品详情与 B 商品标题拼进一次判断。

normalizer 应保留来源已经提供且含义可映射的类别、品牌、代码、规格和图片引用。无语义的类别 ID 可以保存但不冒充已解释的品类。

### 7.3 详情按“能解决什么”分配

不再把 relation 固定顺序当所有阶段的排序。不同动作有不同优先级：

1. 高区分查询召回、标题简略，需要正文确认版本。
2. 有身份线索、只缺一个关键候选字段。
3. 多字段接近但存在需要核实的矛盾。
4. 在售、可能短时间售出的高价值候选。
5. 历史价格参考所需但实时性不高的候选。

可购买性影响动作优先级，不改变同款事实。列表信息足够的候选可以直接判断；明显硬冲突可直接拒绝。

同源大量重复或同一系列噪声不能永久占满全部动作；调度应保留来源和证据缺口的覆盖，给等待候选 aging 优先级，避免 uncertain 长期饿死。

### 7.4 详情截取

保留原始完整详情引用。给模型的是有片段 ID 的身份相关原文：

- 商品标题和正文里的正式名称。
- 系列、版本、尺寸、商品代码。
- 主售内容与“不包含”“仅盒”“特典”等上下文。
- 与同款判断有关的相邻否定语句。

不能仅截前 1500 字符；也不能只提取命中词而切掉“不”。若局部片段仍不能解释对象，获取更完整上下文，必要时单条处理。

不让一次模型生成的摘要成为下一次唯一事实来源。摘要是派生内容，原文引用必须仍可读。

### 7.5 图片的边界

现有标题和详情链路先做对。保留多图引用和来源，便于之后核实同画面。

已有可用视觉能力时，可以对明确缺“图案版本”的候选进行定向辅助；不在第一阶段新建图像向量库或把视觉模型作为必需基础设施。外观相似不能证明型号、真伪或隐藏配件一致。

不能因为没有视觉能力就把文本无法识别的商品硬判同款；也不能虚报已经检查了图片。

## 8. M5：统一裁决，防止又松又漏

### 8.1 分开四个问题

| 维度 | 回答什么 | 示例 |
| --- | --- | --- |
| identityAssessment | 候选所指商品是不是目标身份 | 同一画面、同一发行款 |
| saleRelation | 挂牌实际卖的对象与目标的关系 | 单件、同款多件、含目标套装、随机 BOX |
| eligibility | 是否满足该档案购买条件 | 在售、价格、品相、允许缺件 |
| delivery | 值不值得现在打扰用户 | 按档案阈值决定是否通知 |

同一物品有折痕，不一定改变商品身份。只有盒子、配件或随机 BOX，不等同于用户要的完整单品。这些边界必须在结构中表达，不能靠 includedItems.length 大于一就全拒，也不能把所有套装问题都说成品相。

### 8.2 确认依据

确认具体同款有两条可接受路径：

**路径 A：可靠的商品标识。**

目标与候选的标识符同类型、同作用范围、来源可追溯，并确认它标识主售商品而非引用其他商品、BOX、包装、卖家 SKU 或推荐项；同时没有可信的身份冲突。

JAN 命中并非无条件通行证。整箱 JAN 和单枚对象可能不同；描述可能提到另一个商品代码；来源也可能错误填写。

**路径 B：足以区分具体款式的语义证据。**

由模型对目标与候选的真实原文作同款判断，引用能够连接具体版本、系列、图案或其他关键组合；通过契约与一致性校验，且没有未解决的身份冲突。

不机械要求每条候选写齐目标所有词。卖家缩写可以由其他强证据弥补。也不能仅因缺失列表为空就认定完成身份证明。

“足以区分”不是一组通用加分常量。不同商品类型使用不同证据维度；同作者同尺寸可能不足以区分复制画，同角色同类型可能不足以区分毛绒或徽章。

### 8.3 最终决策矩阵

以下 finalDecision 复用已有 confirmed / uncertain / rejected。辅助 reasonCode、processingStatus 是解释和处理状态，不是新的隐藏业务档位。

| 当前有效证据 | 模型情况 | finalDecision | 必须保留 |
| --- | --- | --- | --- |
| 可靠同范围标识、销售对象匹配、无冲突 | 不需要 | confirmed | 标识证据与校验结果 |
| 具体版本/画面等支持同款，无冲突 | 有效 same_product | confirmed | 关键引用、决策规则版本 |
| 早期 related / uncertain，但详情已证明同款 | 有效 same_product | confirmed | 提升依据；早期分数不再阻止 |
| 明确不同角色、型号、版本、主售类型 | 不需要，或有效 different_product | rejected | 具体反证，含来源 |
| 模型自称 different_product，但引用无效或只说缺字段 | 无效 | uncertain | 校验失败与待补证据 |
| 标题省略身份信息，尚未读详情 | 未执行 | uncertain | 具体缺口和待处理动作 |
| 模型明确 insufficient_evidence | 有效未决 | uncertain | 缺哪项候选证据 |
| 模型请求失败、漏项、JSON 错误 | 无有效表态 | uncertain，且处理失败 | 技术错误；不得默认 high |
| 新旧快照相互冲突 | 任意 | uncertain，先刷新/消歧 | 冲突双方来源与时间 |
| 与目标具体版本不同，只是同系列 | relevant 式泛化无效 | rejected（有反证时） | 版本差异 |
| 仅能确认包含目标，主售为混合套装 | 有效 contains_target | 不进入 exact confirmed 投影 | 包含关系和购买政策单独表达 |

最后一行不能被草率压缩成“只要有套装字样就拒绝”。先识别销售关系；精确单品入口不将 contains_target 当确认单品。若现有档案明确允许含目标组合，使用单独购买资格分支展示/送达，并清楚标明套装；不能污染单品归并和单品价格统计。

映射到既有三态时，对于已经明确不符合默认目标销售单位的记录，可以以 sale-unit mismatch 作为明确拒绝理由；对于销售内容尚未判清的记录只能 uncertain。不得把已确认包含关系的事实删除。

### 8.4 拒绝与降档理由

拒绝理由应是可核查差异：

~~~text
目标为バースデーデート版；候选正文明确为別イベント版。
目标是画作；主售内容明确为电影特典色纸。
目标单枚；挂牌明确为随机 BOX，无法确认提供目标单枚。
~~~

未决理由应指向具体缺口：

~~~text
标题能连接角色和品类，当前候选文本尚无版本依据，详情未读取。
已读详情出现两个互相冲突的版本名，需要核实主售对象。
本次身份判断输出缺失 candidateKey，未形成有效结论。
~~~

上述是格式示意，不是可以套在所有记录上的固定文案。系统知道的缺口由结构化字段生成；技术未处理也应据实写技术原因，不能编造“缺某版本”。

### 8.5 取消 relation 早期短路

relation 可保留为搜索阶段观察或兼容字段，但不能继续：

- exact 不经证据分类一律 confirmed。
- related 无 AI 一律 rejected。
- uncertain 即使后来证据充分也不能提升。
- variant / bundle 仅凭字面预判一律跳过必要消歧。

要把“确定性反证”与“规则推测的 relation”分开。程序能证明的冲突仍可直接定案，无需让模型翻案；程序只计算相似度时不能冒充证明。

### 8.6 通知和界面

- 默认通知 confirmed，且满足档案购买条件与来源新鲜度。
- 每档案放宽门槛继续有效，不新增全局“疑似也发”开关。
- 未执行、模型坏输出、详情 unsupported，不能被包装成“高度疑似”通知。
- 系统能明确排除的结果在诊断中保留，主结果不向用户转交选择题。
- 搜索结果可以同时存在少量已确认商品和部分覆盖提示；技术细节进入展开诊断。
- 成功结果展示原始标题、对应具体商品证据、价格/状态与核验时间；展示翻译错误不影响原文可读性。
- 今日 T5 的“多个不同系列都 confirmed”应通过逐条具体身份核验解决，不是给用户再加十几个过滤选项。

## 9. 执行完成、判定完成、覆盖完成分别表达

### 9.1 不撤销今天的失败保护

现有 f123338 的保护解决了 AI 失败却任务显示成功的问题，898470a 解决模型执行位置问题。第一阶段保留这些行为。

随后将“完整 AI 裁决”的对象从固定 24 条清单，转为显式的当前轮判定清单及逐条状态。不能为了支持局部结果把失败统一改回 completed。

### 9.2 兼容现有 task status

数据库 task status 目前只有 queued / running / completed / failed。首版不急于新增 partial 顶层枚举，以免客户端和 SQL CHECK 约束不一致。

在已有结果/元数据结构中增加：

~~~ts
type RunQuality = {
  processing: "complete" | "partial" | "failed";
  coverage: "exhausted_queries" | "partial" | "unknown";
  discoveredCount: number;
  confirmedCount: number;
  rejectedWithEvidenceCount: number;
  unresolvedCount: number;
  pendingCount: number;
  invalidOutputCount: number;
  sourceFailures: string[];
  stopReasons: string[];
};
~~~

具体持久化字段以迁移设计为准。不能只在 UI 临时计算而不写入审计结果。

### 9.3 状态规则

1. 必要身份处理任务技术失败，沿用 failed；保留已完成的来源事实，不把它们回填成模型成功。
2. 正常达到显式来源/运行预算，可以结束本轮，但 processing/coverage 必须真实标明 partial，客户端不能写“全部商品已判定”。
3. 所有当前轮动作都完成，但合法查询仍只覆盖一部分来源，processing 可 complete，coverage 仍 partial。
4. 没搜到确认结果且 coverage unknown，文案不能写“没有这件商品”。
5. 某查询 exhausted 不等于全网 exhausted；不得承诺绝对不存在其他挂牌。
6. 未决候选有下一步动作和终止原因，不能无期限隐藏在一个永不消费的队列里。

允许在任务整体失败时显示之前有证据的局部事实，必须与“本次搜索成功”分开，也不能借此自动触发失败任务的通知。此项属于后续兼容改造，不在第一阶段偷偷放宽。

## 10. M6：缓存、身份和数据迁移

### 10.1 分层缓存

| 缓存 | 建议 key 包含 | 不应混入 |
| --- | --- | --- |
| 来源详情 | sourceId + sourceItemId + 观测版本/刷新策略 | 其他候选的目标判断 |
| 目标抽取 | 原始输入 hash + 抽取契约/词典版本 | 召回次数 |
| 来源事实抽取 | 候选快照 hash + 字段集合 + 抽取版本 | 某目标的匹配结论 |
| 身份判断 | 目标身份 revision + 候选证据 hash + 判定契约/规则/模型版本 | 仅关键词 query 的粗粒度 key |
| 展示翻译 | 原文/已验证事实 hash + 语言 + 展示版本 | confirmed 与否的隐式默认 |
| 查询命中经验 | source + query语义 + filters + plannerVersion + 时间 | 商品永久身份 ID |

模型返回 uncertain 是合法语义结果，但不永久缓存成拒绝。新详情、新原文、目标内部修复或规则升级，应使相应判定缓存失效。

坏 JSON、合同错误、传输失败可保留短期防风暴记录，不作为可复用的成功语义缓存。

### 10.2 一次版本升级不等于所有缓存都升级

当前存在：

~~~text
product-target-extraction:v2
listing-semantics-v9
product-search-relevance:v2
product-listing-membership-v4
canonical-name-resolution-v2
~~~

精确搜索实际 job 使用独立的 product-search-relevance 版本。只改 listing-semantics 文本或版本不保证精确搜索缓存失效。

实施时建立清单：请求契约版本、模型版本、抽取版本、归一化版本、匹配规则版本、membership 版本、UI 投影版本。变更哪些语义，就升级对应键；避免仅升 promptVersion 但复用旧 finalDecision。

### 10.3 商品身份 key

必须审查现有 normalizedIdentityTarget 和 canonical name resolver：

- 版本、活动、图案等身份维度不能因未单列而被忽略。
- recallAliases、query 词序和通知阈值不改变商品身份。
- 身份维度与购买政策分开，修改价格上限不生成新商品。
- canonical name 相同不是任何情况下复用旧错误变体的充分条件。
- 解析器修复不能未经审查合并多个不同商品。

第一阶段优先修成员判定和写入门槛，不全库重新生成 product_variant_id。若需要修身份 key，先产出旧新映射及影响记录，再按范围迁移，保留引用关系。

### 10.4 今天错误关系的处理

以 T5、T6 为首批定向核查范围：

1. 冻结原任务、来源响应、AI 原输出和 membership 版本。
2. 按新规则形成新的判定草案，引用原始证据。
3. 对需要新详情才能判断的记录保持未决；不得为了回填完整而编造。
4. 原记录通过 is_current / valid_to / supersedes_membership_id 形成历史，新增版本记录承接。
5. 逐条区分模型原表态与新决策原因。
6. 不删除旧 AI batch；它们是审计事实。
7. 不覆盖 human 来源的明确人工决定，冲突进入单独审查。
8. 不因重算重复发送历史通知。

这一步是实施后的数据修复，不在当前写文档阶段执行。不能用只改代码掩盖旧错误 confirmed 仍在当前视图里。

### 10.5 下游消费者审查

需要定位并核查：

- 当前商品结果页和商品变体页。
- 当前成员关系视图。
- 历史价格、挂牌价格、成交事实、可比组。
- 搜索摘要、订阅摘要、邮件/通知筛选。
- 缓存的 intelligence/readiness 等派生结果。
- canonical name 解析和比较档案关联。

confirmed 不是价格可比的全部条件。单枚与 BOX、同款多件、混合套装，即使有包含关系，也不能直接计算同一单品均价。分摊套装价格需要额外依据，本轮不新增无依据估值。

### 10.6 幂等、并发和过期结果

- 新判断绑定 targetRevision、candidateSnapshotHash、policyVersion。
- 队列旧响应到达时发现版本不匹配，保存审计但不覆盖较新结果。
- Workflow 重试不能重复新增 current membership 或重复发送通知。
- 查询页成功后重放任务，复用该页观察记录，不能重复计入 uniqueNewListings。
- 详情内容变化使旧身份判断失效，价格变化本身可只刷新购买资格；需要明确字段依赖。
- 任务冻结 manifest 的设计继续保留，但从“永远固定 24 条”改为每个阶段/批次有明确清单和版本。

### P1：先修输出契约和判定语义

判定矩阵的四处改动（对应 §8.5）：

1. `exact` 不再不经证据分类一律 confirmed。确认走两条可核查的路径：来源可追溯的 JAN / 型号同范围命中（§8.2 路径 A，且不认「来源索引推断」那一条），或身份要素全部命中且无冲突。
2. `related` 且模型没表态不再一律 rejected，落到 uncertain 并带上「缺什么」的理由码。
3. `variant` / `bundle` 不再仅凭字面预判跳过消歧。拒绝改为要求**可核查的冲突**（JAN / 型号 / 排除词 / 厂商 / 系列 / 尺寸 / 颜色），`bundle` 的销售对象未判清时落 uncertain。
4. 模型自评 `confidence: "high"` 不再单独构成确认或拒绝的依据，两个方向都要求它给出原文引用；提示词在身份契约下同步改成「判 relevant / irrelevant 必须给引用，给不出就判 uncertain 并写清缺哪项」。

仍然保留的一条：**程序能证明的冲突直接定案**，不需要等模型翻案；与目标零身份重叠的候选同样由程序定案为 rejected（理由码 `no_identity_anchor`），不堆进未决队列。

配套的两处必须同时改，否则 P1 会自己制造一个新坑：

- 复核名额的分配依据从「relation 白名单」改成「程序是否已经判完」。白名单排除的候选不是「不需要复核」，而是「永远拿不到复核」，而下游又把没复核当成了结论。`bundle` 和「标题缩写导致缺身份组但角色命中」的候选因此首次进入复核范围。
- 任务 manifest 新增 `unreviewedUnresolvedCandidates`：名额用完后还剩多少条没判完。这个数大于 0 时本轮覆盖就是 partial，界面不得写「全部商品已判定」（§9.3）。24 条上限本身仍在，把它换成任务期限内的分批队列属于 P3。

**两个会吃掉证据的合并 bug（计划 §7.2）**

这两个不修，前面所有工作都是白做的——详情抓回来了，然后被自己人删掉：

1. `addCandidate` 里 `if (hit.liveVerified) current.listing = listing` 会**整条替换**候选。所有站内搜索命中都带 `liveVerified: true`，所以「查询 1 召回 → 抓到详情 → 查询 2 又召回一次」的候选会退回列表态，正文里那句版本说明就没了——而它往往正是这条候选唯一的判据。现在重复命中只追加查询溯源；新标题与已抓详情不一致时标记需要刷新，不拼成一个看着一致的假对象。
2. `mergeSearchAndDetailListing` 用对象展开合并。展开时一个值为 `undefined` 的键照样会盖掉左边的值，所以适配器少填一个字段，列表阶段已经拿到的那个值就被抹掉了。现在先剔除 `undefined` 再展开：详情没提到的保留列表已有的，详情真给了空值的才算它说了话。

**派单依据的变化（§7.3）**

旧规则是 `["exact","probable_exact","uncertain","related"]` 白名单 + 按分数排序。两个毛病：分数高但没有待解决问题的候选照样占请求；标题缩写导致落到 `irrelevant` 的候选被整个排除在外——而正文里往往写着完整正式名，那一次请求本可以救它。

新规则先问「这次详情能解决什么」，答不上来就不发请求；答得上来时按能解决的问题排序（高辨识度查询召回但标题简略 > 只差一个身份要素 > 销售对象没判清 > 缺多个要素 > 只剩软属性待核 > 历史参考），在售候选同等条件下优先。只要还有身份要素命中，`irrelevant` 也重新进入范围。

**闭环那一步（§6.4）**

以前一轮搜索是单向的：采集 → 复核一次 → 结束。模型写下的「缺版本证据」没有任何人接手，那句话就烂在理由字段里了。现在它是下一步动作的输入：

```
来源采集 → 复核 → 挑出「模型说不清、但详情可能说得清」的候选
        → 定向补详情 → 重算匹配 → 再复核一次 → 结果合并回同一份 manifest
```

三条边界都写死了：只补还没抓过详情、且来源支持详情的候选；不支持详情记成覆盖问题，不改判身份；预算（每轮 8 条）耗尽时剩下的保持未决，**不因为「没补上」就改判成拒绝**。这两步失败也拖不垮整轮搜索——它们只能把未决变成已决，做不到的时候候选维持未决。

结果合并回同一份 manifest（同 key 覆盖、新 key 追加），下游不需要知道有几轮。覆盖方向只能是新盖旧，因为第二轮多了详情原文，证据严格更强；第一轮的原始输出仍完整留在 `gemini_jobs` 里，审计不丢（§10.6）。

已核对：全仓 `pnpm typecheck` 通过；未改动任何 SQL 语句。

未验证：按仓库规则没有运行测试，本阶段也没有新增测试。详情补抓的实际命中率、二次复核能救回多少条缩写标题候选，都要等 P5 的正常运行观测。

仍未做（属于 P3）：24 条复核上限仍在，没换成任务期限内的分批队列；逐查询游标与停止原因账本没有建；来源之间仍然是「全部搜完再统一复核」，只有复核之后的那一轮是闭环的。

### P3：收紧查询生成和覆盖模型

**标识符被名额挤出去（§6.3）**

旧写法是边生成边占坑：`add()` 一到 5 条就不再收，而生成顺序是原始标题 → 召回别名 ×4 → JAN → 型号 → 厂商 → 系列 → 尺寸。名额永远被前五条吃光，**JAN 和型号这两条最强的查询从来没被发出去过**。商品代码是 §8.2 路径 A 的唯一依据，它进不了查询，那条确认路径就是摆设。

现在改成三步：构造全部合法候选 → 守门 → 排序后分配名额。排序依据是用途（标识符 > 具体类型与版本/系列组合 > 受验证的召回别名 > 其他受约束表达），同级按权重。原始完整标题是一条**可选**查询，不固定永远第一也不永远禁用：一手店把它提到最前（目录用正式商品名），二手站放最后（卖家不会那么写）。

这里不硬编码任何一个商品的词序——毛绒、徽章、复制画、型号商品的区分信息本来就不同。

**守门规则（§6.2）**

站内查询必须留下主体锚点（角色/作品）**和**品类词。「作品 + 角色」不带品类不是一条精确查询，是整站浏览——2026-09-10 那 866 条候选正是这么来的，然后再靠固定 Top N 假装收敛。

三个例外写死了：可靠的完整商品代码可以独立成立；用户提交的完整商品名本身就是目标定义；「角色 + 已验证的具体版本专有词」可以作为受约束兜底，但版本词必须真的出现在目标身份里。

守门只做程序能核验的事（查询里有没有留下锚点、有没有留下品类）。「这个词辨识度高不高」不在这里判——那正是 §6.2 禁止的「靠模型评分放行宽词」。

**游标绑定自己的查询（§6.6）**

旧写法把「某一条查询的下一页」当成了「这个来源的下一页」，翻页时又固定拿第一条查询去用。两者对不上时，翻到的是另一个结果集。现在 token 自带它属于哪条查询（`queryId::cursor`）；旧 token 没有前缀，按原行为走。计划换版导致那条查询不存在时，从第一条查询重新开始，而不是静静返回空页。

**逐查询账本（§6.5）**

每条查询记：抓了几页、返回多少条、新增多少条、重复多少条、几条有硬冲突、来源自报总数及其可靠性、自己的游标、停止原因、覆盖状态、耗时。没发出去的查询也入账（`refined` / `source_error`）——「没搜」和「搜了没有」不能同分。

`exhausted` 只表示这条查询当时返回的分页耗尽，**不表示整个市场已搜尽**。

**已售不算目标已满足（§6.4）**

确认同款但已售出，证明的是「这条查询有价值」，不是「用户要的在售目标已经找到了」。旧写法拿它停搜索，用户拿到的是一件买不到的商品。手动搜索按本次的在售筛选决定，巡检路径固定要求在售——多发的那一条短召回正是为了找另一个在售的卖家。

已核对：全仓 `pnpm typecheck` 通过；`pnpm verify:sql` 通过（新增语句已在生产库上预编译）。

未验证：按仓库规则没有运行测试。`tests/product-search.test.ts` 里断言「原始标题永远第一」的用例已改写成新契约，并新增了一条守门用例，但**都没有被执行过**。收紧后的召回率变化要等 P5 的正常运行观测。

仍未做：24 条复核上限仍在（换成任务期限内的分批队列需要重排 Workflow 的步骤预算）；来源之间仍然是「全部搜完再统一复核」。

## 13. 验收材料与标准

### 13.1 遵守不运行测试的仓库规则

仓库明确禁止运行测试。本轮只做只读调查、文档编辑和文档核对；不新增或运行测试套件，不把测试改名为“回放”绕过规则。

下文列的是审阅与验收标准。当前可执行部分为静态核查、人工对照已保存快照、只读 SQL；后续可被动观察正常业务运行的新记录。自动化新模型回放不属于本轮执行项。

如后续代码涉及 SQL，在实际发布前必须执行 pnpm verify:sql；它是仓库明确要求的生产 PREPARE 部署门禁，不是测试。当前仅新增 Markdown，未运行该门禁。

### 13.2 固定案例清单

不能拿模型自己的输出作真值。每条可评价样本保存目标原文、候选原文/详情快照、可核查的标签依据；证据不足的条目标注“无法建立标签”，不强凑正负例。

| 类别 | 需要观察的情形 | 通过要求 |
| --- | --- | --- |
| 今日徽章混款 | T5 的不同活动、9/10 BOX、单枚 | 不能仅共同词命中就全部确认到同款 |
| 今日 uncertain 被拒 | z586078304 | 原 uncertain 不因 relation 被机械拒绝；新反证若成立可有据拒绝 |
| 今日未复核画作 | m97171084630、m21636898439 | 有明确动作路径；不能直接把它们预标成真品 |
| 今日错误类型 | m88835489224 色纸详情 | 明确主售类型冲突得到有依据拒绝 |
| 缩写标题 | 标题缺版本，正文有完整商品名 | 能通过详情确认，不要求标题逐字覆盖 |
| 同类型困难负例 | 同角色、尺寸、作者，不同画面/活动 | 能指出区分性反证 |
| 正文提及其他商品 | 推荐清单、想换商品、并非主售对象 | 不把被提及目标当主售同款 |
| 否定描述 | “不是某版本”“仅框”“不含本体” | 引用上下文完整，不能倒置含义 |
| 销售对象 | 同款多件、混合套装、随机 BOX | 保留关系，不混入单品可比价 |
| 品相变化 | 有折痕、缺非身份配件 | 身份与购买资格分开 |
| 老库存 | 历史同款，当前状态未核实 | 不能显示本轮已确认在售 |
| 详情不支持 | Shops 或来源能力缺失 | 标为能力/覆盖问题，不当身份冲突 |
| 数据重复 | 多 query 命中同挂牌 | 去重且不丢已获取详情 |
| 新旧冲突 | 新标题与旧详情不一致 | 重新核实，不拼假证据 |
| 模型结构 | 损坏 JSON、漏 ID、重复 ID、错误枚举 | 无效结果不产生确认或拒绝事实 |
| 无依据清洗 | 脑补厂商、官方属性、型号 | 不写入受信事实 |
| 展示异常 | 韩文混入、方向翻错 | 局部修复/使用原文，不拖垮身份结果 |
| 非日系角色商品 | 可靠型号、JAN 或其他商品代码 | 不依赖“角色 + 品类”唯一模板 |

最后一行防止把方案固化成加藤惠周边专用系统。具体样本优先来自已有真实记录；没有记录就明确缺口，不生成假运行结果。

### 13.3 硬性验收不变量

以下要求不需要以模型高分来证明，应能从记录和代码逐条核对：

1. 无效 JSON/无效 ID 不能落成有效身份判断。
2. 无反证的未处理候选不能自动 rejected。
3. 模型明确未决不能因 relation 变成 high-confidence rejected。
4. 不同具体版本不能只凭共享词 confirmed。
5. 召回 query 不进入同款身份等价集合。
6. 后续列表命中不能无说明覆盖已取得详情证据。
7. 游标绑定自己的查询与参数。
8. 非本轮验证的历史状态不能充当本轮在售事实。
9. 原始模型表态与最终决策可分别审计。
10. 预算耗尽与来源无结果在记录中不同。
11. 已确认结果的通知仍受每档案设置约束。
12. 旧版本响应不能覆盖新快照判断；数据修复不能重复通知。

### 13.4 效果指标及口径

| 指标 | 正确口径 | 禁止口径 |
| --- | --- | --- |
| 确认精度 | 人工有据核对的 confirmed 中正确比例，标明样本量和品类 | 把模型 high 当正确 |
| 已知同款覆盖 | 已建立真值的正例中，进入候选/详情/确认各阶段比例 | 将抓取页数内没出现当全网不存在 |
| 误拒 | 有标签正例被 rejected，并定位反证是否错误 | 将所有未决计为误拒 |
| 未决率 | 分候选证据不足、未调度、技术失败、能力缺失 | 合成一个模糊 uncertain 数量 |
| 候选膨胀 | 各 query 新增、重复、强冲突、确认与未决 | 只看最终展示条数 |
| 有效响应时间 | 开始至首个有据且可行动结果；另记来源完成 | 只看模型接口耗时 |
| 查询覆盖 | 逐查询页数、游标、停止原因、来源错误 | 单一主查询 total 代替全部 |
| 模型可靠性 | 契约通过、引用通过、语义通过分别记录 | 只算 JSON.parse 成功率 |
| 数据修复 | 原判到新判的版本差异及依据 | 删除旧行后声称污染为零 |

今天仅两次成功搜索，不能预先设定“上线后必达 99%”或“每商品必定两次 HTTP”。具体性能目标需要多类型样本和正常运行证据；当前先要求已观察到的错误机制消失，且已知正确路径没有被新规则封死。

## 14. 发布、迁移和回退安排

### 14.1 发布前

- 核对本轮改动文件边界，不包含现有无关未跟踪文件。
- 核对新旧请求契约和队列旧任务兼容。
- schema 若改变，先准备兼容读取与增量迁移。
- SQL 改动运行仓库要求的 verify:sql 门禁；不绕过 pre-push。
- 核对通知投影，防止后台诊断用的新状态改变实际送达门槛。
- 当前阶段不进行 git push；仓库 push 会触发部署，不能当成仅备份文档的动作。

### 14.2 渐进启用

按实现包启用内部版本路由，优先精确搜索，避免波及关键词模式。可先让新判断作为并列审计结果存储，与当前结果对照；如果此运行属于测试或自动回放，仍受不运行测试规则约束，不能擅自执行。

实际生产启用时，写清哪个版本负责最终成员和通知，不能让两个版本同时竞争 is_current。

### 14.3 回退

- 路由可以回到前一稳定版本，原始观测与新判定历史保留。
- 不因回退自动恢复已知错误的旧 confirmed 作为可信当前数据。
- 必要时停止受影响新判定投影，保留已验证事实和明确故障状态。
- 模型调用失败恢复已有 fail-closed 行为。
- 数据迁移回退使用版本关系和审计映射，不执行无差别 DELETE。
- 若新规则降低召回，按来源、查询和候选阶段定位，不统一放松通知门槛。

## 15. 风险与明确取舍

| 风险 | 为什么存在 | 本轮应对 |
| --- | --- | --- |
| 过度严格导致漏判 | 要求每个目标词都在卖家标题里 | 允许详情和其他强证据，缺失不等于冲突 |
| 未决变多却无人处理 | 修掉假拒绝后暴露原本没做的工作 | 闭环调度、期限和明确动作；不把 P1 当最终交付 |
| 规则成为另一个脆弱模型 | 过度堆角色/品类加减分 | 只做可核验约束；语义仍由模型参与 |
| 模型被拆得过碎 | 调用依赖过长、上下文丢失 | 按问题拆，不机械每件三次；引用同一快照 |
| 详情请求增多 | 曾经未获机会的候选进入处理 | 先收紧 query，按缺口调度，复用有效证据 |
| 错缓存继续污染 | 不同 prompt 版本和 membership 版本错位 | 分层 key 与版本清单，定向失效 |
| 文本支持仍无法判画面 | 同名近款只在图片不同 | 保留图片证据，定向辅助，未核实不伪称确认 |
| 来源数据本身错误 | 列表标题、类别、总数不可靠 | 原始快照、矛盾处理、总量可靠性标记 |
| 把不可买同款当完成 | 已售/历史状态满足过早停止 | 身份与当前购买目标分别判断 |
| 改共享模块误伤其他业务 | AI schema 与监控共用 | 精确搜索独立协议，兼容层迁移 |
| 架构过度扩张 | 同时建本体、向量库、新服务 | 优先现有模块，不新建平台级基础设施 |

## 16. 明确不在第一轮做的事情

- 新增用户输入补全流程或宽泛商品浏览模式。
- 更换商品搜索为“推荐相关周边”。
- 引入新的付费模型供应商作为依赖。
- 构建全品类商品知识图谱或大型别名自动学习平台。
- 训练专用匹配模型、建立图像向量库。
- 全库重建商品 ID、删除历史 AI 输出。
- 重写全部 adapters 或把 PostgreSQL 迁回其他分析平台。
- 为了降低候选数全局禁止历史或网页补漏。
- 修改用户通知阈值的默认值。

可以扩展的能力应建立在当前闭环可靠之后，不能让本轮修复变成另一个无限扩张项目。

## 17. 给交叉审阅 AI 的审阅任务

请先阅读背景文档，再按以下顺序审阅本计划。不要直接改代码或数据库。

### 17.1 必须回答

1. 方案是否忠实接受“用户提供的是具体商品”，有没有暗中重新引入输入不足/用户补全流程？
2. M1～M7 是否对应真实问题，有没有把代码风险写成已发生事故？
3. 同款确认的证据门槛会不会继续太松；会不会又退化成必须逐词匹配？
4. 套装、随机 BOX、同款多件、品相的定义是否能落到已有成员与通知模型？
5. 新的模型契约是否仍要求小模型同时完成太多任务？
6. 输出校验是否把引用存在误当语义正确，或者承诺了程序做不到的理解能力？
7. 查询守门是否既阻止作品级泛搜，又保留商品代码、具体版本词等合法补漏？
8. 自适应控制是否真能利用详情/判定反馈，还是只是重命名现有 for + break？
9. 未决队列是否有处理路径和边界，是否可能仍永久饿死？
10. 今天已加的 queue/fail-closed 修复是否被保留？
11. 版本和迁移能否阻止旧 confirmed、旧 canonical resolution、旧缓存回流？
12. 能否在不运行测试的仓库约束下明确区分已验证与待验证，不虚报效果？

~~~text
结论：可实施 / 需修改后实施 / 有阻断性设计问题

问题编号：
~~~

### 17.3 待审议但不改变用户前提的工程决策

| 决策 | 当前建议 | 审阅应挑战什么 |
| --- | --- | --- |
| 内部短批规模 | 列表最多 8、详情最多 2，受长度约束 | 是否应按实际输出形状进一步调整 |
| 条目修复次数 | 同一错误最多两次修复 | 是否会无效重复或太早终止 |
| 覆盖持久化 | 优先复用现有 JSON 元数据，必要时增量表 | 并发更新、查询性能、审计体量 |
| 目标 ID 修复 | 先修成员门槛，再定向审查 key | 是否遗漏了会立即重新污染的复用路径 |
