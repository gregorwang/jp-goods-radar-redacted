# 行情邮件未送达 · 排查手册

> 用途：某天没收到关键词行情日报时，从这里开始。
> 直接把这份文档交给 Claude，让它按「第一节」的顺序跑一遍，通常十分钟内能定位。
> 起因：2026-09-21 爱蜜莉雅整天没有日报，排查过程见第六节。

## 结论先说

**邮件没到，九成不是"抓不到货"，而是"抓到了但没走完后面三步"。**

一封日报要走完四段，每一段都断过：

```
抓取 → AI 判定 → 日报聚合 → 发送
```

排查的第一件事永远是**确定断在哪一段**，不要一上来就猜原因。第一节就是干这个的。

还有一条贯穿全局的教训，写在最前面，因为它误导过一次排查方向：

> **数据库里没有错误留痕，不等于"执行被外部掐断"。**
> 留痕这个动作本身要写数据库。数据库连接坏掉时，错误恰恰是写不进去的。
> 一片空白最可能的含义是"连接死了"，而不是"进程被杀了"。

## 一、五分钟分诊（按顺序跑，不要跳）

先拿到档案 id：

```bash
ssh root@203.0.113.10 "sudo -u postgres psql -X -d jpgr -c \"select id, name, dossier_kind, enabled from radar_core.watch_profiles where dossier_kind='keyword'\""
```

下面把 `$P` 换成对应的 id（爱蜜莉雅是 `8e4f3341-c6b9-48bc-a73f-490fcf7a3eb4`）。

### 第 1 步：抓取成了吗

```bash
ssh root@203.0.113.10 "sudo -u postgres psql -X -d jpgr -c \"select b.source_id, r.status, r.started_at, r.result_count, r.new_count, r.error_code from radar_core.watch_runs r join radar_core.watch_bindings b on b.id=r.watch_binding_id where b.watch_profile_id='\$P' and r.started_at>='YYYY-MM-DD' order by r.started_at\""
```

- 全是 `success` → **抓取没问题，去第 2 步**（这是最常见的情况）
- 有 `running` 且已经过了半小时 → 见 **故障 D**
- 有 `failed` → 看 `error_code`，那是来源适配器的问题，和本手册其余部分无关

### 第 2 步：AI 判定完成了吗

```bash
ssh root@203.0.113.10 "sudo -u postgres psql -X -d jpgr -c \"select b.source_id, j.status, j.total_items, j.completed_items, j.attempt_count, j.scan_started_at, left(coalesce(j.last_error,''),80) err from radar_core.gemini_jobs j left join radar_core.watch_bindings b on b.id=j.binding_id where j.created_at>='YYYY-MM-DDT00:00' order by j.created_at\""
```

这是**最高频的断点**。看三个信号：

| 现象 | 含义 | 去看 |
|---|---|---|
| `completed_items` 长时间为 0，`attempt_count` 在涨 | 每次都白跑 | 故障 A |
| `attempt_count` ≥ 7 且推进极慢（按小时挪一批） | 被自己的退避冻住 | 故障 B |
| `status=failed`，`last_error` 只有 `queue_dead_lettered` | 消息重试耗尽 | 故障 A / C |
| 大批 `pending`，但没有对应的 job | 任务压根没建 | 看抓取是否真的写入了商品 |

### 第 3 步：日报在等什么

日报的规则是**等这一轮全部落定才发**。两个等待条件：

```bash
# 条件一：有没有卡死的 running（会无限阻塞，已加 30 分钟超时兜底）
ssh root@203.0.113.10 "sudo -u postgres psql -X -d jpgr -c \"select b.source_id, p.name, r.started_at from radar_core.watch_runs r join radar_core.watch_bindings b on b.id=r.watch_binding_id join radar_core.watch_profiles p on p.id=b.watch_profile_id where r.status='running' and r.started_at < to_char(now() at time zone 'UTC' - interval '30 minutes','YYYY-MM-DD\\\"T\\\"HH24:MI:SS.MS\\\"Z\\\"')\""

# 条件二：还有没有没终结的 AI 任务（见第 2 步）
```

⚠️ **一个容易踩的坑**：`keywordScanMembers` 取的是每个来源"在本轮开始之后的**最新**一次运行"。
如果你为了补救**手动重跑过**某个来源，而那次重跑卡住了，它会**反过来阻塞更早那一轮的日报**。
2026-09-21 就是这么把一封本来能发的日报又卡住了 15 小时。**补救操作本身会制造新的堵点，重跑后一定回头确认它跑完了。**

### 第 4 步：事件和邮件

```bash
ssh root@203.0.113.10 "sudo -u postgres psql -X -d jpgr -c \"select e.event_type, e.status ev, e.created_at, d.channel, d.status, d.outcome, d.sent_at, left(coalesce(d.fallback_reason,d.outcome_error,d.last_error,''),80) err from radar_core.events e left join radar_core.notice_deliveries d on d.event_id=e.id where e.watch_profile_id='\$P' and e.created_at>='YYYY-MM-DD' order by e.created_at desc limit 20\""
```

- 有 `daily_digest` 且 `channel=email`、`status=sent` → **邮件确实发了**，去查收件箱／垃圾箱／Resend 后台
- `channel=email` 但 `status=failed` → 看 `err`，是发送通道问题，到 `next_attempt_at` 会自动重试（最多 12 次，约两天）；`abandoned` = 不再发了
- 只有 `channel=feishu` 没有 email 那一行 → 这个档案只开了飞书（档案页「通知发到哪」），飞书没送到才会补邮件
- `daily_digest` 一行投递记录都没有、事件 `ev=suppressed` → 档案两个开关都关了，或者被折进了超量汇总
（10-14 晚起所有渠道的发送记录都在 `radar_core.notice_deliveries`；更早的在 `email_deliveries`，不再写入）
- 没有 `daily_digest` → 回到第 3 步，它还在等

### 第 5 步：还查不出来，去看 Worker 日志

日志采集是开着的（`observability.enabled: true`，采样率 100%），保留 7 天。
需要 Cloudflare 授权（`cloudflare-observability` MCP）。**这是唯一能看到"数据库写不进去"那类故障的地方。**

优先查这三个：

| 查什么 | 说明 |
|---|---|
| `$workers.outcome` 分组计数 | 出现 `exceededCpu` / `exceededMemory` 才是真的被运行时掐断。**全是 `ok` 说明代码正常返回了，问题在别处** |
| `event` 字段分组计数 | `queue_consumer_failed`＝消息处理抛异常；`queue_failure_persistence_failed`＝**连错误都写不进数据库**（强烈指向连接问题） |
| `$metadata.error` 值分布 | `Query read timeout` / `Connection terminated unexpectedly` / `Client has encountered a connection error` 都是数据库连接问题 |

## 二、已知故障模式

### 故障 A ·（根因）数据库杀掉了等待中的连接 🔴 最重要

**指纹**
- 数据库日志密集出现 `terminating connection due to idle-in-transaction timeout`
- `completed_items` 为 0，`last_error` 空白，`upstream_status` 为 NULL
- AI Gateway 那边**每次调用都是成功的**
- Worker 日志 `outcome` 全是 `ok`，没有 CPU 超限
- **件数越多越容易失败**（这是最独特的指纹）

**机制**

等 AI 返回的那段时间，数据库连接处于"事务开着但没有语句在跑"的状态。超过限制，PostgreSQL 主动杀连接。于是：模型正常答完 → 回头写库时连接已死 → 连错误都记不下来 → 消息重试耗尽进死信 → 数据库里只剩一行没有原因的记录。

小任务（1–3 件，几秒返回）安全，大任务（39／68 件，几十秒）必挂。

**2026-09-21 的现场**：生效值是 **30 秒**（角色级设置，不是全局的 60 秒），而代码允许等 **90 秒**。

**怎么确认**

```bash
ssh root@203.0.113.10 "sudo -u postgres psql -X -d jpgr -c \"select r.rolname, s.setconfig from pg_db_role_setting s join pg_roles r on r.oid=s.setrole join pg_database d on d.oid=s.setdatabase where r.rolname='jpgr_app'\""
```

⚠️ **别只看 `show idle_in_transaction_session_timeout`**。角色级设置会覆盖全局值，而 `show` 在你自己的会话里显示的不是 `jpgr_app` 的值。本次排查差点被这一步误导。

**当前状态**：`jpgr_app` 已放宽到 `3min`；代码侧 AI 等待收到 `55s`。见第三节的配对表。

---

### 故障 B · 任务被自己的退避冻住

**指纹**：`attempt_count` ≥ 7，推进节奏是"每小时挪一批"，但每次执行都正常。

**机制**：退避公式是 `min(1小时, 30秒 × 2^attempt_count)`，而 `attempt_count` 是**领取计数**，不是失败计数 —— 每处理一批就要领取一次。于是任务越大跑得越久，在退避眼里越像"一直在失败"，最后每小时才动一批。同一个计数器还被 `MAX_TRANSIENT_ATTEMPTS`（10）当失败次数用，大任务会被直接判死。

**已修**：判出一批就把 `attempt_count` 归零（只在真有进展时重置）。

**教训**：`attempt_count` 语义是"领取过几次"。**任何地方拿它当失败次数用都是 bug**，这个坑一共踩了三处。

---

### 故障 C · 死信一击判死可自愈的任务

**指纹**：`status=failed`，`last_error` 是 `queue_dead_lettered:...`，而任务其实还有余力。

**机制**：队列的 `max_retries` 按**单条消息**计数，而分批任务要靠许多条消息才跑得完。死信处理器把任务标成 `failed`，而 `failed` 恰好不在 `recoverGeminiJobs`（每分钟一次的自愈巡检）的扫描范围内 —— 自愈从此看不见它。

**已修**：消息耗尽时退回 `queued` 交还给巡检；一件都没判出来的才用紧上限（12 次），有进展的给四倍余量。

**人工捞回的办法**（改完代码后仍然需要，因为修复只影响未来）：

```sql
update radar_core.gemini_jobs
   set status='queued', completed_at=null, lease_expires_at=null,
       next_attempt_at=null, attempt_count=0,
       last_error='manual_revive',
       updated_at=to_char(now() at time zone 'UTC','YYYY-MM-DD"T"HH24:MI:SS.MS"Z"')
 where kind='keyword_enrichment' and status='failed'
   and created_at>='YYYY-MM-DDT00:00' and completed_items<total_items;
```

改完两分钟内巡检会自动捞起来。

---

### 故障 D · 卡死的 running 无限阻塞日报

**指纹**：`watch_runs` 里有 `running` 的行，已经过去几小时，而且不会再变。

**机制**：`running` 没有兜底 —— 一次没跑完的采集不会回来改状态，队列消息重试耗尽就进死信了，这一行永久停在 `running`。日报等的正是"这一轮跑完没有"，于是等满 576 次重试（48 小时）。

**已修**：超过 `STALE_RUN_MINUTES`（30 分钟）还 `running` 的当它没跑成，日报照发并在信里写明这个来源缺了。

**人工收尾**：

```sql
update radar_core.watch_runs
   set status='failed',
       finished_at=to_char(now() at time zone 'UTC','YYYY-MM-DD"T"HH24:MI:SS.MS"Z"'),
       error_code='run_interrupted'
 where status='running'
   and started_at < to_char(now() at time zone 'UTC' - interval '30 minutes','YYYY-MM-DD"T"HH24:MI:SS.MS"Z"');
```

### 故障 E · 判定通道拥堵（未修，已知限制）

AI 判定队列是 `max_concurrency: 1`，**全局单车道**，所有档案共用一个处理位。

目前够用，**前提是各档案的采集时间错开**。现状：爱蜜莉雅 11:03、加藤惠 10:38、千反田 00:58／06:10。

**新增关键词档案时，把 `next_run_at` 错开至少 20 分钟。** 这条零成本，比调并发安全 —— 调并发会让 Gemini 限流预约表出现新的竞态。

---

### 故障 F · 同一批反复撞 55 秒超时

**指纹**：`last_error` 是 `The operation was aborted due to timeout`，`completed_items` 不动，`attempt_count` 在涨；同一时间别的档案判得好好的。

**机制**：模型某段时间变慢，一批 32 件答不完 55 秒；下次领取还是同一批 32 件，于是反复撞墙，日报跟着等。2026-10-08 加藤惠的雅虎拍卖就是这样卡了 40 分钟，后来模型恢复速度才自己过去。

**已修**：超时后本任务的批量砍半（32 → 16 → 8 …，写在 `result_json.batchCap`），并且把已就绪的条目（缓存复用的那部分）先落库，后台不再一直显示 0。日志事件 `gemini_batch_shrunk_after_timeout`。

**不要用放宽 55 秒来解决**——它必须小于第三节的 3min。

**AI 最终放弃时（2026-10-08 起）**：关键词档案里 AI 判不出的条目（`state=failed`）按关键词规则放行，
观察记录写 `decision_status=uncertain`、理由「AI 没能判定，已按关键词规则放行」，日报按来源写一行
「AI 这次没判完：雅虎拍卖 N 件，已只按关键词规则放行」。精确同款不放行。
放弃要等瞬时重试耗尽（10 次，约 4 小时），所以这种日报会**晚到但不会丢**。

### 不是故障 · 邮件里没有定価 / AI 预测 / 同款成交，也没有黄条

**先看档案自己的设置**（2026-10-11 起）：档案详情页「日报附带信息」可以把原价设成
「只要官方定価」或「不显示原价」、把同款成交关掉。关掉的部分发信时就不请求，邮件里自然没有，
也不会出黄条——黄条只在「开着却没取到」时出现。

```sql
SELECT name, digest_price_reference, digest_show_sales FROM radar_core.watch_profiles WHERE dossier_kind='keyword';
```

日报载荷里的 `digestExtras` 记着那封信发出时的设置。设置是全开、邮件里却没有，才回到第三节查价格接口。

## 三、必须成对的数值 ⚠️

**这一节是整份文档最重要的部分。** 本次事故的根因就是一对数字失配，而且没有任何测试能发现它 —— 类型检查看不见，SQL 门禁也看不见。

| 数值 | 当前 | 位置 | 必须小于／大于 |
|---|---|---|---|
| `idle_in_transaction_session_timeout` | **3min** | PG 角色 `jpgr_app`（**不是全局值**） | **必须大于下面两个等待** |
| `LISTING_PROVIDER_TIMEOUT_MILLISECONDS` | 55s | `apps/collector/src/gemini-jobs.ts` | 必须小于上面那个 |
| `RUNNER_JOB_TIMEOUT_MS` | 95s | `apps/collector/src/source-runner-client.ts` | 必须小于上面那个 |
| `ENRICH_REQUEST_TIMEOUT_MS` / `ENRICH_RETRY_DELAY_MS` | 120s / 60s（最坏 5 分钟） | `apps/collector/src/listing-enrich.ts` | **不持有事务**：调用点在 `prepareKeywordDigest` 读完、写入 batch 之前。以后若把它挪进 batch 里，就必须和上面的 3min 成对 |
| 提供方 `ENRICH_DEADLINE_MS` | 100s（数据库最多 45s，模型拿剩下的） | `jp-market-databricks/apps/teika-lookup-worker/src/enrich.js` | **必须小于上面的 120s**。2026-10-07 提供方是「45s + 120s」，模型冷启动一慢日淘先挂断，加藤惠整封的定価、行情全丢（不是只丢估价）。邮件里会出现黄条「本轮价格参考没取到」 |

**规则：改任何一个之前，先看它的对家。** 尤其是把 AI 等待调大时，**必须先调大数据库那一侧**。

## 四、自愈机制现状（知道它们在，才不会重复造）

| 机制 | 周期 | 覆盖什么 | 盲区 |
|---|---|---|---|
| `recoverGeminiJobs` | 每分钟 | `queued` / `processing` / `waiting_rate_limit` 的判定任务 | **不扫 `failed`** |
| 日报 finalize 重排 | 每 5 分钟，最多 576 次 | 等这一轮落定 | 上限 48 小时 |
| 死信退回 `queued` | 出事即刻 | 消息耗尽的任务 | 复活 12／48 次后仍判死 |
| `STALE_RUN_MINUTES` | 日报检查时 | 卡死的 `running` | 只影响日报判据，不改数据 |
