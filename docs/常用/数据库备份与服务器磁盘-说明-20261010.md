## 1. 备份在哪

| 备份 | 多久一次 | 包含什么 | 不包含 |
|---|---|---|---|
| **Databricks 镜像** | 每天 4:30（服务器时间） | 主站的行情、档案、判定记录（`radar_core`、`radar_analytics`、`jpgr_meta`） | 表结构（要靠仓库 `postgres/` 重建） |
| 笔记本手动备份 | 不定期 | 整个库（`pg_dump`） | — 最近一份是 09-28，在 `C:\Users\me\jpgr-backups\` |

Databricks 那份本来是给数据分析用的镜像，顺带当备份用。能把数据找回来，但不是一键还原。
做有风险的数据库操作前，仍然先手动拉一份到笔记本：

```
ssh root@203.0.113.10 "sudo -u postgres pg_dump -Fc -Z 6 -d jpgr" > jpgr-<时间>.dump
```

同步程序的说明在服务器上：`/etc/jpgr-databricks/README.md`。

## 2. 10-09、10-10 两晚同步失败（已修）

**现象：** 日志里是 `The request could not be processed by the warehouse`。

**原因：** Databricks 的计算机器闲置 10 分钟会自动关机。以前来了查询它会自己开机，
10-09 起不再自动开了，同步一发查询就被拒，连最简单的 `SELECT 1` 都过不去。

**修法：** 在同步程序里加了一步，写数据之前先显式开机、等开好再写
（服务器 `/usr/local/sbin/jpgr-databricks-sync` 的 `ensure_warehouse_running`）。
改之前的原程序备份在 `/usr/local/sbin/jpgr-databricks-sync.bak-20261010`。
10-10 上午手动开机重跑了一次，89 张表全部成功。

**同步失败了怎么办：**
1. 看日志最后的报错：`journalctl -u jpgr-databricks-sync.service -n 40`
2. 手动开机再重跑：
   ```
   ssh root@203.0.113.10
   export DATABRICKS_CONFIG_FILE=/etc/jpgr-databricks/databrickscfg HOME=/var/lib/jpgr-databricks-sync
   databricks warehouses start d9d23032acdd4d4d -p jpgr-free
   systemctl start --no-block jpgr-databricks-sync.service   # 跑完约 20 分钟
   ```
3. 重跑之前先看磁盘（见下一节），剩不到 3G 就先别跑。

## 3. 服务器磁盘为什么会涨

**同步每次会在服务器上导出一份副本，约 2.2G，只有同步成功才会删旧的。**
所以同步连续失败几天，磁盘就每天多 2G。10-10 就是这样从 70% 涨到 88%，
手动重跑时又多导出一份，一度到了 95%（只剩 1.8G）。

磁盘满了会连带数据库出问题，比备份失败更危险。看磁盘：`ssh root@203.0.113.10 "df -h /"`。

10-10 清理记录（清完 70%，空出 10G）：
- 同步成功后自动删掉的旧导出：约 6G
- 手动删的：抓取程序 9 月的旧版本（1.1G）、7 月迁移的临时文件、7 月的第一份同步快照、
  软件安装缓存、旧系统日志（压到 100M）

**没动的（不是这个项目的，要不要清由用户决定）：** Kindle 网关 1.6G、agy 旧版本备份 600M、
emt-sre 实验备份 450M、动画数据 `/srv/anime-emergency-20260729` 577M。
