理解本系统决策链路的三大铁律

01 · 注意力是最稀缺的资源（误报的终局仍然是漏报）

系统的产出不是“找到的商品”，是“值得用户花时间看的商品”。一封不该发的邮件消耗用户当天的注意力预算，拉低下一封邮件被打开的概率。连发三封 AI 自己都写明“角色不对、品类不对”的邮件，第四封真品就没人看了。把自己有能力做的判断转嫁给用户不是谨慎，是失职。

02 · 判定档位和送达门槛是两件事，永远不要焊死

判定档位（decision_status × match_relation × AI 的 relevance）描述系统怎么看这条候选，力求准确；送达门槛（watch_profiles.suspect_notice_policy）描述什么档位值得打扰人。二值化的“发 / 不发”是历史每一次事故的共同根因。默认取最严的一档：只发确认同款（confirmed_only）。

03 · 拒绝要有反证，降档要写清缺什么

“没找到证据”和“找到了反证”在代码里不能同分：硬标识符（JAN / 型号）冲突、命中排除词、AI 明确判 irrelevant 是反证，可以定案；字面覆盖不达标、模型没把握是证据不足，只能降档。降档时那行差异说明（difference.missing）是这条记录的全部价值，写不出具体缺了哪个词，等于没降档。

3.1 三种 intent 的区别

intentKind 触发条件 系统怎么对待用户输入 alias 策略
keyword 关键词雷达 原始查询原样保留（含日文空格/标点），配包含词/排除词组 无 alias 概念
named_product 精确同款，但 AI 没抽取过、且启发式指纹「弱」（strength < 2） 每轮从用户填的商品名重新启发式重算指纹 alias 只做本地匹配证据，永不发给网站
fingerprint 精确同款，AI 抽取成功（aiExtracted=true），或启发式指纹够强（strength ≥ 2） 信任已存的指纹槽位，不用启发式覆盖 alias 只要还带着「身份锚 + 品类」就可以发给网站；recallQueries 一定发

named_product 和 fingerprint 对 alias 的差别，本质是「用户给的是不是一个确定的完整标题」：

  • named_product = 用户已经给了确定标题，搜索按字面契约执行，自动切出来的缩写词不能替用户改写他的查询。
  • fingerprint = 系统对目标做过结构化理解，知道哪些是身份锚（角色 + 品类），带着锚的缩写词发出去是安全的。

为什么某些 alias 只用于本地 matching：一个只剩品类的缩写（比如单独一个 ぬいぐるみ）发给用 OR 匹配或推荐兜底的来源（Yahoo / Amazon），会把精确搜索变成整站浏览。所以 namedProductReductions 生成的缩写必须保留完整的本地已知身份，否则只留在本地当加分证据。

一手店卖的是还在发行的新货，不收二手。对绝版限定商品，一手店搜不到是结构性的 —— 东西早卖完了，换任何召回词都一样。

这不是停止监控：一手店有再販，货会重新上架，那正是要盯的；只是「没有」就是没有，多问两遍不会变成有。一手店标题是商品数据库出的，也不需要「兜住口语化缩写」那层保险。

二手市场的标题是人手打的，冴えカノ、育て方 这种口语缩写真实存在。保留 1 条短召回兜住它。

14. 「相似度不是最终答案」+ 补全值不作负证据

#ch-14

14.1 为什么关注差异

结合案例：目标是 冴えない彼女の育てかた♭ … A3プリモアート。同一轮候选里有 8 条 Fes. Fine 版。

  • 相似度视角：同作品、同品类（プリモアート）、可能同角色（加藤恵）→ 65~90 分 → 会过「确认同款」线。
  • 差异视角：目标有 ♭ 和 深崎暮人イラスト，Fes. Fine 版没有 → missing: ["冴えない彼女の育てかた♭","深崎暮人イラスト"] → 降 uncertain。

「有 ♭」和「没 ♭」是两件不同的商品。系统必须关注这个「差」。

14.2 补全值不作负证据

抽取器被允许把作品名补成官方全名（高木さん → からかい上手の高木さん）。但补出来的词随后被当成「必须命中的身份词」，于是与目标逐字相同的真品（高木さん からかいパーカー グレー Lサイズ）实测 100 分却判 uncertain，理由写着「缺少『からかい上手の高木さん』」—— 要求卖家写出用户自己都没写的词。

现在（只对 aiExtracted 生效）：抽取出的槽位值必须在用户写的 canonicalName 里有依据，才当身份词（evidencedIdentityTerms）；它仍参与加分与召回。手填的厂商/系列/型号是显式输入，不受此限。

同一判别符的多个粒度（冴えない彼女の育てかた♭ 整词 + ♭ 单字）只保留信息量更大的长词。

逐条解释

exact 为什么可以 deterministic confirmed：JAN/型号完全一致是程序完全有把握的证据，模型的自评置信度不能覆盖它。过去这里要求 confidence === "high" 且无套装/缺件迹象，三道 AND 门任何一道都会让真品无声消失（m83965697348，标题逐字相同、在售 ¥28,500，连续六轮被丢）。

variant / bundle / irrelevant 为什么 matcher 可以直接 rejected：这些是「找到了反证」，不是「没找到证据」。

related 的三个分支：09-06 改动核心。过去 related 在读 AI 之前就短路成 rejected —— 于是缩写标题的真品被硬拒、模型写清楚的否定结论从未参与判定。现在：模型说「是」→ 降 uncertain 交用户；说「不是」→ rejected 定案；不表态 → 维持 rejected（related 本身就是证据不足）。

probable_exact 什么时候 AI relevant 可以升 confirmed：

  • identityProven（missing 和 conflicting 都为空）→ 身份已由文本证明，模型只是「没把握措辞」，confidence: low 也升 confirmed。
  • 或者 confidence: high 且没有多件套装/缺件迹象。

identityProven 具体意味着什么：目标的身份要素一个不缺（missing 空），且没有字段冲突（conflicting 空）。= 「候选文本已经完整证明了这就是目标商品」。

missingParts / multipleIncludedItems 为什么不一定意味着「不是同一个商品」：它们描述的是品相和包装。一件缺了小配件（台座、特典卡）的商品仍然是同一个商品，用户更需要看到它。所以身份已证明时它们不再拦截，只留在邮件的判定理由里；身份未证明时才继续要求高置信度。

AI confidence 什么时候决定命运，什么时候不能：

  • 决定命运：probable_exact + relevant + 身份未完全证明 → 需要 confidence: high 才 confirmed。
  • 不能覆盖：relation == exact（确定性证据），以及 probable_exact + identityProven（文本已证明）。

逐个事件的判据

price_drop

price_drop 必须同时满足：

  1. notifyPriceDrop 已启用
  2. priceDropConfirmed === true —— 二次确认。首次看到降价时不立刻发，排一个 ConfirmPriceDropJob（delaySeconds: 30），下一次抓取确认价格真的降了才算数。防止来源瞬时抖动/解析错误制造假降价。
  3. oldPrice 和 newPrice 都是有效价（validComparablePrice）
  4. newPrice < oldPrice
  5. oldPrice - newPrice >= minDropAmount（用户配的最小降幅）

事件 key 含小时桶（observedAt.slice(0,13)）：同轮重试幂等，之后真实再次发生的同一转移可重新通知。

target_price

target_price 如何判断第一次跨线：crossed = oldPrice === undefined || oldPrice > input.targetPrice。即上一次的价格还在目标价之上（或没有上一次），这一次 <= targetPrice —— 只有「跨过」那一刻发，之后一直低于目标价不会反复发。

restock

restock 如何判断：上一次是 sold_out / unavailable / preorder / backorder，这一次变 available。

sold_out

sold_out 为什么 unavailable 可能还需要额外确认：

  • sold_out = 来源明确说「卖光了」→ 直接算终局。
  • unavailable = 页面消失 / 404 / 解析不到 —— 可能是来源临时抽风。所以需要 availabilityChangeConfirmed === true（详情页明确返回不可购买，或连续两次 404 已完成业务确认）才算终局。payload 里标 inference: "confirmed_missing"。
sold_out

new_listing 的终局闸门：["sold_out", "unavailable"] 不发 new_listing。但库存未知不等于不可买 —— Yahoo! Shopping 公开搜索页没有库存字段，归一化后 availability 恒为 unknown。用「可购买白名单」做闸门会让这个来源永久静默（采集、匹配、AI 判定全部照常，但一条通知都发不出）。所以只排除明确的终局，不排除 unknown。

29.2 用户问的四个具体问题

classify_deal() 是规则还是 ML：纯规则函数。按折价比例（5%/10%/20% 动态带）和绝对差额（¥100/¥300/¥800 护栏）分档，不是训练得到的决策树。README.md 明确写：「不是训练得到的机器学习决策树」。

variant-intelligence.ts 与 Databricks 的 deal classification 是不是同一个：不是。packages/core/src/variant-intelligence.ts 留在 jp-goods-radar，是应用内的「价格位置判定」（给商品情报页用，判断一条在售报价在同款样本里的位置、哪些样本可比）。Databricks 的 classify_deal 是另一套折价机会分档。resale-economics.ts 是第三样东西 —— 未接入的 TypeScript 三情景原型，Databricks 没调用它。

price_reference（原価库）主要解决什么问题：提供厂商定価 / 官方原価作为参照基线，区别于「二手在售中位价」。三个 schema 并列不合并：

  • amiami（21,826 行）：AmiAmi 零售商目录记录的厂商定価。
  • aniplex（4,848 行）：ANIPLEX Online 官方商城的官方一手原価。
  • hobbysearch（8,369 行）：Hobby Search 零售商目录的厂商定価。

三张表不能按商品编号 join（编号空间完全不同）。跨源关联唯一合法的键是 jan（只有 amiami 和 hobbysearch 有）。它服务于 reference-vs-resale-analysis 这类「二手价 vs 原价」的研究，不是 classify_deal 的 benchmark（后者用的是同款在售中位价）。

AmiAmi / ANIPLEX / Animate / Hobby Search 在原価库里的角色：

  • ANIPLEX：发行方官方商城的一手定价（最权威，但覆盖窄，5 个 IP）。
  • AmiAmi / Hobby Search：零售商目录里记录的厂商定価（覆盖广）。AmiAmi 保留商品当年的税基，Hobby Search 恒为当下 10% 税込。

规则 #01
ProductFingerprint 是商品身份证，不是搜索关键词集合。 每个字段都在某个具体判定里发挥作用；edition（♭、レーシングVer.、一番くじ）是这个领域区分兄弟款的关键字段。
规则 #02
目标建立分两轮异步：启发式指纹先顶着，AI 抽取好了再合并写回。 AI 抽取全空 → 退回启发式，绝不阻塞建档。抽取成功后 aiExtracted:true 会永久关掉回填重试。
规则 #03
召回阶段宁可多抓证据，价格与库存不能提前杀掉同款。 exactProductEvidenceFilters 在精确同款采集时清空所有价格/品相/在售过滤 —— 已售的、超预算的、中古的同款都要进身份证据库。
规则 #04
「计划最多 5 条查询」是给建档用的上界；巡检每轮只发 1 + fallback。 一手店（animate/amiami/amazon 等 7 家）只发主查询；二手市场最多 +1 条短召回。主查询命中合格同款就收手，主查询整个失败就不再扇出。
规则 #05
搜索排名不是身份依据。 Yahoo/Amazon 会返回 OR 匹配和推荐；高排名命中只有在候选文本已独立命中身份字段后才加分。
规则 #06
JAN / model 冲突是真正的反证，可以直接否决。 命中用户填的排除词、AI 高信度判 irrelevant、品类家族冲突（书 vs 手办）同样是反证。
规则 #07
缺失信息只能降档到 uncertain，不能等同反证。 「没找到证据」≠「找到了反证」。降档时那行「缺少『XXX』」是这条记录的全部价值。
规则 #08
系统关注「差异」不是「相似度」。 同作品 + 同角色 + 同品类可能仍不是同一件商品；纯累加打分会把兄弟款推过确认线。
规则 #09
match_relation、AI relevance、decision_status 是三个独立维度，落三列，永远不要混。
规则 #10
Gemini 只处理 matcher 无法定案的中间区（probable_exact / related / uncertain）。 matcher 已确认（exact）和已否决（variant/bundle/irrelevant）的它不碰。它不是从头判断每件商品。
规则 #11
AI 说 relevant 不等于 confirmed。 related + relevant 只到 uncertain；probable_exact + relevant 还要看身份是否已由文本证明（missing 空）或模型是否高置信度。
规则 #12
confirmed 和「是否通知」是两件事。 decision_status 是系统认知，送达门槛（watch_profiles.suspect_notice_policy，每档案一个，默认 confirmed_only）是「什么档位值得打扰这个人」。误报的终局仍然是漏报 —— 漏在收件箱里。
规则 #13
C2C 的 sold 是终局，商家的 sold_out 可能补货。 Mercari/Yahoo フリマ/eBay/拍卖一条挂牌对应一件实物，售出即终局；Animate/骏河屋/Rakuten SKU 会补货，「售罄→补货」是核心场景。
规则 #14
降价要二次确认（30 秒后再抓一次），目标价只在第一次跨线时发，售罄的 unavailable 要额外确认才算终局。 库存 unknown（Yahoo Shopping）不等于不可买，不能用它做通知闸门。
规则 #15
jp-goods-radar 负责「诚实地看见并保存事实」，jp-market-databricks 负责「基于事实判断值不值得买」。 后者是独立仓库、独立管道（Bronze→Silver→Gold→飞书），classify_deal 是纯规则（S/A/B 按折价比例和绝对额），benchmark 是同款在售中位价；原価库（price_reference）是另一套官方/厂商定価参照，不是 classify_deal 的基线。
