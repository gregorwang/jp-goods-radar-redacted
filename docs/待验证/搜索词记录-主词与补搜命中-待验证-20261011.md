## 为什么做

精确同款档案每轮先搜**主词**（完整商品名）。如果主词没找到能买的同款，再追加一条**补搜**短词。普通关键词档案只搜档案里填的那一个词。

以前只有煤炉的记录里留了实际搜的词。其他渠道走备用通道（Firecrawl、采集服务）之后，请求记录里看不到词，所以下面这几个问题一直答不了：

- 主词、补搜各找回几件？
- 确认同款是哪条词找到的？
- 补搜到底有没有用？

代码里补搜的条数（`apps/collector/src/index.ts` 的 `EXACT_PRODUCT_WATCH_FALLBACK_VARIANTS`）就是因为缺这份数据，只能凭煤炉一家的证据定成 1 条。

## 做了什么

- 新表 `radar_core.watch_run_query_attempts`（迁移 `20261011180000_watch_run_query_attempts`，已登记）：每轮每条实际发出的词记一行，包括是主词还是补搜、搜回几件、其中几件是前面的词没找到的、是哪几件商品（商品编号），以及成功还是失败。
- 写入在 `apps/collector/src/query-attempts.ts`，写失败只打日志，不影响采集。记录保留 365 天（`watch_runs` 只留 90 天）。
- 这项改动不改搜索方式、不改结果、不花钱。
- 采集程序提交 `f597938`，10-11 10:42（日本时间）自动发布。

## 10-25 要跑的三条查询

```bash
ssh root@203.0.113.10 "sudo -u postgres psql -X -d jpgr" <<'EOF'
-- ① 每个渠道：主词 / 补搜 平均搜回几件、新找到几件、失败和 0 件的轮次
SELECT source_id, role, count(*) AS 轮次,
  round(avg(upstream_count),1) AS 平均搜回, round(avg(new_candidate_count),1) AS 平均新找到,
  count(*) FILTER (WHERE outcome='failed') AS 失败,
  count(*) FILTER (WHERE upstream_count=0 AND outcome='succeeded') AS 零件
FROM radar_core.watch_run_query_attempts GROUP BY 1,2 ORDER BY 1,2;

-- ② 判定结果按"第一次找到它的是哪条词"拆开（confirmed = 确认同款）
WITH hit AS (
  SELECT a.watch_run_id, a.source_id, a.ordinal, a.role, item
  FROM radar_core.watch_run_query_attempts a, jsonb_array_elements_text(a.source_item_ids_json::jsonb) item),
first_hit AS (
  SELECT DISTINCT ON (watch_run_id, item) watch_run_id, source_id, role, item FROM hit ORDER BY watch_run_id, item, ordinal)
SELECT f.source_id, f.role AS 首次找到它的词, o.decision_status, count(*) AS 件数
FROM first_hit f JOIN radar_core.watch_run_listing_observations o
  ON o.watch_run_id=f.watch_run_id AND o.source_item_id=f.item
GROUP BY 1,2,3 ORDER BY 1,2,3;

-- ③ 有没有漏记：关键词档案的定时搜索轮次里，缺记录的应为 0
SELECT b.source_id, count(*) AS 搜索轮次,
  count(*) FILTER (WHERE NOT EXISTS (SELECT 1 FROM radar_core.watch_run_query_attempts a WHERE a.watch_run_id=r.id)) AS 缺记录
FROM radar_core.watch_runs r JOIN radar_core.watch_bindings b ON b.id=r.watch_binding_id
WHERE b.kind='keyword' AND r.trigger_type='cron' AND r.status IN ('success','failed') AND r.started_at > '2026-10-11T02:30'
GROUP BY 1 ORDER BY 1;
EOF
```

> ⚠️ **10-14 修过一个记录口径的 bug**（code review 发现），跑①③时要注意：
> 修复上线前，**普通关键词档案**（不是精确同款）搜索失败的那一轮一行都不记，`new_candidate_count` 也直接填了搜回总数（老货算成新货）。
> 所以修复前的数据里，普通关键词档案的"失败"偏少、"平均新找到"偏高，③的"缺记录"也会把这些失败轮次算进去。
> 精确同款档案的记录一直是对的。看普通关键词档案的这两项时，加 `AND created_at > '<修复上线时间>'`
> （以 `git log` 里 "query attempts" 那次提交推上去的时间为准），或者只拿精确同款档案下结论。

②里的"件数"是按轮次算的，同一件商品每轮都会算一次。要看有几件不同的商品，就把 `count(*)` 换成 `count(DISTINCT f.item)`。

## 怎么判

**先看③。** 哪个渠道缺记录不是 0，就先去查为什么没写进来，这个渠道的数据先不用。

**再看②，按渠道下结论：**

| 看到的 | 结论 | 可以做的 |
|---|---|---|
| 某渠道补搜**从没**首次找到过确认同款，也很少找到"不确定"的 | 这个渠道的补搜只在花钱 | 这个渠道的补搜降到 0 条（骏河屋走付费备用通道，省得最多） |
| 补搜找到过确认同款 | 补搜有用 | 保留；如果这个渠道主词经常 0 件、补搜才有货，考虑让补搜优先 |
| 补搜大多被判"不是同款"，但偶尔找到"不确定" | 说不清 | 再攒两周，或者人工看看那几件"不确定"的 |

**最后看①里的"平均搜回"。** 如果某条词每轮都搜回满满一页（煤炉、雅虎通常一页 30～40 件，骏河屋一页 24 件），说明这条词太宽，目标款可能排在后面没看到。上一轮就有这个例子：「初音ミク ミニ色紙」在骏河屋有 482 件。这种情况要结合②一起看：

- 这个档案在别的渠道找到过确认同款，在这个渠道却一直没有：词太宽可能真的漏了货，考虑多翻一页或者换个更窄的词。
- 别的渠道也没有：只是没货，不用改。
