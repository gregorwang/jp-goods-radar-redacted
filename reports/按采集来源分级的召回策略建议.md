### 1. 每个来源的产出：全历史与 09-04 以来确认商品大盘

在数据分析中，必须将“观测次数（Observations）”与“去重商品（Unique Items）”严格区分：同一件在架商品若每天被扫到 4 轮，连续 5 天会产生 20 条 confirmed 观测，但这在用户端只代表**1 件实际商品**。

```sql
-- 统计全历史与 09-04 以来各来源的产出对比
SELECT 
  o.source_id,
  count(*) FILTER (WHERE o.decision_status = 'confirmed') as confirmed_obs_all,
  count(DISTINCT o.source_item_id) FILTER (WHERE o.decision_status = 'confirmed') as confirmed_items_all,
  count(*) FILTER (WHERE substr(o.observed_at, 1, 10) >= '2026-09-04' AND o.decision_status = 'confirmed') as confirmed_obs_0904,
  count(DISTINCT o.source_item_id) FILTER (WHERE substr(o.observed_at, 1, 10) >= '2026-09-04' AND o.decision_status = 'confirmed') as confirmed_items_0904
FROM radar_core.watch_run_listing_observations o
JOIN radar_core.watch_bindings wb ON wb.id = o.watch_binding_id
WHERE wb.source_config_json LIKE '%exact_product%'
GROUP BY o.source_id
ORDER BY confirmed_items_all DESC;
```

1. **全历史累计去重 confirmed 商品仅 25 件**：

   - `yahoo_auctions_jp`：6 件（占 24.0%）

### 3. 核心决断：扩写到底有没有救回来过东西？(全量 Payload 追踪)

这是决定系统是否应当全面关停扩写的根本问题。我们对 09-04 以来产出 confirmed 的所有轮次，逆向解析其所有 captures 的 `request_url`、`ordinal` 以及 `raw_payload` 中的 `searchCondition.keyword`，追踪这 16 件 confirmed 商品到底出现在哪个 capture 中：

```sql
-- 验证 Confirmed 商品的命中变体类型（主查询 vs 扩写追加）
WITH confirmed_search_hits AS (
  SELECT 
    ci.source_id,
    ci.source_item_id,
    ci.title as item_title,
    wp.name as profile_name,
    c.raw_payload::jsonb->'searchCondition'->>'keyword' as search_keyword,
    CASE 
      WHEN length(c.raw_payload::jsonb->'searchCondition'->>'keyword') >= length(wp.name) * 0.8 THEN 'main_query'
      ELSE 'fallback_expansion'
    END as query_type
  FROM radar_core.watch_run_listing_observations o
  JOIN radar_core.watch_bindings wb ON wb.id = o.watch_binding_id
  JOIN radar_core.watch_profiles wp ON wp.id = wb.watch_profile_id
  JOIN radar_core.source_response_captures c ON c.run_id = o.watch_run_id AND c.source_id = o.source_id
  JOIN radar_core.listings ci ON ci.source_id = o.source_id AND ci.source_item_id = o.source_item_id
  WHERE wb.source_config_json LIKE '%exact_product%'
    AND o.decision_status = 'confirmed'
    AND c.raw_payload LIKE '%' || o.source_item_id || '%'
    AND c.raw_payload LIKE '%searchCondition%'
)
SELECT 
  source_id, source_item_id, item_title,
  count(*) FILTER (WHERE query_type = 'main_query') as hits_in_main,
  count(*) FILTER (WHERE query_type = 'fallback_expansion') as hits_in_expansion,
  CASE 
    WHEN count(*) FILTER (WHERE query_type = 'main_query') > 0 AND count(*) FILTER (WHERE query_type = 'fallback_expansion') = 0 THEN 'ONLY_MAIN_QUERY'
    WHEN count(*) FILTER (WHERE query_type = 'main_query') > 0 AND count(*) FILTER (WHERE query_type = 'fallback_expansion') > 0 THEN 'BOTH_MAIN_AND_EXPANSION'
    WHEN count(*) FILTER (WHERE query_type = 'main_query') = 0 AND count(*) FILTER (WHERE query_type = 'fallback_expansion') > 0 THEN 'RESCUED_BY_EXPANSION'
  END as verdict
FROM confirmed_search_hits
GROUP BY source_id, source_item_id, item_title;
```

#### 实证结果：
1. **`RESCUED_BY_EXPANSION`（仅由扩写挽救回来的商品）：0 件！**
2. 在全部可追踪的确认商品中：
   - **4 件为 `ONLY_MAIN_QUERY`**（仅由主查询命中，扩写未命中或根本未触发）；
   - **3 件为 `BOTH_MAIN_AND_EXPANSION`**（主查询本来就已经搜出来了，扩写只是冗余命中）；
   - 乐天、雅虎二手、雅虎拍卖的出货轮次中，**全部只有 1 次搜索请求（主查询）**，直接击中目标，后续详情补抓并判定 confirmed。
3. **扩写的实际危害**：
   - 2026-09-05 发生的事故误报（将路人女主剧场版 `Fes. Fine 加藤惠 A3 プリモアート` 误判为同款），正是扩写将查询缩写为 `冴えカノ プリモアート` 后，把版本不符的商品强行拉进候选池导致的。
   - **结论**：一手店必须 100% 关停扩写；二手市场即便保留，也必须将扩写次数从 2 次压至最多 1 次，且仅在主查询为 0 时触发。

### 4. 一手店的再販在数据中出现过吗？(时间尺度实证)

通过检索 `radar_core.listing_snapshots` 中一手来源（Animate、乐天、AmiAmi）的历史货态与重现事件，提取真实的再販周期：

```sql
-- 检索一手店状态变更与断档重现跨度
WITH item_snaps AS (
  SELECT 
    l.source_id, l.source_item_id, l.title, s.observed_at, s.availability,
    lag(s.availability) OVER (PARTITION BY l.id ORDER BY s.observed_at) as prev_avail,
    lag(s.observed_at) OVER (PARTITION BY l.id ORDER BY s.observed_at) as prev_observed_at
  FROM radar_core.listings l
  JOIN radar_core.listing_snapshots s ON s.listing_id = l.id
  WHERE l.source_id IN ('animate', 'cospa', 'charaon', 'amazon_jp', 'amiami', 'rakuten_ichiba', 'yahoo_shopping')
)
SELECT source_id, source_item_id, title, prev_avail, availability as new_avail,
       ROUND(EXTRACT(EPOCH FROM (observed_at::timestamptz - prev_observed_at::timestamptz)) / 86400, 1) as gap_days
FROM item_snaps
WHERE prev_avail IS NOT NULL AND prev_avail <> availability;
```

#### 实证结果：
- `animate` 商品 `3444889` (Re:Zero 4th BD 1)：`backorder` 变为 `available`（补货再販），跨度为 **21.0 天**；
- `animate` 商品 `3444895` (Re:Zero 4th DVD 2)：`backorder` 变为 `available`（补货上架），跨度为 **5.0 天**；
- `animate` 商品 `3444890` (Re:Zero 4th BD 2)：`preorder` 变为 `available`（正式发售转现货），跨度为 **28.0 天**；
- `animate` 商品 `3537647` (艾米莉亚立牌)：断档消失到重新搜出，间隔为 **13.0 天**。

#### 巡检频率结论：
一手店商品再販或补货的物理周期是 **5 至 28 天（以周或月计）**。一旦补货上架，库存通常会稳定持续在售 24~48 小时以上。因此，**一手店“每天巡检 1 次”完全充裕且已是上限**，缩短为数小时一次是毫无边际收益的算力透支。

## 三、第二优先问题分析 (业务逻辑排障)

### 5. 骏河屋异常：89 条 probable_exact，confirmed 为什么是 0？

经全量核实 09-04 以来骏河屋的 89 条 `probable_exact` 观测：
1. **85 条（95.5%）的真实货态为 `availability = 'sold_out'`**。骏河屋系统保留了大量历史已售罄商品的详情页。jpgr 系统的判定准则为“已售罄不参与购买雷达”，因此 AI 与规则层准确将其置为 `decision_status = 'rejected'`。
2. **4 条（4.5%）在售商品确实是版本不符的竞品**。例如用户盯的是 Tony 浴衣版初音色纸，骏河屋在售的是 2024 年和 2025 年赛道现场版色纸（标价 ¥460~¥630）。AI 准确指出其版本冲突并拒绝。
3. **更早历史印证**：骏河屋在 08-31 曾命中在售的奖牌展画册（¥7,900），当时被准确判为 `confirmed`。
4. **结论**：**骏河屋的匹配器与 AI 决策逻辑完全正常**。不需要调整匹配器，但必须关闭扩写以避免抓取更多历史售罄死链接。

### 6. COSPA、Chara-ON、Amazon JP 的零产出归因

1. **COSPA 与 Chara-ON（全历史 182 轮全部 0 结果）**：
   - 彻底的**厂牌与品类错配**。
   - 监控池中 6 件商品为 F:NEX 限定毛绒、讲谈社艺术画册、角川 A3 复制原画、Azone 娃娃。
   - COSPA 为自有授权服饰厂牌，Chara-ON 为垂直周边店，根本不可能收录或再販其他厂牌的限定物。这 182 轮全部属于无效空转。
   - **建议**：上线前置拦截规则，非自有授权品类禁止绑定这两家单店。
2. **Amazon JP（日亚）**：
   - 日亚共产生 8 条 `probable_exact`，确认数为 0。
   - 抽检显示日亚长词分词过于泛化，搜爱蜜莉雅毛绒玩具，返回大量第三方 Cosplay 假发（¥23,500）与非限定挂件，且许多商品标记为 `availability = 'unknown'`。
   - **建议**：日亚坚决关停扩写，仅用完整商品名强过滤，或将监控权重降为最低。

### 8. 品类 × 来源交叉分析

- **书籍/画册类 (`メダリスト展`)**：流动性最好，5 大平台均有出货，且乐天与骏河屋能提供低于拍卖炒价的捡漏机会。
- **高客单限定原画 (`プリモアート`) 与服饰**：仅在煤炉等高热度 C2C 流动，一手店与综合商城完全绝迹。
- **稀缺孤品 (`F:NEX 毛绒`、`Tony 浴衣色纸`、`Azone 娃娃`)**：全网零出货。这表明对于真正绝版的极稀缺物品，监控的意义在于“捕捉那万分之一的再販或个人挂牌”，各渠道均应收缩至最低成本维持监听。

## 四、样本量局限性声明与置信度标注

为防止小样本过度拟合，现对上述结论的确定性作严谨分级：

1. **【高置信度 · 确定结论】一手店必须关闭扩写**：
   - 依据：全历史 182+ 轮次无一例外印证一手店主查询 0 结果导致扩写 100% 空转打满；全历史确认品中扩写贡献为 0。
2. **【高置信度 · 确定结论】一手店巡检频率定为每天 1 次完全充裕**：
   - 依据：Animate / 乐天货态变更与再販跨度实测为 5~28 天，重现间隔 9~13 天。
3. **【高置信度 · 确定结论】COSPA / Chara-ON 对非自有商品为 100% 无效空转**：
   - 依据：厂牌经营范畴物理决定的不可行性，182 轮恒为 0 结果。
4. **【中等置信度 · 初步倾向】二手市场完全关停扩写还是保留 1 条**：
   - 现有样本中二手市场确认品 100% 被主查询命中，扩写无直接挽回增益；但由于当前精确同款仅 6 个核心档案（25 个确认品），样本量较小。为防止极个别个人卖家极端口语化缩写导致的漏报，**保守建议保留最多 1 条强特征短扩写，而非彻底焊死为 0**。随着未来商品池扩充至数百件，可进一步再评估。

## 五、系统埋点与数据架构改进建议

在本次分析中，由于历史表设计偏向在线运行，存在两处分析归因断层，建议在后续版本中补充埋点：

| 目标数据表 | 建议新增字段 | 当前痛点 | 改进后工程收益 |
|---|---|---|---|
| `radar_core.watch_run_listing_observations` | `matched_query text`<br>`variant_index integer` | 观测表未记录该商品是由第几条变体检索出来的，分析时必须通过 `raw_payload` 反向模糊匹配，对于 HTML 来源无法还原。 | 代码中 `candidate.hits` 本身就持有这些字段，顺手落库即可实现变体产出的 100% 精确直接统计。 |
| `radar_core.source_response_captures` | `response_summary_json text` | 目前对 HTML 类型执行 `raw_payload IS NULL`，导致 HTML 来源在排查漏报与误报时无法还原抓取现场列表。 | 无需存庞大 HTML，抓取端只需将前 10 条结果的简要标题和价格序列表转为极简 JSON 存入，兼顾低存储与 100% 现场复现。 |

## 六、报告复现完整 SQL 代码集

### SQL 1：验证各来源 09-04 以来精确同款绑定的请求与产出大盘
```sql
WITH exact_wb AS (
  SELECT id, source_id, watch_profile_id
  FROM radar_core.watch_bindings
  WHERE source_config_json LIKE '%exact_product%'
),
runs_0904 AS (
  SELECT 
    wb.source_id,
    count(r.id) FILTER (WHERE r.status = 'success') as success_runs,
    count(r.id) FILTER (WHERE r.status = 'success' AND r.result_count = 0) as zero_runs
  FROM exact_wb wb
  JOIN radar_core.watch_runs r ON r.watch_binding_id = wb.id
  WHERE substr(r.started_at, 1, 10) >= '2026-09-04'
  GROUP BY wb.source_id
),
captures_0904 AS (
  SELECT wb.source_id, count(c.id) as total_requests
  FROM exact_wb wb
  JOIN radar_core.watch_runs r ON r.watch_binding_id = wb.id
  JOIN radar_core.source_response_captures c ON c.run_id = r.id
  WHERE substr(r.started_at, 1, 10) >= '2026-09-04'
  GROUP BY wb.source_id
),
obs_0904 AS (
  SELECT 
    wb.source_id,
    count(o.watch_run_id) FILTER (WHERE o.decision_status = 'confirmed') as confirmed_obs,
    count(DISTINCT o.source_item_id) FILTER (WHERE o.decision_status = 'confirmed') as confirmed_items,
    count(DISTINCT o.source_item_id) FILTER (WHERE o.match_relation = 'probable_exact') as probable_items
  FROM exact_wb wb
  JOIN radar_core.watch_run_listing_observations o ON o.watch_binding_id = wb.id
  WHERE substr(o.observed_at, 1, 10) >= '2026-09-04'
  GROUP BY wb.source_id
)
SELECT 
  ew.source_id,
  r.success_runs,
  c.total_requests,
  round(c.total_requests::numeric / nullif(r.success_runs, 0), 1) as req_per_run,
  round(r.zero_runs::numeric / nullif(r.success_runs, 0) * 100, 1) as zero_run_pct,
  o.confirmed_obs,
  o.confirmed_items,
  o.probable_items,
  round(c.total_requests::numeric / nullif(o.confirmed_items, 0), 1) as req_per_confirmed_item
FROM (SELECT DISTINCT source_id FROM exact_wb) ew
LEFT JOIN runs_0904 r ON r.source_id = ew.source_id
LEFT JOIN captures_0904 c ON c.source_id = ew.source_id
LEFT JOIN obs_0904 o ON o.source_id = ew.source_id
ORDER BY o.confirmed_items DESC NULLS LAST, c.total_requests DESC;
```

### SQL 3：验证一手店货态变动周期（以 Animate 为例）
```sql
WITH item_snaps AS (
  SELECT 
    l.source_id, l.source_item_id, l.title, s.observed_at, s.availability,
    lag(s.availability) OVER (PARTITION BY l.id ORDER BY s.observed_at) as prev_avail,
    lag(s.observed_at) OVER (PARTITION BY l.id ORDER BY s.observed_at) as prev_observed_at
  FROM radar_core.listings l
  JOIN radar_core.listing_snapshots s ON s.listing_id = l.id
  WHERE l.source_id = 'animate'
)
SELECT source_item_id, title, prev_avail, availability as new_avail, prev_observed_at, observed_at,
       ROUND(EXTRACT(EPOCH FROM (observed_at::timestamptz - prev_observed_at::timestamptz)) / 86400, 1) as gap_days
FROM item_snaps
WHERE prev_avail IS NOT NULL AND prev_avail <> availability;
```
