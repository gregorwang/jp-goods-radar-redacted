# 格银西里尔 Web UI 设计与实现指南

本文供后续会话中的 UI 设计、视觉重构、组件完善和动效实现使用。目标不是缩短工时，而是在正确理解参考、产品语义和组件技术边界的前提下，把界面做准确、做美观，并留下可复核的视觉证据。

速度不是本指南的验收指标。不能为了少做几步而跳过参考站观察、交互状态检查、移动端检查或无障碍验证。与此同时，也不要用与 UI 风险无关的后端排查制造“看起来很全面”的工作量；验证应与改动范围相称。

## 2. 产品视觉语义

格银西里尔不是普通后台模板，也不是动漫官网复刻。它是一个安静工作的私人商品观测室，视觉应同时表达：

- 纸张、档案、信号记录和长期观察；
- 克制、可靠、私人使用，而不是营销式热闹；
- 日本编辑设计的留白与精细排版；
- 来源状态、价格变化和监控证据的清楚层级。

应保留的设计语言：

- 近白纸张背景和轻微雾蓝透明层；
- 大面积留白，而不是用卡片填满所有空间；
- 明朝/宋体式展示标题，小字号无衬线或等宽辅助信息；
- 1px 细线、低对比边界和有限的青蓝状态强调；
- 纵排注释、坐标、英文小标题，以及确有含义的证据编号等编辑式细节；
- 柔和树影、纸张纹理和克制的模糊；
- 有呼吸感的进入、展开和切换动画。

应避免：

- 大面积黑色侧栏、黑色搜索框或黑色表单块；
- 到处使用圆角卡片、胶囊按钮和强阴影；
- 每个区域都加渐变、发光或动画；
- 为了“高级感”降低正文可读性；
- 把参考站的亮青色机械复制到所有控件；
- 使用假的历史、商品、事件或订阅填充截图。

## 3. 从参考站提炼出的层级规则

### 3.1 字体

参考站的核心不是某一个字体名称，而是字体角色分工：

- 大标题和叙事标题使用轻至常规字重的明朝体，依靠字号、留白和行距形成气质；
- 导航、按钮、标签使用小号无衬线体，字重偏轻，增加字距；
- 编号、状态、时间和系统代码使用极小等宽字或几何无衬线体；
- 不依靠粗体制造所有层级。

当前项目对应字体变量位于 `src/app/globals.css`：

- `--display`：展示标题、商品标题、选中值和重点数字；
- `--sans`：正文、表单和导航；
- `--mono`：编号、状态、坐标、代码和时间。

建议层级，而非每处必须完全相同：

- 页面主标题：`clamp()` 响应式大字号，字重约 400–500；
- 区块标题：约 26–43px 的展示体；
- 控件当前值：约 16–19px 的展示体；
- 正文：约 11–13px，行高 1.7–2；
- 导航和标签：约 8–10px，增加字距；
- 代码、编号、时间：约 7–10px 的等宽字。

字号小不等于信息不重要。小字号必须配合足够对比度、留白和清晰的分组关系。

### 3.2 颜色

优先使用现有设计变量，不在组件里随意创造新的近似颜色：

- `--paper` / `--paper-bright`：页面和浮层纸张；
- `--ink` / `--ink-soft`：主文字和辅助文字；
- `--muted`：编号、说明和次级状态；
- `--line` / `--line-strong`：结构边界；
- `--blue` / `--blue-deep`：焦点、选中和重要状态；
- `--acid-soft`：极轻的选中或悬停底色。

青蓝是信号，不是大面积装饰。一个视区中应能明确看出哪里是真正的当前状态或操作焦点。

### 3.3 线条、留白和材质

- 结构优先使用 1px 线条，而不是厚边框和圆角容器；
- 一个区块内部先依靠网格、对齐和留白分组，边框只承担必要结构；
- 浮层可以使用近白背景、轻模糊和较深阴影，但不能变成与页面无关的通用后台菜单；
- 纸张纹理、树影和雾蓝背景必须保持低透明度，不能妨碍文字。

## 4. 动效规则

参考站的重要动效特征：持续时间克制、位移很短、透明度变化平滑，并经常配合轻微模糊。

当前可复用的节奏：

- 普通悬停和图标变化：约 220–300ms；
- 菜单、下拉和区块进入：约 300–400ms；
- 大型叙事内容揭示：约 600–1200ms；
- 推荐缓动：`cubic-bezier(.215,.61,.355,1)`；
- 更柔和的大幅运动可使用 `cubic-bezier(.16,1,.3,1)`。

动效必须有语义：

- 展开：提示层级被打开；
- 位移：提示焦点或选择变化；
- 透明度与模糊：提示内容进入或离开；
- 箭头旋转：提示开合状态。

不要为静态正文添加持续漂浮。所有动画必须在 `prefers-reduced-motion: reduce` 下被关闭或压缩到近乎即时。

## 5. 先选对组件模型，再做视觉

这是本项目 UI 工作最重要的技术经验。

### 5.1 原生控件的边界

浏览器原生 `<select>` 的闭合外壳可以被部分样式化，但展开后的选项面板通常由浏览器或操作系统绘制，无法完整控制字体、间距、分隔线、动画和选中状态。

当设计目标明确要求自定义展开层时，不要继续在原生 `<select>` 外面堆 CSS。应使用经过验证的无障碍 primitive，例如当前项目使用的 `@radix-ui/react-select`，再用项目 CSS 完成视觉。

原生控件仍适合：

- 不要求自定义展开层；
- 浏览器一致性不是验收条件；
- 移动端原生选择体验比品牌视觉更重要。

自定义 primitive 适合：

- 展开层是设计的重要组成部分；
- 需要选项分层、编号、状态图标或自定义动画；
- 需要可靠处理方向键、Enter、Space、Esc、焦点、触屏和碰撞定位。

### 5.2 不要手写不完整的 ARIA 控件

弹层、对话框、组合框、菜单和选择器涉及焦点管理、键盘导航、Portal、碰撞检测和读屏语义。除非有充分理由和完整测试，不要用几个 `div`、`role` 和 `useState` 临时拼出一个“看起来能用”的控件。

### 5.3 先做共享 primitive

当多个页面存在同类 UI，应先确定共享组件的语义和状态，再在页面内组合。优先候选包括：

- Editorial Select；
- 输入框与筛选器；
- 状态标签和来源状态；
- 弹层、确认对话框和 Drawer；
- 页面标题、章节标题和纵排注释；
- 表格、时间线和证据列表；
- 桌面侧栏与移动底部导航。

共享不是为了减少文件数量，而是为了保证同一语义具有同一视觉和交互规则。

## 6. 侧栏与参考站菜单的关系

参考站使用的是叙事型官网菜单；本项目是高频工具，需要持续可达的主导航。因此不能机械照搬全屏 Drawer。

当前正确适配是：

- 桌面保留固定侧栏，以满足工具型信息架构；
- 支持收缩为窄轨，保留图标、当前页和展开入口；
- 收缩状态持久化；
- 移动端改为底部导航，不把桌面窄轨硬塞进 390px 视口；
- 从参考站继承细线、轻字重、英文小标题和开合节奏，而不是复制其页面结构。

导航序号只有在确实表达流程、时间或证据索引时才成立。主导航页面不存在固定阅读顺序，因此不能为了“编辑感”添加 `01–06`；无语义序号会削弱图标和当前页的识别。

判断一个侧栏是否成功，不能只看“能不能收缩”，还要看：

- 收缩后当前页是否仍清楚；
- 展开入口是否可发现并有可访问名称；
- 主内容宽度和视觉重心是否自然变化；
- 状态刷新后是否保留；
- 移动端是否没有横向溢出或遮挡关键操作。

## 7. 质量优先的 UI 工作流程

### 阶段 A：建立真实基线

1. 记录当前分支、生产版本和工作树状态。
2. 用浏览器打开待改页面，保存桌面与移动端截图。
3. 操作所有相关状态：默认、悬停、焦点、展开、选中、空状态、错误状态、加载状态。
4. 打开参考站相近区域，观察相同状态和转场。

不能只看参考站首屏，也不能只看当前页面的静态截图。

### 阶段 B：写出设计判断

动手前应能明确回答：

- 当前页面最重要的信息是什么？
- 用户下一步最可能做什么？
- 哪些内容属于展示体、正文、标签、代码或状态？
- 当前问题是颜色、层级、布局，还是组件模型错误？
- 哪些视觉语言来自参考站，哪些必须因工具语义而调整？
- 哪些状态在现有实现中尚未被设计？

如果这些问题还无法回答，应继续观察和分析，而不是开始堆 CSS。

### 阶段 C：实现

1. 优先修正组件模型和 DOM 语义。
2. 复用现有 token；确需新增 token 时说明用途。
3. 按层级顺序完成布局、字体、颜色、线条、材质，最后才是动画。
4. 保持严格 TypeScript；选项和状态使用字面量联合或 schema，不用无约束断言。
5. 不把视觉组件与 API、数据库或来源逻辑耦合。

### 阶段 D：逐状态视觉验收

每个交互组件至少核验：

- 默认态；
- hover；
- focus-visible；
- open / active；
- selected / checked；
- disabled（如果存在）；
- 键盘操作；
- 点击外部与 Esc 关闭；
- 视口边缘碰撞和长内容；
- `prefers-reduced-motion`。

页面级至少核验：

- 约 1440px 桌面；
- 约 390×844 移动端；
- 有真实长数据的页面；
- 空状态和图片失败占位；
- 无横向溢出；
- 关键操作在首屏或合理滚动后可达。

### 阶段 E：代码和发布验收

纯 UI 改动按影响范围选择最小必要检查，通常从以下命令中选取相关项：

```powershell
pnpm --filter @jpgr/web typecheck
pnpm --filter @jpgr/web lint
python tests/browser_verify.py
git diff --check
```

如果 UI 改动没有改变 API 合约、数据库、Collector 或来源适配器，不要主动开展数据库、来源探针或 Worker 行为排查，也不要固定运行完整测试、完整浏览器套件或生产构建。验证必须与实际风险相称。

生产 Web 由 Cloudflare Workers Builds 从 `main` 直接构建和部署，不经过 GitHub Actions 或 artifact 中转。运行时代码变化上线后，再按风险查看真实生产页面和关键交互；文档或交付流程改动不触发应用部署。

## 8. Events 下拉组件案例

### 失败方案

旧实现使用原生 `<select>`，外层添加渐变、边框、标签和箭头。闭合状态得到改善，但展开选项仍是系统原生面板，导致：

- 展开层与页面字体和颜色不一致；
- 无法实现项目需要的编号、代码层级和选中标记；
- 无法稳定控制展开动画；
- 只修饰了问题的外壳，没有改变真正被用户看到的选项层。

### 成功方案

当前实现位于：

- `src/components/editorial-select.tsx`
- `src/components/event-manager.tsx`
- `src/app/globals.css`

关键判断：

- 使用 Radix Select 负责语义、焦点、键盘和浮层定位；
- 使用项目 CSS 负责全部视觉；
- 中文选项、系统代码、编号和选中标记分层展示；
- 采用细线结构、近白纸张、轻青蓝选中底色；
- 使用约 340ms 的轻模糊进入动画；
- 移动端改为单列，保留触控尺寸；
- 浏览器测试覆盖展开截图、选择、Esc、侧栏收缩和 390px 视口。

这个案例的通用结论不是“所有 select 都换成 Radix”，而是：先判断真正需要设计的是哪一层，再选择能够控制那一层的正确组件模型。

## 9. 常见失败模式

- 只搜索文件名，没有在浏览器中查看参考站；
- 只看默认态，没有打开菜单、弹层或 Drawer；
- 把参考站理解成一组颜色，而没有理解字体和留白；
- 在错误的原生控件边界外不断补样式；
- 所有文字都使用相同字号和字重；
- 为每个信息块增加独立圆角卡片；
- 桌面好看后直接宣称移动端完成；
- 截图时使用假数据，掩盖长标题和长列表问题；
- UI 任务扩大为无关的后端健康排查；
- 本地视觉尚未稳定就频繁提交和部署；
- 为了赶时间跳过真实生产页面核验。

## 10. 搜索结果页的信息与 AI 规则

搜索结果不是来源字段的陈列柜，而是用户判断“是不是这个商品、现在能不能买、值不值得关注”的决策界面。卡片的信息优先级固定为：

1. 可购买状态与当前价格；价格缺失时明确写“价格待确认”，不能留白、显示 `¥0` 或把缺失值参与价格排序；
2. 商品身份，包括来源、标题、版本、店铺或卖家、来源商品 ID；
3. 经证据约束的 AI 摘要、品相、缺陷、缺件和包含物；
4. 品牌、作品、尺寸、材质、发布日期等确实有助于辨认或比较的来源事实；
5. “加入关注档案”和“打开来源页”两个下一步操作。

分类字段可以作为 AI 理解上下文或审计来源，但只有在能帮助用户区分商品时才进入主信息层，不能因为抓取到了字段就机械展示。价格、状态和重要商品事实不能藏在“卡内详情”里；原文证据可以放在原生 `<details>` 中供审计。

搜索结果页的主操作是先把商品加入关注档案。目标价属于关注建立后的监控策略，应在单品关注详情中设置或清除；用户不设目标价时仍可记录价格与补货变化。

搜索结果筛选必须复用 Events 已验证的 `EditorialSelect`，保持同一语义、键盘行为、字体层级和浮层动效，不能退回只修饰外壳的原生 `<select>`。

页面内的 Gemini 请求应串行执行，避免同一搜索同时占用免费层配额。批量商品整理必须逐条校验证据并隔离失败项，不能因一条不合格内容让整页失败；修改提示词、schema 或证据规则时必须同步升级缓存版本，避免旧的无效响应持续命中。

## 11. UI 完成定义

一个 UI 任务只有同时满足以下条件才算完成：

- 产品语义、信息优先级和用户操作路径清楚；
- 与参考站共享的是设计原则，而不是被复制的素材；
- 组件模型能够支持目标视觉和全部交互状态；
- 字体、字号、字重、行高、字距、颜色和留白都有明确层级；
- 桌面和移动端均经过真实浏览器查看；
- 键盘、焦点、Esc、触屏和 reduced motion 与风险相称地验证；
- 没有横向溢出、关键内容遮挡或不可读低对比；
- 与改动范围相称的类型检查、lint、构建或浏览器验证通过；
- Cloudflare Workers Builds 完成生产构建和部署；
- 生产页面再次验证，不用乐观措辞代替证据。

## 12. 新会话交接模板

新的 UI 会话开始时，可按下面格式快速建立上下文，但仍必须亲自查看页面：

```text
本次只处理 apps/web 前端 UI。
请先阅读根目录 AGENTS.md、apps/web/AGENTS.md 和 apps/web/UI_DESIGN_GUIDE.md，
再用浏览器查看当前生产页、本地页和 kakekoi 参考站。

目标页面：
需要改善的区域：
用户认为不好的具体状态：
必须保留的业务语义：
需要覆盖的桌面/移动端状态：

不要凭静态代码猜视觉；不要把纯 UI 工作扩大为无关后端排查。
质量、美观和准确性优先，不得为了节省时间跳过参考研究与视觉验收。
```

交付时应明确区分：

- 已实现并在本地浏览器验证；
- 已通过 Cloudflare 构建；
- 已部署生产；
- 已在生产实测；
- 只是设计建议，尚未实现。
